workstation dev env

Dev-environment provisioning for Linux hosts, plus the WezTerm config that connects to them from Windows. A single Makefile under makefile/ drives everything — system packages, PATH, tool installs, and the chezmoi handoff for dotfiles. bootstrap.sh is a thin seed that runs make MODE=dev|prod provision. Adding a tool is a two-line edit.

🐧 First-time setup on a Linux host

Pick prod for no-sudo / user-wide install, dev for sudo / system-wide. Sets a token + identity, then pipes bootstrap.sh. 

export GITHUB_TOKEN='<your-PAT>' \
       GIT_USER_NAME='Arrush Chaturvedi' \
       GIT_USER_EMAIL='contact@arrushc.com' && \
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh \
  | bash -s -- --prod

🪟 First-time setup on Windows

Run from an elevated PowerShell. Installs choco + tools, applies dotfiles, hard-links the wezterm config. 

$env:GITHUB_TOKEN  = '<your-PAT>'
$env:GIT_USER_NAME  = 'Arrush Chaturvedi'
$env:GIT_USER_EMAIL = 'contact@arrushc.com'
irm -Headers @{Authorization="token $env:GITHUB_TOKEN"} `
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.ps1 | iex

Machine types

Every host belongs to exactly one group in hosts.conf. The group decides the provisioning MODE — no separate scope flag.

Group Sudo Binary dest Helix runtime Used for
dev_machine Yes /usr/local/bin /usr/local/lib/helix/runtime Hosts you own — full system-wide install via OS package manager (dnf on RHEL/Fedora) + /usr/local/bin.
prod_machine No ~/.local/bin ~/.config/helix/runtime Hosts you don’t fully own — user-wide install only, no system packages.

Scope values live in makefile/scope.mk, keyed off MODE=dev|prod. bootstrap.sh derives MODE from its --dev / --prod flag (exactly one is required); scripts/update-hosts.sh derives it from each host's group column in hosts.conf for bulk remote updates.

Setup

1. Configure once

Update before pushing your fork:

  • bootstrap.sh — if you forked the repo, change DOTFILES_REPO at the top of the script to point at your fork's clone URL.
  • hosts.conf — add hosts with ./scripts/manage-hosts.sh --add ... (or edit and --format), or let bootstrap.sh self-register them.

2. On each Linux host

bootstrap.sh needs only curl, git, make, tar, unzip, and iproute (ip). A single preflight check reports all missing prereqs at once. The script then runs make MODE=<dev|prod> provision inside makefile/ — no ansible-core install, no Python ≥ 3.9 gate.

Env vars to set before running

Var Why
GITHUB_TOKEN Authenticates the curl fetch of bootstrap.sh + the script’s internal git clone/pull/push. Persisted into .git/config so chezmoi update, manual git pull, and the auto-push step keep working without re-passing it. Never committed. Generate at github.com/settings/tokens with repo scope (classic) or Contents:Read (fine-grained).
GIT_USER_NAME Author name on the auto-registration commit (falls back to whoami).
GIT_USER_EMAIL Author email on the auto-registration commit (falls back to whoami@hostname).

Keep these in a password manager (1Password, Bitwarden, KeePass) so the token and identity travel together.

Copy-paste one-liner

Binaries → ~/.local/bin · no dnf step. 

# === Bootstrap: prod machine (no sudo, ~/.local/bin) ===
export GITHUB_TOKEN='<your-PAT>' \
       GIT_USER_NAME='Arrush Chaturvedi' \
       GIT_USER_EMAIL='contact@arrushc.com' && \
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh | bash -s -- --prod && \
exec zsh   # or: source ~/.bashrc, if you can't chsh on this host

Binaries → /usr/local/bin · installs system packages via dnf. 

# === Bootstrap: dev machine (sudo, /usr/local/bin + system packages) ===
export GITHUB_TOKEN='<your-PAT>' \
       GIT_USER_NAME='Arrush Chaturvedi' \
       GIT_USER_EMAIL='contact@arrushc.com' && \
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh | bash -s -- --dev

What bootstrap.sh does, in order

1Preflight
→
2Clone repo~/.local/share/chezmoi

→

→

Self-registration uses hostname -s, detected primary IP, whoami, and the group from --dev/--prod. Push failures (auth, conflict, no upstream) print a recovery command but don’t abort — provisioning has already succeeded. Both modes are idempotent; re-run any time. After bootstrap, copy your SSH key from a client — see Host management → Copy SSH key.

dev Claude Code statusline prompt

At the tail of bootstrap.sh --dev, after chezmoi initializes, you’ll be prompted to configure the Claude Code statusline via ccstatusline. Four options:

  1. Use the chezmoi-tracked status line — apply the tracked widget config + Claude Code settings (same look as every other dev_machine).
  2. Define a new status line for this machine — launch the ccstatusline TUI; on save, choose whether to persist across future chezmoi update runs (a yes adds this host to a per-host opt-out block in .chezmoiignore.tmpl).
  3. Set a new global status line — launch the TUI; on save, the result is re-added to the chezmoi source, committed, and pushed so every other dev_machine picks it up on next sync.
  4. Skip — no setup this run.

Re-runnable any time: make -C makefile claude-statusline MODE=dev. Auto-installs Linux-native Node.js (pinned LTS) as a dep via make -C makefile node-runtime MODE=dev, so a fresh dev_machine doesn’t need npx on PATH beforehand. The ccstatusline version is pinned in makefile/versions.mk via CCSTATUSLINE_VERSION; Node version via NODE_VERSION.

dev JetBrainsMono Nerd Font Mono

make provision MODE=dev runs the nerd-fonts target, which installs JetBrainsMono Nerd Font Mono to ~/.local/share/fonts/JetBrainsMonoNerdFontMono/ and refreshes the fontconfig cache. The font is required for Nerd Font glyphs in starship, eza --icons=auto, lazygit, k9s, yazi, broot, helix file-tree, chezit, ccstatusline, and the Claude Code TUI.

WSL hosts skip this step automatically — WSL apps render via WezTerm on the Windows host, which reads Windows-registered fonts. Run bootstrap.ps1 on the Windows side to install the font there instead (step 8: Invoke-InstallNerdFonts via scripts/install-nerd-fonts.ps1). Re-runnable any time: make -C makefile nerd-fonts MODE=dev. Font version pinned in makefile/versions.mk via JETBRAINSMONO_NERD_VERSION.

Reinstalling from scratch (--reinstall)
Linux 
./bootstrap.sh --prod --reinstall              # prompts before wiping
./bootstrap.sh --dev  --reinstall --yes        # skip prompt

# From outside the repo (script in memory, won’t self-delete):
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh | bash -s -- --prod --reinstall --yes
Windows 
.\bootstrap.ps1 -Reinstall          # prompts before wiping
.\bootstrap.ps1 -Reinstall -Yes     # skip prompt

# From outside the repo:
irm -Headers @{Authorization="token $env:GITHUB_TOKEN"} `
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.ps1 | iex

Wipes: the cloned repo (~/.local/share/chezmoi / C:\Git\workstation) and chezmoi’s config dir (~/.config/chezmoi/).

Does not wipe: installed tools (re-bootstrap detects and skips), deployed dotfiles in $HOME (chezmoi re-applies over them), SSH keys, system packages.

Self-deletion guard. Running .\bootstrap.ps1 -Reinstall from inside the repo would delete the script while executing. Both scripts detect this and refuse with a clear message — use the curl/irm-pipe form or copy the script outside first.

3. On Windows

The Windows host is a client — no provisioning Makefile (that's Linux-only), but chezmoi runs here too to deploy wezterm.lua, the PowerShell profile, Zed/VSCode settings. bootstrap.ps1 is the parallel of bootstrap.sh.

Run from elevated PowerShell. Chocolatey needs admin to install, as do most package installs. Right-click PowerShell → “Run as administrator”. With -SkipToolInstall, elevation is not required.

Tools installed (via Chocolatey): chezmoi, Git, Starship, zoxide, WezTerm, Zed, VSCode. Required: chezmoi, Git. Optional ones warn-not-fail. Choco rather than winget because winget’s PATH propagation is unreliable mid-session.

JetBrainsMono Nerd Font Mono (per-user) — installed to %LOCALAPPDATA%\Microsoft\Windows\Fonts\ and registered under HKCU\Software\Microsoft\Windows NT\CurrentVersion\Fonts by scripts/install-nerd-fonts.ps1 (invoked from bootstrap.ps1 step 8). Per-user install — no admin needed for the registry registration even though bootstrap.ps1 itself runs elevated. Visible to WezTerm, Zed, VS Code, and any other Windows app. Font version matches JETBRAINSMONO_NERD_VERSION in makefile/versions.mk.

One-liner (elevated PowerShell)

# === Bootstrap: Windows client ===
$env:GITHUB_TOKEN  = '<your-PAT>'
$env:GIT_USER_NAME  = 'Arrush Chaturvedi'
$env:GIT_USER_EMAIL = 'contact@arrushc.com'
irm -Headers @{Authorization="token $env:GITHUB_TOKEN"} `
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.ps1 | iex

Or after cloning manually

git clone https://github.com/ArrushC/workstation.git `
  "$env:USERPROFILE\.local\share\chezmoi"
cd "$env:USERPROFILE\.local\share\chezmoi"
.\bootstrap.ps1                                  # default flow (must be elevated)
.\bootstrap.ps1 -RepoPath D:\dev\workstation     # alternate clone path
.\bootstrap.ps1 -SkipToolInstall                 # tools already installed; non-elevated OK
.\bootstrap.ps1 -SkipChezmoi                     # clone + install but don’t deploy dotfiles
.\bootstrap.ps1 -SkipKeyGen                      # skip the SSH-key prompt

Default clone path is %USERPROFILE%\.local\share\chezmoi, which matches bootstrap.sh’s $HOME/.local/share/chezmoi and chezmoi’s own default source directory. If you previously cloned to the pre-v2 default C:\Git\workstation, bootstrap.ps1 detects it and offers to move the clone to the new location. Pass -RepoPath C:\Git\workstation to keep the legacy path, or -Yes to auto-move without prompting.

What bootstrap.ps1 does

1Preflightadmin check
→
2Bootstrap Choco + tools
→
3Clone repo
→
4chezmoi init --apply
→
5Set WEZTERM_CONFIG_FILEUser env var
→
6SSH keyprompt

Admin is required only if there are required tools to install. If everything’s on PATH, no admin needed and the install step short-circuits. GITHUB_TOKEN persists into .git/config (github.com-scoped) so subsequent git push, chezmoi update, and manage-hosts.ps1 ops authenticate without re-passing the env var.

WezTerm config model: chezmoi tracks chezmoi/dot_config/wezterm/wezterm.lua as the canonical source, but .chezmoiignore.tmpl skips dot_config/wezterm on Windows — chezmoi never writes a copy to %USERPROFILE%\.config\wezterm\. Step 5 instead sets a User-scope environment variable WEZTERM_CONFIG_FILE pointing directly at the chezmoi source path. WezTerm reads the repo file live, so edits (including manage-hosts.ps1 -Sync rewriting the sentinel block) appear immediately via automatically_reload_config. This replaces the pre-v2 hardlink mechanism, which broke whenever chezmoi atomic-wrote the target on a content mismatch. Bootstrap also cleans up any legacy %USERPROFILE%\.config\wezterm\wezterm.lua left from prior hardlinked installs, so a stale fallback can’t silently win if you ever unset the env var.

After bootstrap, restart your shell so the chezmoi-applied $PROFILE picks up — starship prompt, cz/cza/cze/czd/czu/czs aliases, git aliases, etc. Editing dotfiles: same workflow as Linux. cze <path> opens the source-state copy; cza applies; czd shows the diff; cz cd jumps to the source dir for direct git ops.

Bootstrapping WSL distros

WSL distros are first-class managed hosts — same tools, same chezmoi-tracked zshrc + starship prompt + aliases as a real Linux box. They’re accessed through wezterm’s WSL domain mechanism, not SSH, so bootstrap.sh auto-detects WSL ($WSL_DISTRO_NAME / /proc/version) and skips the hosts.conf self-registration step. The rest of the flow (tool install, dotfiles apply) runs unchanged.

Open a WSL tab in WezTerm (or wsl.exe in any shell) and run: 

# Inside the WSL distro:
sudo dnf install -y curl git python3 python3-pip iproute    # RHEL / AlmaLinux / Fedora
# or: sudo apt install -y curl git python3 python3-pip iproute2   # Debian / Ubuntu
export GITHUB_TOKEN='<your-PAT>'
export GIT_USER_NAME='Arrush Chaturvedi'
export GIT_USER_EMAIL='contact@arrushc.com'
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh | bash -s -- --dev

Use --dev for WSL distros where you have sudo (the common case — you own the WSL host). Tools land in /usr/local/bin, starship + aliases + fzf + zoxide + zellij all become available on next shell.

Why WSL tabs land in ~: Two complementary mechanisms in chezmoi/dot_config/wezterm/wezterm.lua: (1) default_cwd = '~' on every WSL domain, so a fresh WSL tab cd’s to the WSL user’s home instead of inheriting wezterm’s own cwd (typically /mnt/c/Users/<windows-user>); and (2) a smart_new_tab callback bound to CTRL+SHIFT+T that forces cwd = '~' for WSL panes whose cwd isn’t tracked — otherwise act.SpawnTab 'CurrentPaneDomain' would fall back to wezterm’s own cwd on every new tab. Without these, the default bash prompt renders \W as the literal Windows-user folder name instead of substituting ~.

Cwd tracking via OSC 7: the chezmoi-tracked ~/.zshrc (and ~/.bashrc for bash fallback) emits an OSC 7 file://<host>/<pwd> sequence after every prompt (__wezterm_osc7 wired via add-zsh-hook precmd in dot_zshrc.tmpl; PROMPT_COMMAND append in dot_bashrc.tmpl). Once WSL is bootstrapped, cd /tmp followed by CTRL+SHIFT+T lands the new tab in /tmp, not ~ — smart_new_tab sees the tracked cwd and defers to wezterm’s normal inheritance. Pre-bootstrap (default WSL bash, no OSC 7), the callback’s fallback keeps new tabs in ~.

Truecolor signaling. Every chezmoi-managed shell exports COLORTERM=truecolor on startup (see dot_zshrc.tmpl / dot_bashrc.tmpl) and WezTerm advertises TERM=wezterm to every spawned PTY (config.term in wezterm.lua). Apps querying terminfo see Tc, Smulx, and Setulc — full 24-bit RGB plus extended underline capabilities — via the vendored wezterm.terminfo at chezmoi/dot_local/share/wezterm/, which a chezmoi run_onchange script compiles into ~/.terminfo/ on every apply. Verify with infocmp wezterm (exit 0; lists Tc, Smulx, Setulc) and echo $TERM in a new pane (prints wezterm).

Shell prompt selection

At the zsh prompt, SHIFT+arrow keys select text like a normal editor — extend a highlight, type to replace it, BACKSPACE to delete it. These bind in the shell line editor only, so any full-screen tool (helix, fzf, less) keeps its own SHIFT+arrow behaviour. bash maps the same keys to plain cursor movement (no highlight — a readline limitation).

Bind Action
SHIFT+← / SHIFT+→ Extend selection by character
CTRL+SHIFT+← / CTRL+SHIFT+→ Extend selection by word
SHIFT+HOME / SHIFT+END Extend selection to line start / end
Type any character Replace the selection (zsh)
BACKSPACE / DELETE Delete the selection (zsh)
ALT+W / CTRL+W / CTRL+Y Copy / cut / paste selection (zsh) — copy also reaches the system clipboard via OSC 52, including over SSH

Completion & suggestions

The zsh prompt loads five vendored, pinned plugins from ~/.config/zsh/plugins/ — zsh-only (bash keeps system completion + readline history search); deploy on both dev and prod; Windows-ignored. Three wired tools — atuin, broot, yazi — round out history search and directory navigation.

Plugin What it does
zsh-autosuggestions v0.7.1 A greyed-out suggestion from history appears as you type — press → or End to accept it. Themed Catppuccin overlay0 (#6c7086).
zsh-syntax-highlighting 0.8.0 Live command-line coloring as you type — unknown commands in red, valid ones in green, quoted strings and paths distinguished. Themed Catppuccin Mocha. Sourced last (it wraps ZLE widgets).
fzf-tab v1.3.0 Tab becomes an fzf picker that reuses the same Catppuccin theme as Ctrl-R / Ctrl-T. < / > switch between completion groups, and Tab on a directory descends into it. Files preview with bat, directories with eza.
zsh-history-substring-search v1.1.0 Type part of a past command, then ↑ / ↓ walk through the history entries containing it.
zsh-you-should-use 1.11.1 After you run a command that has an alias defined, prints a reminder to use the alias (e.g. 💡 gs) — soft mode, it never blocks.

Resulting prompt key map: Ctrl-R atuin history search · ↑/↓ substring history · → accept suggestion · Tab fzf completion · Shift+arrows select. For directory navigation: z/zi (zoxide), br (broot fuzzy tree → cd), y (yazi file manager → cd). atuin and the five plugins are zsh-only; br/y work in bash too.

Host management

hosts.conf is the single source of truth. One output is regenerated from it: the chezmoi/dot_config/wezterm/wezterm.lua SSH-domains block (in-place replace between -- HOSTS:START / -- HOSTS:END sentinels). On Linux WezTerm is irrelevant; on Windows, edits propagate live via WEZTERM_CONFIG_FILE — no chezmoi apply needed for that file.

scripts/update-hosts.sh reads hosts.conf directly when doing bulk remote updates — the group column drives the per-host MODE.

Group must be dev_machine or prod_machine. Both manage-hosts scripts validate the input and reject anything else — an unknown group means update-hosts.sh can't derive MODE from it. Interactive prompt defaults to prod_machine.

Don’t hand-pad hosts.conf. The save routine recalculates column widths from data; manual padding gets normalised away on next save. Auto-sorted by group, then by name, on every save — manual reordering won’t survive.

  • Looks the host up in hosts.conf and uses its User/Ip columns.
  • If id_ed25519 is missing, prompts to generate one with ssh-keygen -t ed25519 -N "" (no passphrase). Decline and the command exits without copying.
  • Linux uses native ssh-copy-id if available; otherwise falls back to a manual SSH method that de-duplicates the file. Windows always uses the manual method (no ssh-copy-id in Windows OpenSSH).

Useful right after bootstrapping a fresh client.

Adding tools & hosts

Adding a new tool

Two files, one line each. Tool installs live in makefile/ — make provision invokes them as part of the normal bootstrap flow. There are three macros; prefer EGET_TOOL for single-binary GitHub releases (the common case — ~42 of the current 60 tools use it).

  1. Pin the version in makefile/versions.mk.
  2. Add one $(eval $(call EGET_TOOL,<name>,$(<NAME>_VERSION),<user/repo>[,<tag>][,<extra args>])) line in makefile/tools.mk. The 4th arg overrides the default v$VERSION tag (use it for tools like delta whose tag is 0.19.2, not v0.19.2). The 5th arg passes flags to eget — commonly --asset musl when upstream publishes both gnu and musl variants. 
# makefile/versions.mk
DIRENV_VERSION := 2.34.0
# makefile/tools.mk
$(eval $(call EGET_TOOL,direnv,$(DIRENV_VERSION),direnv/direnv))

eget figures out the right asset from direnv/direnv + the tag, downloads it, finds the binary inside, and installs to $(DEST). The wrapper at lib/eget.sh bakes in noise filters (.sbom, .sig, .deb, etc.) so eget's auto-detection almost always picks unambiguously.

Fallback to TOOL for the shapes eget can't handle: multi-binary archives with junk files (age has LICENSE, yazi has shell completions), non-GitHub URLs (ncdu at dystroy.org), raw binary URLs (jq, broot, sops), curl-pipe installers (chezmoi, claude), or helix's binary-plus-runtime layout. Use the matching helper: archive.sh, direct.sh, pipe.sh, or helix.sh. Fallback to USER_TOOL for pip user-site tools. Do not add tool-specific logic to bootstrap.sh or invent a parallel install path under scripts/.

Sanity-test before pushing (set GITHUB_TOKEN to avoid eget's unauthenticated rate limit): 

cd makefile
make direnv MODE=prod DEST=/tmp/install-test STAMP=/tmp/install-test-stamps
ls /tmp/install-test/direnv            # binary present?
make direnv MODE=prod DEST=/tmp/install-test STAMP=/tmp/install-test-stamps   # second run: no output (stamp protected)

Bumping a tool version

Edit one line in makefile/versions.mk and commit. The version is baked into the stamp filename at $STAMP/<tool>-<version>.done, so the change invalidates the old stamp; the next make all redownloads the new release automatically. No make clean needed.

Multi-binary tools split into two camps. eget with --all covers archives containing only the binaries we want (ast-grep ships sg+ast-grep, uv ships uv+uvx). archive.sh with a colon-separated binary spec covers archives that also have LICENSE / completion files we don't want to install (age, yazi). See makefile/tools.mk for both patterns.

Troubleshooting

Bootstrap reports “Missing required prerequisites: …”

Install all listed tools at once via your distro’s package manager.

RHEL/Fedora: sudo dnf install curl git python3 python3-pip iproute

Debian/Ubuntu: sudo apt install curl git python3 python3-pip iproute2

Bootstrap deliberately collects every gap up front so you only have to install once.

Bootstrap finishes with “Push failed (auth, conflict, or no upstream)”

Provisioning succeeded — only the host-list push didn’t.

Recover with cd ~/.local/share/chezmoi && git push.

Common causes: no SSH key for the git remote, a divergent upstream (git pull --rebase first), or you’ve forked and never set the remote.

Private repo: clone fails with “Authentication failed” or 404

Set GITHUB_TOKEN to a PAT with repo (classic) or Contents:Read (fine-grained) scope and re-run.

The token is written into .git/config as http.https://github.com/.extraheader so subsequent ops (push, chezmoi update, manual git pull) all work — re-passing the env var on later runs just refreshes the stored value.

To clear: git -C ~/.local/share/chezmoi config --unset http.https://github.com/.extraheader.

manage-hosts.sh --copy-id keeps prompting for a password every connection

The key landed but sshd isn’t using it.

Check the target’s /etc/ssh/sshd_config: PubkeyAuthentication yes, AuthorizedKeysFile .ssh/authorized_keys.

Check perms: ~/.ssh = 700, ~/.ssh/authorized_keys = 600.

On SELinux RHEL: restorecon -R -v ~/.ssh.

ssh-keygen on Windows opens a passphrase prompt despite -N '""'

Some PowerShell quoting variants strip the empty-passphrase argument.

Re-run interactively and just press Enter twice; the rest of the flow is unchanged.

WezTerm SSH tab dies with “client_loop: send disconnect: Broken pipe” and floods the pane with garbage

Two layers of self-healing apply — both are already configured by chezmoi.

Prevention. Chezmoi ships ~/.ssh/config with ServerAliveInterval 30, ServerAliveCountMax 3, and TCPKeepAlive yes. Dead connections are detected within ~90s instead of hours, so the cursor-position-report flood you see when the remote keeps writing into a zombied pipe should be rare. Confirm with ssh -G <hostname> | grep -i serveralive.

Recovery. When a pipe does break, press CTRL+SHIFT+F5 inside the dead tab. WezTerm spawns a new tab against the same SSH domain; Zellij’s attach --create main (from default_prog) reattaches the existing remote session, so you land back exactly where you were. The dead tab is left open for scrollback — close it with CTRL+SHIFT+W once you’ve confirmed the reconnect.

Per-machine overrides. Add host blocks to the un-tracked ~/.ssh/config.local file (same pattern as ~/.zshrc.local) — the tracked config has Include config.local at the top, so per-host overrides win over the global Host * defaults.

WezTerm shows old config after an edit

Normally edits to chezmoi/dot_config/wezterm/wezterm.lua are visible immediately because bootstrap.ps1 sets a User-scope WEZTERM_CONFIG_FILE env var pointing directly at the chezmoi source, and WezTerm’s automatically_reload_config picks up file edits live.

Confirm the env var is set: 

[Environment]::GetEnvironmentVariable('WEZTERM_CONFIG_FILE', 'User')

Should print the full chezmoi-source path (something like C:\Users\you\.local\share\chezmoi\chezmoi\dot_config\wezterm\wezterm.lua). If it’s empty, the env var was never set (bootstrap didn’t run, or it was set in System scope but cleared from User scope). If it points at a stale path, the repo was moved without re-running bootstrap.

Restore: .\bootstrap.ps1 -SkipToolInstall -SkipChezmoi -SkipKeyGen (just re-runs the env-var step) or a full bootstrap.ps1. Restart any running WezTerm instances after — the env var is read at process start.

Migrated from a pre-v2 install? The old layout hardlinked %USERPROFILE%\.config\wezterm\wezterm.lua to the chezmoi source. The new bootstrap deletes that file as a hygiene step — if WEZTERM_CONFIG_FILE is ever unset, WezTerm falls back to its default search path and would find the stale legacy hardlink. If you ever see WezTerm picking up stale content after switching bootstraps, re-run bootstrap.ps1 to clear it.

bootstrap.ps1 aborts with “Admin required to install: …”

The preflight names exactly which tools are missing and require elevation. Two paths:

(a) Close the shell, right-click PowerShell → “Run as administrator”, re-run.

(b) choco install -y the named packages yourself in an admin one-shot, then re-run non-elevated with -SkipToolInstall.

If every tool is already installed and on PATH, the script just notes “All Chocolatey-managed tools already installed” and proceeds without asking for admin.

bootstrap.ps1 says “<Tool> is registered with choco but its binary isn’t on PATH — re-installing with --force”

Recoverable warning — choco’s local database lists the package as installed but the binary’s missing (usually from an interrupted install or someone removing files).

The script automatically passes --force to reinstall it. If choco install --force itself fails: 

choco uninstall <id> -y
choco install -y <id>
bootstrap.ps1 reports “Chocolatey install completed but `choco` is not on PATH”

The choco installer succeeded but the current shell’s PATH wasn’t refreshed in time.

Close the elevated PowerShell, open a new elevated PowerShell, and re-run — the new session inherits the updated machine PATH and picks up choco correctly.

A choco install step says “package not found” or “deprecated”

Choco package IDs occasionally get renamed/retired upstream.

Edit $ChocoTools in bootstrap.ps1 to point at the current ID (search at community.chocolatey.org/packages), or set the tool as Required = $false so the rest of the install proceeds and install it manually.

hosts.ini is out of sync with hosts.conf

Run ./scripts/manage-hosts.sh --sync. Never edit hosts.ini directly — it’s auto-generated.

Bootstrap errored with “Missing required flag: --dev or --prod”

The script no longer has a default scope — exactly one of --dev (sudo, system-wide) or --prod (no sudo, user-wide) must be passed.

The old --full flag was removed; if you still have it in a script or paste buffer, replace it with --dev.

manage-hosts.{sh,ps1} --add errored with “Invalid group”

The only valid groups are dev_machine and prod_machine — anything else means update-hosts.sh can't derive a MODE from it.

Re-run with one of those two values (default is prod_machine).

make errored with “MODE=dev requires HAS_SUDO=true” or “MODE not set”

scope.mk guards both: you can't set MODE=dev without sudo (system-wide install is meaningless without it), and there's no default for MODE — the choice is too load-bearing to silently fall through.

Use one of make dev / make prod (which set MODE for you) or pass it explicitly: make MODE=prod provision.

Cockpit login fails — "Permission denied"

Cockpit auths via PAM against local user accounts — your account must have a password set. SSH-key- only accounts can't log in to the Cockpit web UI. Fix: sudo passwd $USER on the host, then retry. (You'll still want to keep SSH on keys; this password is only for the Cockpit login form.)

Dozzle fails to start — "docker not found" / container won't pull

Dozzle runs as a Docker container, so the host must have Docker (or Podman with a Docker shim). make dozzle-service fails loud with a "docker not installed" message when command -v docker returns nothing. Install Docker via your distro's instructions, then re-run make dozzle-service. If Docker is installed but the docker pull amir20/dozzle:<tag> step fails, check journalctl -u dozzle -n 30 — likely a registry-rate-limit or DNS issue.

Colors look banded or 8-bit on a remote host

WezTerm renders 24-bit color, but the remote app needs to emit truecolor sequences — it won’t unless $COLORTERM=truecolor is set in the shell (via the chezmoi-managed dot_zshrc.tmpl / dot_bashrc.tmpl) or ~/.terminfo/w/wezterm exists. Run chezmoi update && chezmoi apply (czu && cza) on the affected host, then verify with infocmp wezterm (exit 0) and echo "$COLORTERM" (truecolor in a new shell).

Tofu boxes / missing icons after install

Symptom: starship prompt shows boxes instead of icons; eza rows show empty cells where icons should appear; lazygit / k9s / yazi look broken. JetBrainsMono Nerd Font Mono isn’t loaded.

Triage:

  • Linux: fc-list | grep -i 'jetbrainsmono nerd font mono' — expect 6 entries. Empty? Run cd makefile && make nerd-fonts MODE=dev. Re-run starting shells to refresh.
  • Windows: Test-Path "$env:LOCALAPPDATA\Microsoft\Windows\Fonts\JetBrainsMonoNerdFontMono-Regular.ttf" — expect True. False? Re-run bootstrap.ps1 (the Invoke-InstallNerdFonts step is idempotent; takes a stamp-based fast path on a second run).
  • VS Code / Zed still showing tofu: apps cache font lists at launch. Quit and relaunch.
  • WezTerm still showing tofu: Ctrl+Shift+R in WezTerm reloads the config; if that doesn’t help, restart WezTerm. Confirm JETBRAINSMONO_NERD_VERSION in makefile/versions.mk matches the $Version literal in scripts/install-nerd-fonts.ps1 — drift between the two means Linux and Windows hosts can end up on different font versions.
  • WSL host running make nerd-fonts says “skipping on WSL”: intentional. WSL apps render via the Windows host’s WezTerm, which uses Windows-registered fonts. Run bootstrap.ps1 on the Windows side instead.
czt / chezmoi feels slow on WSL (a second or two per command)

Symptom: every chezmoi call stalls ~1.5 s on a WSL host — and czt (the chezit TUI) fires several on launch and refresh, so it feels laggy. The process is mostly idle, not computing (low CPU, high wall-clock).

Cause: WSL2 with appendWindowsPath=true tacks the entire Windows %PATH% (~90 /mnt/c dirs) onto $PATH. chezmoi probes clipboard tools (wl-copy, xclip, xsel) via exec.LookPath at startup; none exist on the Windows side, so each probe stat-walks every /mnt/c dir over the slow 9p/drvfs mount. Hundreds of failed stats ≈ 1.5 s.

Fix (two parts):

  • Set appendWindowsPath=false under [interop] in /etc/wsl.conf, then wsl --shutdown from a Windows terminal (ends all WSL sessions) and reopen.
  • The tracked ~/.zshrc / ~/.bashrc re-add only the two Windows dirs still called from WSL — PowerShell (for ~/.claude/notify.sh toasts) and system32 (clip.exe). No action needed; it’s automatic on shell start.

Verify in a fresh tab: echo $PATH | tr ':' '\n' | grep -c /mnt/ drops from ~90 to ~2; time chezmoi status drops from ~1.6 s to ~0.1 s.

Trade-off: other Windows executables (explorer.exe, VS Code’s code) leave the WSL $PATH. Re-add any you want in ~/.zshrc.local.
