workstationdev env

Dev-environment provisioning for Linux hosts, plus Warp and Windows Terminal on Windows. A single Makefile under makefile/ drives everything — system packages, PATH, tool installs, and the chezmoi handoff for dotfiles. bootstrap.sh is a thin seed that runs make MODE=dev|prod provision. Adding a tool is a two-line edit.

arrush@workstation: ~/.local/share/chezmoi DEV ENV
❯ make MODE=dev provision
✓ system packages & PATH ······ done
✓ 90+ CLI tools (static bins) ··· done
✓ chezmoi handoff → dotfiles ···· done

🐧 First-time setup on a Linux host

Pick prod for no-sudo / user-wide install, dev for sudo / system-wide. Sets a token + identity, then pipes bootstrap.sh. 

export GITHUB_TOKEN='<your-PAT>' \
       GIT_USER_NAME='Arrush Chaturvedi' \
       GIT_USER_EMAIL='contact@arrushc.com' && \
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh \
  | bash -s -- --prod

🪟 First-time setup on Windows

No admin needed. Install Git first, then this installs Warp, Windows Terminal, chezmoi, and Starship under your user profile, applies dotfiles, and deploys the terminal configs. 

$env:GITHUB_TOKEN  = '<your-PAT>'
$env:GIT_USER_NAME  = 'Arrush Chaturvedi'
$env:GIT_USER_EMAIL = 'contact@arrushc.com'
irm -Headers @{Authorization="token $env:GITHUB_TOKEN"} `
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.ps1 | iex

Machine types

Every host belongs to exactly one group in hosts.conf. The group decides the provisioning MODE — no separate scope flag.

Group Sudo Binary dest Helix runtime Used for
dev_machine Yes /usr/local/bin /usr/local/lib/helix/runtime Hosts you own — full system-wide install via OS package manager (dnf on RHEL/Fedora) + /usr/local/bin.
prod_machine No ~/.local/bin ~/.config/helix/runtime Hosts you don’t fully own — user-wide install only, no system packages.

Scope values live in makefile/scope.mk, keyed off MODE=dev|prod. bootstrap.sh derives MODE from its --dev / --prod flag (exactly one is required); scripts/update-hosts.sh derives it from each host's group column in hosts.conf for bulk remote updates.

Setup

1. Configure once

Update before pushing your fork:

  • bootstrap.sh — if you forked the repo, change DOTFILES_REPO at the top of the script to point at your fork's clone URL.
  • hosts.conf — add hosts with ./scripts/manage-hosts.sh --add ... (or edit and --format), or let bootstrap.sh self-register them.

2. On each Linux host

bootstrap.sh needs only curl, git, make, tar, unzip, and iproute (ip). A single preflight check reports all missing prereqs at once. The script then runs make MODE=<dev|prod> provision inside makefile/ — no ansible-core install, no Python ≥ 3.9 gate.

Env vars to set before running

Var Why
GITHUB_TOKEN Authenticates the curl fetch of bootstrap.sh + the script’s internal git clone/pull/push. Persisted into .git/config so chezmoi update, manual git pull, and the auto-push step keep working without re-passing it. Never committed. Generate at github.com/settings/tokens with repo scope (classic) or Contents:Read (fine-grained).
GIT_USER_NAME Author name on the auto-registration commit (falls back to whoami).
GIT_USER_EMAIL Author email on the auto-registration commit (falls back to whoami@hostname).

Keep these in a password manager (1Password, Bitwarden, KeePass) so the token and identity travel together.

dev Claude Code statusline prompt

At the tail of bootstrap.sh --dev, after chezmoi initializes, you’ll be prompted to configure the Claude Code statusline via ccstatusline. Four options:

  1. Use the chezmoi-tracked status line — apply the tracked widget config + Claude Code settings (same look as every other dev_machine).
  2. Define a new status line for this machine — launch the ccstatusline TUI; on save, choose whether to persist across future chezmoi update runs (a yes adds this host to a per-host opt-out block in .chezmoiignore.tmpl).
  3. Set a new global status line — launch the TUI; on save, the result is re-added to the chezmoi source, committed, and pushed so every other dev_machine picks it up on next sync.
  4. Skip — no setup this run.

Re-runnable any time: make -C makefile claude-statusline MODE=dev. Auto-installs Linux-native Node.js (pinned LTS) as a dep via make -C makefile node-runtime MODE=dev, so a fresh dev_machine doesn’t need npx on PATH beforehand. The ccstatusline version is pinned in makefile/versions.mk via CCSTATUSLINE_VERSION; Node version via NODE_VERSION.

dev JetBrainsMono Nerd Font Mono

make provision MODE=dev runs the nerd-fonts target, which installs JetBrainsMono Nerd Font Mono to ~/.local/share/fonts/JetBrainsMonoNerdFontMono/ and refreshes the fontconfig cache. The font is required for Nerd Font glyphs in starship, eza --icons=auto, lazygit, k9s, yazi, broot, helix file-tree, chezit, ccstatusline, and the Claude Code TUI.

WSL hosts skip this step automatically — WSL apps render via Windows Terminal on the Windows host, which reads Windows-registered fonts. Run bootstrap.ps1 on the Windows side to install the font there instead (step 7: Invoke-InstallNerdFonts via scripts/install-nerd-fonts.ps1). Re-runnable any time: make -C makefile nerd-fonts MODE=dev. Font version pinned in makefile/versions.mk via JETBRAINSMONO_NERD_VERSION.

Reinstalling from scratch (--reinstall)
Linux 
./bootstrap.sh --prod --reinstall              # prompts before wiping
./bootstrap.sh --dev  --reinstall --yes        # skip prompt

# From outside the repo (script in memory, won’t self-delete):
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh | bash -s -- --prod --reinstall --yes
Windows 
.\bootstrap.ps1 -Reinstall          # prompts before wiping
.\bootstrap.ps1 -Reinstall -Yes     # skip prompt

# From outside the repo:
irm -Headers @{Authorization="token $env:GITHUB_TOKEN"} `
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.ps1 | iex

Wipes: the cloned repo (~/.local/share/chezmoi / %USERPROFILE%\.local\share\chezmoi) and chezmoi’s config dir (~/.config/chezmoi/).

Does not wipe: installed tools (re-bootstrap detects and skips), deployed dotfiles in $HOME (chezmoi re-applies over them), SSH keys, system packages.

Self-deletion guard. Running .\bootstrap.ps1 -Reinstall from inside the repo would delete the script while executing. Both scripts detect this and refuse with a clear message — use the curl/irm-pipe form or copy the script outside first.
Health check & update scan (--doctor / --check-for-updates)
Linux 
./bootstrap.sh --dev --doctor              # health report (read-only)
./bootstrap.sh --dev --check-for-updates   # update scan (read-only)

# Same engines, invoked directly:
make -C makefile doctor MODE=dev           # or MODE=prod
make -C makefile check-updates MODE=dev
Windows 
.\bootstrap.ps1 -Doctor              # health report (read-only)
.\bootstrap.ps1 -CheckForUpdates     # update scan (read-only)

Both modes are read-only — they exit before the provisioning flow starts and never install, register, or push anything. Use the same --dev/--prod flag the host was bootstrapped with (it picks the install scope being inspected).

--doctor reports what is installed, missing, stale, or broken: prerequisites, the repo’s git state (branch, commits ahead/behind upstream after a fetch, uncommitted changes), chezmoi init state + dotfile drift, the login shell, then every managed tool (binary + version stamp, one ✓/!/✗ line each, with the exact make repair command), the dev-only services (docker/dozzle/cockpit/rsyslog — active or inactive), wsl-config, and the dnf package lists. On Windows it covers the portable and installer-class tools, Warp, Windows Terminal, Nerd Fonts, BurntToast, the Start Menu shortcuts, the workstation SSH-profile fragment, the managed Warp Tab Configs, the dnGrep config seed, the profile shim, and the SSH key.

--check-for-updates checks the workstation repo first (fetch + commits-behind — pull before trusting the pin comparison), then compares every pinned tool version against the newest upstream release tag via git ls-remote (no GitHub API, no rate limits). latest-tracking tools (broot, nb, chezmoi, the pip tools, …) are reported as rolling. The scan is report-only: updating a pin is still the manual edit in makefile/versions.mk (Linux) or $PortableTools in bootstrap.ps1 (Windows), followed by a re-provision.

Enforcement / CI (make lint / make install-hooks)
Linux 
make -C makefile lint MODE=dev     # or MODE=prod — runs check-invariants.sh
make -C makefile install-hooks     # installs .githooks/pre-commit (git pre-commit hook)

make lint runs scripts/check-invariants.sh, which verifies the mechanically-checkable subset of the load-bearing invariants: version-pin dual/triple-edits, line-endings + executable bits on the tracked shell-script set, PowerShell BOM presence, sentinel-block open/close matching, and .chezmoiignore target-path patterns. It also runs shellcheck at warning+ on the repo's maintained shell scripts. Encrypted secrets (age)

chezmoi can keep real secrets encrypted in the repo using age. Without configuration, encryption is dormant — nothing changes.

One-time setup (per identity):

age-keygen -o ~/.config/chezmoi/key.txt   # prints your public key (recipient)

Set the printed public key as WORKSTATION_AGE_RECIPIENT (export it before running bootstrap.sh, or re-run chezmoi init) to activate encryption. bootstrap.sh and bootstrap.ps1 will warn (soft) if the recipient is set but the identity file is missing.

Adding a secret:

chezmoi add --encrypt ~/.netrc   # an encrypted_*.age file appears in the source

The resulting encrypted_*.age file is safe to commit — it decrypts only where the identity (~/.config/chezmoi/key.txt) is present. The identity itself is never committed; the recipient public key is fine to commit.

New host:

Copy key.txt to ~/.config/chezmoi/ before running chezmoi apply. Without it, any encrypted_*.age files will fail to decrypt.

Back up the identity. key.txt is the master secret — losing it loses every encrypted file in the repo. Store it in a password manager alongside your GITHUB_TOKEN.

The Windows host is a client — no provisioning Makefile (that's Linux-only), but chezmoi runs here too to deploy the Windows Terminal settings.json (themed Catppuccin Mocha), the PowerShell profile, and Zed/VSCode settings. bootstrap.ps1 is the parallel of bootstrap.sh.

Bootstrapping WSL distros

WSL distros are first-class managed hosts — same tools, same chezmoi-tracked zshrc + starship prompt + aliases as a real Linux box. They’re accessed through Windows Terminal’s AlmaLinux-9 WSL profile (or wsl.exe from any shell), not SSH, so bootstrap.sh auto-detects WSL ($WSL_DISTRO_NAME / /proc/version) and skips the hosts.conf self-registration step. The rest of the flow (tool install, dotfiles apply) runs unchanged.

The tracked settings.json already lists an AlmaLinux-9 profile (WSL’s own Microsoft.WSL profile source supplies it — no manual Settings step needed); the default profile stays Nushell, so pick AlmaLinux-9 from the new-tab dropdown. The distro’s login shell is /usr/bin/zsh; use Linux-home paths for active projects where practical. Open a new tab (or wsl.exe in any shell) and run: 

# Inside the WSL distro:
sudo dnf install -y curl git python3 python3-pip iproute    # RHEL / AlmaLinux / Fedora
# or: sudo apt install -y curl git python3 python3-pip iproute2   # Debian / Ubuntu
export GITHUB_TOKEN='<your-PAT>'
export GIT_USER_NAME='Arrush Chaturvedi'
export GIT_USER_EMAIL='contact@arrushc.com'
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh | bash -s -- --dev

Use --dev for WSL distros where you have sudo (the common case — you own the WSL host). Tools land in /usr/local/bin, starship + aliases + fzf + zoxide + zellij all become available on next shell.

Why WSL tabs land in ~: the AlmaLinux-9 profile comes from WSL’s own Terminal fragment (source: Microsoft.WSL), which launches wsl.exe -d AlmaLinux-9 --cd ~, so a fresh WSL tab starts in the WSL user’s home instead of the inherited Windows cwd (typically /mnt/c/Users/<windows-user>). Long-lived work still belongs in a zellij session — a closed tab doesn’t take the shell with it.

Truecolor signaling. Every chezmoi-managed shell exports COLORTERM=truecolor on startup (see dot_zshrc.tmpl / dot_bashrc.tmpl), and Windows Terminal runs TERM=xterm-256color — full 24-bit RGB. Verify with the smooth-gradient one-liner in the Troubleshooting section (renders without banding).

WSL config is tracked & deployed. Two files configure WSL, and the repo owns both. /etc/wsl.conf (per-distro: systemd, automount, interop, default user) is deployed on WSL hosts by make wsl-config — part of make dev / provision, gated to WSL hosts with sudo, from the tracked configs/wsl/wsl.conf. The global %USERPROFILE%\.wslconfig (WSL2 VM memory / CPU / networking, all distros) is deployed by chezmoi on the Windows host from chezmoi/dot_wslconfig. Both need wsl --shutdown from a Windows terminal to take effect; wsl-config prints the reminder, and a chezmoi run_onchange script prints it on Windows when .wslconfig changes. The tracked .wslconfig already opts into dynamic memory (autoMemoryReclaim=gradual returns cached RAM to Windows) and pre-opts into sparse VHDs (sparseVhd=true — currently disabled upstream; see Troubleshooting “WSL disk keeps growing” for manual disk reclaim).

Host management

hosts.conf is the single source of truth. Two outputs are regenerated from it, one per managed terminal, both on every Windows bootstrap.ps1 run:

  • the Warp Tab Configs (%APPDATA%\warp\Warp\data\tab_configs\workstation-ssh-<host>.toml, one per row) — Invoke-WarpTabConfigs;
  • the workstation SSH-profile fragment for Windows Terminal (%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\workstation\hosts.json, one SSH: <host> profile per row) — Invoke-WindowsTerminalFragments.

Both run the same ssh -t <user>@<ip> zellij attach --create main, so a host opened in either terminal attaches the same remote session — that’s zellij working as designed, not a conflict. Each generator owns only its own prefix, so launch entries you create yourself survive. On Linux nothing is generated — the provisioning scripts read hosts.conf directly.

scripts/update-hosts.sh reads hosts.conf directly when doing bulk remote updates — the group column drives the per-host MODE.

Group must be dev_machine or prod_machine. Both manage-hosts scripts validate the input and reject anything else — an unknown group means update-hosts.sh can't derive MODE from it. Interactive prompt defaults to prod_machine.

Don’t hand-pad hosts.conf. The save routine recalculates column widths from data; manual padding gets normalised away on next save. Auto-sorted by group, then by name, on every save — manual reordering won’t survive.

Zellij

Zellij is the persistence layer: it runs on the remote host, so a dropped SSH tab never takes your work with it. Every generated Warp Tab Config and Windows Terminal profile lands you in zellij attach --create main.

A new session opens as a single full-width pane with the tab and status bars — zellij’s built-in default layout. The two repo layouts are opt-in:

Command What you get
zs Attach to (or create) the main session
zs <session> Same, for a named session
zs <session> dev or zellij -l dev Editor pane (60%) left; terminal + run stacked right
zs <session> ops or zellij -l ops btop on top; a lazyjournal pane and a shell below — both tools ship to prod hosts too

The layout argument only applies when the session is being created. Naming an existing session always attaches to it, so you can never clobber running work by passing the wrong layout.

Keys worth knowing (on top of zellij’s defaults):

Bind Action
CTRL+S Session mode — session manager, detach
ALT+S Scroll mode, then / to search the scrollback
ALT+1…9 Jump straight to that tab
ALT+N New pane (zellij default)
ALT+H/J/K/L Move focus between panes (zellij default)
ALT+[ / ] Cycle swap layouts as you add panes (zellij default)
ALT+E Floating file browser (strider, built in)
CTRL+G Lock / unlock — passes every key through to the running program (zellij default)
CTRL+T then S Broadcast input to every pane in the tab (zellij default)

Why ALT+S exists: CTRL+S is remapped to Session mode, which shadows zellij’s own CTRL+S → Scroll. That left scrollback search with no way in from Normal mode; ALT+S restores it and collides with nothing in either Windows terminal.

Editing in a pane? CTRL+G locks zellij. Helix and zellij both want CTRL+O, CTRL+S, CTRL+B/F and CTRL+N/P. Locked mode hands every keystroke to the program in the pane; CTRL+G again returns. The community plugin that automates this (zellij-autolock) is not installed — it is broken on zellij 0.44 and unmaintained; see the note in docs/claude/file-care.md.

Tabs name themselves after the directory. Both rc files rename the active tab to the current folder’s basename on every cd (~ for home), so a row of tabs reads as a row of projects. A tab holds several panes with independent directories, so whichever pane you last cd’d in wins, and a manual rename (CTRL+T then R) is replaced on your next cd. Opt out with WORKSTATION_ZELLIJ_TAB_NAMES=0 in ~/.zshrc.local.

Floating panes: zr <cmd> runs a command in one (zr lazygit, zr btop; bare zr gives a floating shell). It overlays the layout instead of resizing it — ALT+F toggles floating panes back into view, and CTRL+P then E embeds one into the layout to keep it.

Sessions survive a reboot. Zellij serializes each session — tabs, panes, working directories, and (newly) up to 10 000 lines of pane scrollback — under ~/.cache/zellij/ on the host it runs on, so zellij attach main after a restart brings the session back with its output intact. The tradeoff is deliberate and called out in the tracked config.kdl: terminal output can contain secrets, and that cache is protected only by being user-owned and mode 700. Drop serialize_pane_viewport if that is not a trade you want on a given host.

Config changes need a fresh session. Zellij reads config.kdl when a session is created, so chezmoi apply alone changes nothing about a running main — zellij kill-session main, then reattach.

Services

The web-admin trio below (Docker engine, Cockpit, Dozzle) is dev_machine-only and skipped on WSL; pueue runs on every Linux host, both groups.

  • Docker engine — installed automatically by make provision (the docker-engine target): Docker CE from Docker’s official dnf repo, service enabled, and your user added to the docker group (log out/in once for sudo-less docker / lazydocker). If Docker is already present from a manual install, the target leaves it alone. Versions come from dnf — there is no pin in versions.mk.
  • Cockpit — open https://<host>:9090 in a browser; log in with your Linux user account (PAM). Self-signed cert on first hit — accept the warning. Covers services, journal, storage, network, packages, podman.
  • Dozzle — runs as a Docker container managed by systemd; bound to localhost. SSH-tunnel to view: ssh -L 8080:localhost:8080 <host>, then http://localhost:8080 on your workstation. Real-time Docker container logs. Bump the pinned image tag by editing DOZZLE_VERSION in makefile/versions.mk; the next make dev re-pulls and restarts the unit.
  • Shell shortcuts — on any dev_machine, the chezmoi-tracked shells alias dozzle-status, dozzle-logs (follows journalctl), dozzle-restart, and cockpit-status for fast health checks. Defined in dot_zshrc.tmpl / dot_bashrc.tmpl; harmless no-ops on prod_machine hosts where the services aren't installed.
  • WSL note — the engine install and both services are skipped automatically on WSL dev_machines (like nerd-fonts). The web-admin stack targets a standalone Linux dev box, and on WSL the engine belongs to Docker Desktop on the Windows host, so make provision prints a “skipping on WSL” line for docker-engine / dozzle-service / cockpit-service instead of failing.
  • pueue — unlike the services above, this one runs on every Linux host (both groups, WSL included): the daemon (pueued) runs as a per-user systemd unit, auto-enabled by chezmoi apply. Inspect with systemctl --user status pueued. Note that the daemon and all queued jobs are torn down when your last login session ends; if jobs must survive logout, enable user lingering with loginctl enable-linger.

The five panels

Dashboard

Four live cards — Provision (fresh/stale/missing tool counts), Dotfiles (pending file count), Fleet (host counts by total/dev/prod), and Health (check glyphs: ✓ pass / ✗ fail / — never-ran; services count or gating reason; interop state on WSL) — refreshed on launch and on every g. Tab to a focused card and press Enter to jump straight into that panel.

Provision

Every tool from make inventory (name / kind / pinned version) in a filterable table, colored by stamp state (✓ fresh / ⟳ stale / ✗ missing, read from the ~/.local/share/workstation-install stamp dir) — type into the filter box to narrow by name. r runs the selected tool, c clean-reinstalls it (-j1 clean-<tool> <tool>, forced serial), u opens the updates table (below), R runs a full make provision, x cancels the running task. Output streams into the log pane below the table.

Multi-select. space marks or unmarks the cursor row (a • in the table's mark column) and Esc clears every mark; a N marked indicator appears next to the filter box once at least one row is marked. Marks are name-keyed, not row-keyed, so they survive typing into the filter. With one or more tools marked, r runs all of them in a single make invocation (table order, not mark order) instead of just the cursor row — the sudo overlay still gates the whole run if any marked tool is non-user-kind. Marks clear automatically after a successful (non-cancelled, rc=0) marked run, but persist on failure or cancellation so you can retry without re-selecting.

Sudo overlay. On a dev Linux host, a privileged action (any scope/bespoke tool, or full provision) first checks the cached sudo -n -v timestamp — if it's still valid the command runs immediately with no prompt. Otherwise a password modal collects it, validates via sudo -S -v (a wrong password re-prompts inline), and a 60-second keepalive re-touches the timestamp while the task runs. User-kind tools and everything on prod never trigger it — prod's own $(SUDO) is empty. The whole panel is unavailable on Windows (see the platform matrix), so the overlay never applies there.

Updates table. u opens a parsed, sortable table of a make check-updates run — one row per tool with a status glyph (↑ update available / ✓ ok / ! ahead of its pin / · rolling (latest-tracking) / ? unknown), the pinned and latest versions, and the raw detail line. It's cache-first: whatever's already cached at ~/.cache/workstation-tui/updates.json renders immediately (instant even offline), then a fresh check kicks off in the background via make check-updates CHECK_UPDATES_PORCELAIN=1 (the porcelain flag switches check-updates.sh to plain status|name|detail lines, no banner or ANSI) and overwrites the cache on success — if a task is already running it shows a “task running — showing cached results” banner instead of queuing a second check. The same cache backs a fourth line on the Dashboard's Provision card (↑ N updates · checked <age>, or “updates: never checked” before the first run). s toggles the sort key (status-first, or name), R forces a re-check, Esc / q closes. The table is read-only by design — like the CLI scan above, updating a pin is still the manual edit in makefile/versions.mk.

Dotfiles

Pending chezmoi status changes in a table on the left, a live diff of whichever row is highlighted on the right, plus a source-repo git line (branch · clean/dirty · ahead/behind). Enter on a pending row applies just that file (confirm, then chezmoi apply --force <abs path> for that file alone), a applies every pending change (confirm, then chezmoi apply --force), U pulls and applies from git (confirm, then chezmoi update --force), A re-adds the highlighted file (chezmoi re-add <path> — for sync-from-host files like Windows Terminal's settings.json), d opens the full diff (every pending file, concatenated) in a scrollable overlay. chezmoi's own interactive overwrite prompts never fire under the TUI — every mutation is --force, always after an explicit in-app confirm.

Fleet

The hosts.conf table (name / address / user / group), with a two-stage reachability probe against every host on each refresh: a TCP connect first, and — only if that succeeds — a second, BatchMode ssh (never prompts, short connect timeout) checking for the .local/share/chezmoi checkout directory. A dedicated setup column shows the result: setup (repo checked out), missing (host reachable but no checkout), ssh-failed (ssh itself couldn't complete — auth, host key, or a non-BatchMode-compatible host), or a dim dash when the host is down or not yet probed (stage two never ran). A push column shows the outcome of the most recent push this session — a glyph (✓ done / ✗ failed / – cancelled — outcomes land only after the dashboard settles, so queued/ running never appear here) plus a relative age (42s / 7m / 3h / 2d), or a dim dash for a host never pushed since the TUI started — it resets on restart, nothing is persisted to disk. s SSHes to the selected host (suspends the TUI into a real ssh session); z suspends instead into ssh -t … zellij attach --create main — the same session the Windows Terminal and Warp profiles attach to — while s stays plain ssh, and a missing remote zellij surfaces as a warning toast naming the exit code. a adds and e edits a host through a form modal that shells out to manage-hosts.sh --add / --remove --skip-confirm — edit is a remove-then-add sequence, guarded against renaming into an already-existing host's name, x removes the selected host (confirmed, then that same non-interactive manage-hosts.sh --remove --name <n> --skip-confirm). SSH, push, and key distribution are Linux-only: on Windows they're refused (“pushes/ssh are Linux-side”), but add/edit/remove still work, via manage-hosts.ps1. A hand-edited hosts.conf with a duplicate name keeps the first row and logs a warning for the rest, instead of crashing the panel.

Push dashboard. p opens a push dashboard scoped to just the selected host, P one scoped to every host — both confirm first, then run each host's own scripts/update-hosts.sh --name <host> in parallel, up to 4 at a time. Each row tracks state / elapsed time / last output line live as the runs progress; Enter on a row opens that host's full scrollback, x cancels the whole run (confirmed), and Esc closes the dashboard — guarded (“push still running — cancel and close?”) while any host is still queued or running, immediate once everything has settled. Closing stamps every host's outcome into the Fleet table's push column. A push and a local task (a Provision or Dotfiles run) are mutually exclusive — starting one refuses the other with a “task running” / “push running” toast — and a completed run fires exactly one OS toast, counts only (N ok, N failed (Ns)), never host names.

Quick-stats. Enter on a Fleet row opens a read-only quick-stats overlay for that host: a single BatchMode ssh (15-second timeout) collecting four sections — Vitals (uptime / mem / disk / kernel / os), Workstation (repo / commit / branch / dirty / stamp age / drift), Session (users / names / latency), and Tools (chezmoi / git / make) — plus the round-trip latency measured from the initial TCP probe. A host that's down, or reachable but where ssh itself fails, degrades to a one-line unreachable banner instead of the sections — ssh is never even attempted against a host that's already down. R re-runs both probe stages from scratch; there's no caching, so closing (Esc / q) and reopening does the same.

Guided key distribution. k opens a host picker (a SelectionList) pre-checking whichever hosts most need it — those whose last setup probe came back ssh-failed — with a header line showing whether your local ~/.ssh/id_ed25519.pub is present. a toggles select all / none, Enter confirms (refusing an empty selection), Esc cancels. The TUI then suspends into your terminal and runs manage-hosts.sh --copy-id --name <host> once per selected host, in table order, one at a time — each may need an interactive password, and the script offers to generate an ed25519 key first if you don't have one — printing a banner between hosts so it's clear whose prompt is on screen. On resume, the Fleet panel re-probes (healing ssh-failed glyphs for hosts that now accept the key) and a single toast reports counts (N ok, N failed).

Health

A check registry — doctor, check-updates, invariants (scripts/check-invariants.sh), templates (scripts/check-templates.sh) — each row showing its last cached result, age, and a one-line summary (the last non-empty log line, truncated to 80 chars). Below the table: a services line (docker / dozzle / cockpit / rsyslog via systemctl is-active) and, on WSL hosts, a WSL-interop line (/proc/sys/fs/binfmt_misc/WSLInterop). Enter runs the selected check and records its result to ~/.cache/workstation-tui/health.json — one of three per-user caches the TUI writes under ~/.cache/workstation-tui/, alongside the updates table's cache and the task history log (both documented below). R runs every currently-available check as one streamed sequence, but — because that sequence exposes no per-command return code back to the panel — it does not update any row's cached result; rows keep showing whatever their last individual Enter run recorded, or “never”. Run Enter on a row afterward to refresh it specifically — a deliberate v1 scope limit, not a bug. o opens the full accumulated log in a scrollable overlay. All four checks run unprivileged — Health never triggers the sudo overlay.

Desktop notifications. Every completed task (a single tool run, a marked-tool batch, a full provision, a dotfiles apply…) can fire an OS toast via the same ~/.claude/notify.sh the Claude Code hooks use. A failed task (non-zero exit) always notifies; a successful one only notifies when it ran at least 10 seconds — long enough that you plausibly tabbed away; a cancelled task never notifies (the in-app “cancelled” toast already covers it). The notify call is fire-and-forget and silently does nothing if notify.sh isn't present on the host.

Command palette

Ctrl-P, from any panel, opens Textual's built-in fuzzy-search command palette. Three sources feed it. Every whole-app / whole-panel action — one go to <panel> per panel, refresh, toggle watch, check updates, task history, help, quit, and each panel's own “do it to everything” command (provision all, apply all pending, push all hosts, run all health checks, distribute keys) — is a fixed, static list shown in full before you type anything. One command per live row in whichever panel's own data currently holds it — run <tool> / clean <tool> (Provision), push <host> / ssh <host> / stats <host> (Fleet), apply <path> / diff <path> (Dotfiles), run check <label> (Health) — is built fresh from every tool, host, pending file, and health check on each keystroke, so these appear only once you start typing (dumped in full up front, this list would be the whole app's data on screen at zero keystrokes). And the most recent re-runnable task/sequence entries from task history, shown as re-run: <summary> (<age>, rc <rc>) — push and key-distribution runs have no single command to replay and never appear here.

Every palette command routes through the exact same panel action a key press or table row would — the same confirm modals, sudo gate, and busy-refusal toasts apply, nothing is reimplemented for the palette. Picking a vanished run <tool> / clean <tool>, push <host> / ssh <host>, or apply <path> hit aborts with a “<name> no longer available” toast instead of acting on the wrong row; stats <host> and diff <path> simply no-op if the row is gone, run check <label> always runs (checks are a fixed list, never a vanishing one), and a re-run: <summary> hit carries its own recorded command, so there's no “target that moved” case for it at all. The palette's own system-commands list is curated down to just Quit — Textual's generic Theme/Keys entries don't apply to this app's fixed Catppuccin Mocha theme.

Task history

H, from any panel, opens a read-only browser over every recorded run: Provision/Dotfiles tool tasks (a marked-tool batch runs and records as ONE make invocation, not a sequence), panel-level command sequences (Health's run all health checks, a Fleet host edit's remove-then-add), Fleet pushes, and guided key-distribution runs — up to the 200 most recent, newest first, each row showing a relative age, an outcome glyph (✓ ok / ✗ failed / – cancelled), kind, summary, return code, and duration. Enter opens that entry's full captured log in the same scrollable overlay other log views use; r re-runs the cursor entry — for a re-runnable task/sequence entry (one recorded with a command) this confirms first, then routes through the very same sudo-gate / busy-refusal path a fresh r/R press would (a sequence entry replays just that one recorded command as a single task, not the whole original sequence); push and key-distribution rows (and any task/sequence recorded with no command) have no single command to replay, so r on one skips the confirm and shows a “re-run from the Fleet panel” toast instead. Esc / q closes.

Entries persist to ~/.cache/workstation-tui/history/ (an append-only index.jsonl plus one <id>.log file per entry) and are pruned to the newest 200 after every write — older entries and their log files are deleted, not just hidden. A history write is fire-and-forget and never blocks or fails the run it's recording; on a write failure the app shows one warning toast per session rather than silently dropping the record. Re-running the make check-updates history entry streams its output to the log like any other re-run, but does not refresh the Provision panel's updates table or cache — use u for that.

Adding tools & hosts

Adding a new tool

Two files, one line each. Tool installs live in makefile/ — make provision invokes them as part of the normal bootstrap flow. There are three macros; prefer EGET_TOOL for single-binary GitHub releases (the common case — 64 of the current 87 tools use it).

  1. Pin the version in makefile/versions.mk.
  2. Add one $(eval $(call EGET_TOOL,<name>,$(<NAME>_VERSION),<user/repo>[,<tag>][,<extra args>])) line in makefile/tools.mk. The 4th arg overrides the default v$VERSION tag (use it for tools like delta whose tag is 0.19.2, not v0.19.2). The 5th arg passes flags to eget — commonly --asset musl when upstream publishes both gnu and musl variants. 
# makefile/versions.mk
DIRENV_VERSION := 2.34.0
# makefile/tools.mk
$(eval $(call EGET_TOOL,direnv,$(DIRENV_VERSION),direnv/direnv))

eget figures out the right asset from direnv/direnv + the tag, downloads it, finds the binary inside, and installs to $(DEST). The wrapper at lib/eget.sh bakes in noise filters (.sbom, .sig, .deb, etc.) so eget's auto-detection almost always picks unambiguously.

Fallback to TOOL for the shapes eget can't handle: multi-binary archives with junk files (age has LICENSE, yazi has shell completions), non-GitHub URLs (ncdu at dystroy.org), raw binary URLs (jq, broot, sops), curl-pipe installers (chezmoi, claude), or helix's binary-plus-runtime layout. Use the matching helper: archive.sh, direct.sh, pipe.sh, or helix.sh. Fallback to USER_TOOL for pip user-site tools. Do not add tool-specific logic to bootstrap.sh or invent a parallel install path under scripts/.

Sanity-test before pushing (set GITHUB_TOKEN to avoid eget's unauthenticated rate limit): 

cd makefile
make direnv MODE=prod DEST=/tmp/install-test STAMP=/tmp/install-test-stamps
ls /tmp/install-test/direnv            # binary present?
make direnv MODE=prod DEST=/tmp/install-test STAMP=/tmp/install-test-stamps   # second run: no output (stamp protected)

Bumping a tool version

Edit one line in makefile/versions.mk and commit. The version is baked into the stamp filename at $STAMP/<tool>-<version>.done, so the change invalidates the old stamp; the next make all redownloads the new release automatically. No make clean needed.

Multi-binary tools split into two camps. eget with --all covers archives containing only the binaries we want (ast-grep ships sg+ast-grep, uv ships uv+uvx). archive.sh with a colon-separated binary spec covers archives that also have LICENSE / completion files we don't want to install (age, yazi). See makefile/tools.mk for both patterns.

Troubleshooting

Bootstrap reports “Missing required prerequisites: …”

Install all listed tools at once via your distro’s package manager.

RHEL/Fedora: sudo dnf install curl git python3 python3-pip iproute

Debian/Ubuntu: sudo apt install curl git python3 python3-pip iproute2

Bootstrap deliberately collects every gap up front so you only have to install once.

Bootstrap finishes with “Push failed (auth, conflict, or no upstream)”

Provisioning succeeded — only the host-list push didn’t.

Recover with cd ~/.local/share/chezmoi && git push.

Common causes: no SSH key for the git remote, a divergent upstream (git pull --rebase first), or you’ve forked and never set the remote.

Private repo: clone fails with “Authentication failed” or 404

Set GITHUB_TOKEN to a PAT with repo (classic) or Contents:Read (fine-grained) scope and re-run.

The token is written into .git/config as http.https://github.com/.extraheader so subsequent ops (push, chezmoi update, manual git pull) all work — re-passing the env var on later runs just refreshes the stored value.

To clear: git -C ~/.local/share/chezmoi config --unset http.https://github.com/.extraheader.

manage-hosts.sh --copy-id keeps prompting for a password every connection

The key landed but sshd isn’t using it.

Check the target’s /etc/ssh/sshd_config: PubkeyAuthentication yes, AuthorizedKeysFile .ssh/authorized_keys.

Check perms: ~/.ssh = 700, ~/.ssh/authorized_keys = 600.

On SELinux RHEL: restorecon -R -v ~/.ssh.

ssh-keygen on Windows opens a passphrase prompt despite -N '""'

Some PowerShell quoting variants strip the empty-passphrase argument.

Re-run interactively and just press Enter twice; the rest of the flow is unchanged.

Copying inside a remote Zellij session doesn’t reach the Windows clipboard

Zellij runs on the remote host, so it cannot touch your local clipboard directly. The only mechanism that crosses an SSH connection is the OSC 52 escape sequence, which zellij uses by default — but only while copy_command is unset in ~/.config/zellij/config.kdl. Setting it (to xclip, wl-copy, pbcopy, …) overrides OSC 52 with a program that runs on the remote box, where there is no display and usually no such binary — so every yank silently goes nowhere. The tracked config deliberately leaves it unset and says so in a comment; don’t re-add it.

Both managed terminals accept OSC 52 writes — Warp via osc52_clipboard_access = "write_only" in its tracked settings.toml, Windows Terminal natively. If copy still doesn’t land:

  • Re-apply and reconnect — zellij reads its config when the session is created, so an already-running main keeps the old behavior until zellij kill-session main (or a fresh host).
  • Check the config actually parsed: zellij setup --check must say Well defined. KDL comments are // — a single # line invalidates the whole file and zellij silently falls back to built-in defaults.
Zellij’s tabs and pane borders are green, not mauve

Green is zellij’s built-in catppuccin-mocha showing through. The repo ships its own catppuccin-mocha-mauve theme (in ~/.config/zellij/themes/) that re-accents the chrome to the same mauve #cba6f7 that Warp (its accent and cursor) and fzf use. Windows Terminal is deliberately not part of that set — its Catppuccin Mocha scheme carries no mauve at all (ANSI purple maps to pink #f5c2e7), so there is nothing to change there. Seeing green means the zellij theme isn’t in effect. Two causes, in order of likelihood:

  • The session predates the change. Zellij reads its config when a session is created, so chezmoi apply does nothing to a running main. Run zellij kill-session main and reattach.
  • The theme file didn’t deploy. Check ls ~/.config/zellij/themes/ on the host zellij runs on — that’s the remote box, not your laptop. If it’s missing, chezmoi update && chezmoi apply there.

Note that zellij setup --check is no help here: it reports Well defined even when theme names a theme that doesn’t exist, and zellij then falls back to the built-in one silently. That gap is why scripts/check-invariants.sh matches the theme "<name>" line against the block names in themes/*.kdl — run make lint MODE=prod if you suspect the config itself.

Green in one place is correct and deliberate: a pane’s success exit code. Success stays green and failure stays red so status still reads at a glance — only the chrome went mauve.

SSH tab dies with “client_loop: send disconnect: Broken pipe” and floods the pane with garbage

Two layers of self-healing apply — both are already configured by chezmoi.

Prevention. Chezmoi ships ~/.ssh/config with ServerAliveInterval 30, ServerAliveCountMax 3, and TCPKeepAlive yes. Dead connections are detected within ~90s instead of hours, so the cursor-position-report flood you see when the remote keeps writing into a zombied pipe should be rare. Confirm with ssh -G <hostname> | grep -i serveralive.

Recovery. When a pipe does break, open the host’s SSH: <host> profile again from the SSH hosts folder in Windows Terminal’s new-tab dropdown. Zellij’s attach --create main reattaches the existing remote session, so you land back exactly where you were; close the dead tab once you’ve confirmed the reconnect.

Per-machine overrides. Add host blocks to the un-tracked ~/.ssh/config.local file (same pattern as ~/.zshrc.local) — the tracked config has Include config.local at the top, so per-host overrides win over the global Host * defaults.

Warp: missing Tab Configs, wrong theme, or it opened PowerShell instead of AlmaLinux-9

Warp hot-reloads settings.toml, so a theme or font change lands as soon as chezmoi applies it (cza on WSL, or chezmoi apply in a Windows shell). Tab Configs are the exception — Warp reads %APPDATA%\warp\Warp\data\tab_configs\ at launch, so a regenerated set needs a full Warp restart before new SSH: <host> entries appear in the “+” menu.

If something is still wrong:

  • No SSH: <host> entries — re-run .\bootstrap.ps1; Invoke-WarpTabConfigs rebuilds them from hosts.conf every run. .\bootstrap.ps1 -Doctor counts them. If it says Warp is not installed while Warp clearly is, the Uninstall-registry DisplayName changed — the generator keys off it.
  • Theme reverted to a stock one — the theme is referenced by the relative filename catppuccin-mocha.yaml, and it must exist under %APPDATA%\warp\Warp\data\themes\. A chezmoi apply restores it.
  • Opened PowerShell, not AlmaLinux-9 — Warp warns and falls back to the system default when it rejects new_session_shell_override. Use the WSL: AlmaLinux-9 Tab Config to get back in, then re-check the key against Warp’s current settings schema.
  • Your edits keep coming back — chezmoi owns settings.toml. Change it in the Settings panel if you like, then re-sync the repo with chezmoi re-add. Don’t enable Warp’s settings sync (is_settings_sync_enabled); cloud sync and chezmoi will fight over the file.
  • The same host opened in both terminals mirrors itself — expected. Both launchers run zellij attach --create main, so they attach the same remote session and zellij sizes it to the smallest client. Detach one, or start a differently-named session by hand.
  • Nushell looks broken in Warp — it is, knowingly. See Warp keybinds: Warp doesn’t support Nushell, so use Windows Terminal for it.
Windows Terminal shows old settings / missing SSH hosts

The tracked settings.json deploys via chezmoi straight to the Store package’s LocalState path — so an edit in the repo needs a chezmoi apply (cza on WSL, or chezmoi apply in a Windows shell) before Windows Terminal can see it. settings.json itself hot-reloads: the change lands in open windows within a second of the apply.

Fragments are the exception — Windows Terminal reads Fragments\ only at launch, so a regenerated Fragments\workstation\hosts.json needs a full restart (close every window) before new SSH: <host> profiles appear.

If a host is still missing after the restart:

  • Stale or absent fragment — re-run .\bootstrap.ps1; Invoke-WindowsTerminalFragments rebuilds it from hosts.conf on every run (verify with .\bootstrap.ps1 -Doctor, which counts the profiles in it).
  • Brand-new fragment source — recent Windows Terminal builds list fragment providers on Settings → Extensions and can require a one-time enable of the workstation entry before its profiles show up.
bootstrap.ps1 aborts with “Git is required but isn’t on PATH”

Git is a prerequisite — the script does not install it. Install Git for Windows (an admin-free per-user install is offered by the installer), reopen PowerShell, and re-run: 

winget install Git.Git
# or download: https://git-scm.com/download/win

The GitHub CLI is not such a prerequisite — the script installs it (pinned portable); authenticate once after the bootstrap: 

gh auth login
bootstrap.ps1 aborts with “<Tool> sha256 mismatch — refusing to install”

The portable tools (Starship/Helix/Nushell/jq/OpenCode/omp/uv/DevToys CLI/dnGrep/LogExpert) are pinned to a specific version and sha256 in $PortableTools inside bootstrap.ps1. A mismatch means the pinned hash is stale (upstream re-published the asset) or the download was corrupted/tampered. The script refuses to install an unverified binary. Installer-class tools ($InstallerTools, e.g. Obsidian, Zed, DevToys, DBeaver, WinSCP, Beyond Compare) are not pinned — they verify against the GitHub API’s sha256 digest for the latest asset (WinSCP and Beyond Compare, which publish no GitHub releases, verify against the official winget manifest’s sha256 instead), and the same hard-fail applies on a mismatch.

Fix: re-download the pinned asset, recompute its hash, and update the Sha256 field for that tool (then re-run). On a trusted network you can verify the upstream asset: 

(Get-FileHash -Algorithm SHA256 .\<asset>.zip).Hash.ToLower()
PowerShell aliases / adminpw / cz* don’t load (the profile seems ignored)

Almost always Documents folder redirection (OneDrive / corporate folder redirection). PowerShell loads $PROFILE from the redirected location (e.g. %USERPROFILE%\OneDrive - <Org>\Documents\), but chezmoi deploys the managed profile to the literal %USERPROFILE%\Documents\PowerShell\ — so your shell never loads it.

bootstrap.ps1 handles this automatically (step 5b drops a one-line loader at the real $PROFILE that dot-sources the managed canonical). If you hit it before re-running bootstrap, confirm the mismatch and create the loader yourself: 

# differ? -> Documents is redirected
$PROFILE.CurrentUserCurrentHost
"$env:USERPROFILE\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1"

# point the real $PROFILE at the managed canonical
$dir = Split-Path $PROFILE.CurrentUserCurrentHost
New-Item -ItemType Directory -Force -Path $dir | Out-Null
'. "$env:USERPROFILE\Documents\PowerShell\Microsoft.PowerShell_profile.ps1"' |
  Set-Content $PROFILE.CurrentUserCurrentHost
hosts.ini is out of sync with hosts.conf

Run ./scripts/manage-hosts.sh --sync. Never edit hosts.ini directly — it’s auto-generated.

Bootstrap errored with “Missing required flag: --dev or --prod”

The script no longer has a default scope — exactly one of --dev (sudo, system-wide) or --prod (no sudo, user-wide) must be passed.

The old --full flag was removed; if you still have it in a script or paste buffer, replace it with --dev.

manage-hosts.{sh,ps1} --add errored with “Invalid group”

The only valid groups are dev_machine and prod_machine — anything else means update-hosts.sh can't derive a MODE from it.

Tofu boxes / missing icons after install

Symptom: starship prompt shows boxes instead of icons; eza rows show empty cells where icons should appear; lazygit / k9s / yazi look broken; on Windows, Windows Terminal pops Unable to find the following fonts: JetBrainsMono NFM. JetBrainsMono Nerd Font Mono isn’t loaded.

Triage:

  • Linux: fc-list | grep -i 'jetbrainsmono nerd font mono' — expect 6 entries. Empty? Run cd makefile && make nerd-fonts MODE=dev. Re-run starting shells to refresh.
  • Windows: Test-Path "$env:LOCALAPPDATA\Microsoft\Windows\Fonts\JetBrainsMonoNerdFontMono-Regular.ttf" — expect True. False? Re-run bootstrap.ps1 (the Invoke-InstallNerdFonts step is idempotent; takes a stamp-based fast path on a second run). The installer activates the font in the current session (AddFontResourceW + WM_FONTCHANGE), so no logout is needed. If the .ttf exists but apps still can’t find the font (Windows Terminal pops Unable to find the following fonts: JetBrainsMono NFM) — typically after a reboot — the cause is that Windows does not reliably load HKCU per-user fonts into the system font collection at logon (the per-user fonts dir “has no special powers” and is excluded from the KnownFolder API).   • VS Code / Zed still showing tofu: apps cache font lists at launch — quit and relaunch. czt / chezmoi feels slow on WSL (a second or two per command)

Symptom: every chezmoi call stalls ~1.5 s on a WSL host — and czt (the chezit TUI) fires several on launch and refresh, so it feels laggy. The process is mostly idle, not computing (low CPU, high wall-clock).

Cause: WSL2 with appendWindowsPath=true tacks the entire Windows %PATH% (~90 /mnt/c dirs) onto $PATH. chezmoi probes clipboard tools (wl-copy, xclip, xsel) via exec.LookPath at startup; none exist on the Windows side, so each probe stat-walks every /mnt/c dir over the slow 9p/drvfs mount. Hundreds of failed stats ≈ 1.5 s.

Fix (two parts):

  • Set appendWindowsPath=false under [interop] in /etc/wsl.conf — now deployed for you by make wsl-config (tracked at configs/wsl/wsl.conf) — then wsl --shutdown from a Windows terminal (ends all WSL sessions) and reopen.
  • The tracked ~/.zshrc / ~/.bashrc re-add only the two Windows dirs still called from WSL — PowerShell (for ~/.claude/notify.sh toasts) and system32 (clip.exe). No action needed; it’s automatic on shell start.

Verify in a fresh tab: echo $PATH | tr ':' '\n' | grep -c /mnt/ drops from ~90 to ~2; time chezmoi status drops from ~1.6 s to ~0.1 s.

Trade-off: other Windows executables (explorer.exe, VS Code’s code) leave the WSL $PATH. Re-add any you want in ~/.zshrc.local.

WSL disk (ext4.vhdx) keeps growing — freed space never returns to Windows

Symptom: deleting files inside the distro never shrinks the virtual disk on the Windows side. That part is expected: WSL2 VHDs grow on demand but never shrink on their own.

The auto-shrink feature (sparse VHD) is disabled upstream on WSL ≥ 2.5 after data-corruption reports (microsoft/WSL #13075) — so the tracked sparseVhd=true in chezmoi/dot_wslconfig is currently inert (it self-activates for newly created VHDs if Microsoft re-enables the feature), and wsl --manage <Distro> --set-sparse true refuses unless forced.

Find the VHD first (regular PowerShell):

Get-ChildItem HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss |
  ForEach-Object { Get-ItemProperty $_.PSPath } |
  Select-Object DistributionName, BasePath

Safe one-time reclaim (admin PowerShell; manual maintenance — the repo deliberately does not automate this): 

wsl --shutdown
Optimize-VHD -Path "<BasePath>\ext4.vhdx" -Mode Full

No Hyper-V module (Optimize-VHD missing)? Use the always-available diskpart route (still admin): 

wsl --shutdown
diskpart
# inside diskpart:
select vdisk file="<BasePath>\ext4.vhdx"
attach vdisk readonly
compact vdisk
detach vdisk
exit

Unsafe opt-in — only if you accept the corruption risk Microsoft disabled this over (read-only filesystems, lost files). Back up first, then force sparse mode so the disk auto-returns freed space: 

wsl --export <Distro> D:\backup\<Distro>.tar
wsl --manage <Distro> --set-sparse true --allow-unsafe

RAM is the separate, already-solved half: autoMemoryReclaim=gradual in the tracked .wslconfig returns cached VM memory to Windows automatically — no action needed.

LSP servers — a language server is missing or make lsp-servers failed for one server

make lsp-servers MODE=dev (also runs as part of make dev) installs each server best-effort — one failure warns and continues. Servers and their mechanisms:

  • rust-analyzer / marksman / taplo — eget binaries, dev + prod; re-run make provision MODE=dev.
  • gopls — go install via go-runtime; needs make go-runtime MODE=dev first.
  • lua-language-server — tree install (not a single binary); verify lua-language-server --version.
  • basedpyright — uv tool install to user site; check uv tool list.
  • typescript-language-server / bash-language-server / yaml-language-server / vscode-json-languageserver — npm, needs node-runtime; check npm list -g --prefix /usr/local.
  • clangd — verified-only (comes from clang-tools-extra via dnf, see the C/C++ entry below); make lsp-servers only warns if absent.

Re-run a single mechanism: make lsp-servers MODE=dev. To force a reinstall of the Go toolchain: make clean-go-runtime go-runtime MODE=dev.

C / C++ toolchain — a tool is missing, or ninja / vcpkg behaves oddly

The compilers, debuggers and analysis tools (gcc-c++, clang, clangd/clang-tidy/clang-format, lldb, valgrind, cppcheck, cmake, meson, ninja-build, heaptrack, the sanitizer runtimes) install via dnf on dev_machine only, best-effort. Several come from EPEL/CRB, not BaseOS — make provision auto-enables both (EPEL + CodeReady Builder) on RHEL-family hosts, because EPEL on EL9 needs CRB or meson/ninja-build (which live in CRB) and heaptrack/bear (which pull CRB deps) fail to resolve. If a package still shows skipped (e.g. CRB couldn’t be auto-enabled), enable it manually and re-run: 

sudo dnf install epel-release
sudo dnf config-manager --set-enabled crb   # EL9 Alma/Rocky/Stream (powertools on EL8)
make -C makefile MODE=dev packages

ninja: command not found — on RHEL the binary is ninja-build, not ninja. If a project hard-codes ninja, symlink it once: ln -s "$(command -v ninja-build)" ~/.local/bin/ninja.

Two GDB front-ends, no conflict. Plain gdb auto-loads GEF (via the tracked ~/.gdbinit); pwndbg is a separate standalone command. So gdb ./a.out → GEF, pwndbg ./a.out → pwndbg, and gdb -nx ./a.out → vanilla gdb (no GEF). nnd ./a.out is the modern from-scratch TUI debugger.

vcpkg: it lives at $VCPKG_ROOT (/usr/local/share/vcpkg, exported by the shell rc on dev hosts). The tree is root-owned, so classic-mode vcpkg install <pkg> (which writes into the tree) needs sudo — prefer manifest mode (a vcpkg.json per project, installs into the project’s vcpkg_installed/), or sudo chown -R "$USER" "$VCPKG_ROOT" to use classic mode unprivileged. Prefer the compiler sanitizers (-fsanitize=address,undefined, ~2–4× overhead) over Valgrind (~20–50×) for everyday checks; keep Valgrind for unmodified binaries and uninitialized-read detection ASan misses.

wpy not found, or import textual fails in it

The blessed Python env is built by provisioning on both dev_machine and prod_machine. Rebuild it from scratch:

Linux: make python-env-rebuild MODE=dev # or MODE=prod

Windows: delete %LOCALAPPDATA%\workstation\stamps\python-env.*.stamp and re-run .\bootstrap.ps1.

The same rebuild upgrades the latest-tracking libraries. If wpy resolves but an import fails, an ad-hoc uv pip install likely broke a dependency — the rebuild resets the env to the canonical nine libraries.

NFS tools (showmount, nfsstat, autofs) are missing on a dev host

The NFS client group (nfs-utils, nfs4-acl-tools, autofs) installs via dnf on dev_machine only — and is skipped entirely on WSL hosts by design (same policy as the Docker engine and Cockpit: provision prints skipping NFS client group on WSL). On a native dev host, re-run make -C makefile MODE=dev packages.

autofs is installed but not enabled — an automounter with no maps does nothing. Write your maps first, then sudo systemctl enable --now autofs.

bootstrap.ps1 popped a UAC prompt (or SSHFS-Win reports “skipping”)

That’s the SSHFS-Win step — the one deliberate exception to the otherwise admin-free bootstrap. SSHFS-Win depends on WinFsp, a kernel-mode filesystem driver; kernel drivers install machine-wide, so elevation is unavoidable. The step is best-effort: declining the prompt, being offline, or having neither winget nor network just skips it — nothing else in the bootstrap is affected, and an already-installed machine never sees the prompt (Uninstall-registry detection).

Install it later with winget install SSHFS-Win.SSHFS-Win (pulls WinFsp automatically) or re-run .\bootstrap.ps1 and accept the prompt; suppress the attempt entirely with -SkipElevated. Once installed, mount with net use X: \\sshfs\user@host or browse \\sshfs\user@host directly in Explorer.

Running workstation prints “the TUI needs a terminal” instead of launching

By design — the TUI only launches when both stdin and stdout are a real terminal (sys.stdin.isatty() and sys.stdout.isatty()). A redirected/piped invocation (workstation < /dev/null, an ssh host workstation one-liner, a cron job) prints workstation: the TUI needs a terminal — see --help for headless commands. to stderr and exits 1. Use the headless subcommands instead — workstation status, workstation doctor, workstation dotfiles status, etc. (see workstation TUI → Launch).

If the workstation command is missing entirely, or behaves like an old build after a repo update, rebuild the Python scripting env it lives in: make python-env-rebuild MODE=dev (or MODE=prod) — this rewrites the venv, the launchers, and reinstalls the TUI package.

workstation TUI's Provision panel fails with “sudo timestamp caching disabled” instead of prompting

Your password was accepted, but the sudoers config has timestamp_timeout=0 — the validated timestamp never caches, so the privileged command still can't run unattended inside the TUI. v1 doesn't implement an app-suspend fallback for this case; instead the panel names the exact command to run yourself in a real terminal (e.g. make -C makefile provision MODE=dev). Run it there — it will prompt for sudo normally.

workstation TUI's Provision / Fleet / Health table looks stale after a change made elsewhere

Press g — it re-reads all five panels' data in one pass (tool inventory + stamp scan, hosts.conf, chezmoi status, health cache/services/interop). The Provision panel in particular reads tool freshness from the stamp directory (~/.local/share/workstation-install, the same path for both MODEs) — an install done by hand, by update-hosts.sh, or under a different MODE on the same host won't show as fresh until the next g.

workstation tab-completion isn't offering subcommands

The zsh completion stub (~/.config/zsh/completions/_workstation) deploys like any other dotfile — via chezmoi, not automatically the moment the source file lands in this repo. czs shows it A (pending add) until you run cza (or any chezmoi apply / dotfiles apply). Once applied, new shells pick it up on their next compinit rebuild — the repo's compinit -C trades a per-launch freshness check for speed (see the comment above it in dot_zshrc.tmpl), so a shell whose cached ~/.zcompdump predates the deploy won't see it either, until that cache is rebuilt (same caveat as the existing _bootstrap.sh / _manage-hosts.sh / _update-hosts.sh completions): rm -f ~/.zcompdump && exec zsh.
