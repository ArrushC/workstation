First-time setup on a Linux host

Pick prod for no-sudo / user-wide install, dev for sudo / system-wide. Sets a token + identity, then pipes bootstrap.sh. 

export GITHUB_TOKEN='<your-PAT>' \
       GIT_USER_NAME='Arrush Chaturvedi' \
       GIT_USER_EMAIL='contact@arrushc.com' && \
curl -fsSL -H "Authorization: token $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.sh \
  | bash -s -- --prod

First-time setup on Windows

No admin needed. Install Git and ensure curl.exe is on PATH first, then this installs Warp, Windows Terminal, and Starship under your user profile, applies dotfiles, and deploys the terminal configs. 

$env:GITHUB_TOKEN  = '<your-PAT>'
$env:GIT_USER_NAME  = 'Arrush Chaturvedi'
$env:GIT_USER_EMAIL = 'contact@arrushc.com'
$bootstrapFile = [System.IO.Path]::GetTempFileName()
try {
    $curl = Get-Command curl.exe -CommandType Application -ErrorAction Stop | Select-Object -First 1
    & $curl.Source --disable --fail --silent --show-error --location --retry 3 --retry-delay 2 --connect-timeout 30 `
      --header "Authorization: token $env:GITHUB_TOKEN" --output $bootstrapFile `
      https://raw.githubusercontent.com/ArrushC/workstation/main/bootstrap.ps1
    if ($LASTEXITCODE -ne 0) { throw "Bootstrap download failed (curl exit $LASTEXITCODE)" }
    $bootstrap = [System.IO.File]::ReadAllText($bootstrapFile, [System.Text.Encoding]::UTF8)
    & ([scriptblock]::Create($bootstrap))
} finally {
    Remove-Item -LiteralPath $bootstrapFile -Force
}

Machine types

Every host belongs to exactly one group in hosts.conf. The group decides which bootstrap.sh flag (--dev/--prod) a host runs — no separate scope flag.

Group Sudo System packages / /etc Used for
dev_machine Yes dnf (RHEL/Fedora) + managed /etc files Hosts you own — the one scope where mise bootstrap also installs system packages and writes system-owned /etc files.
prod_machine No none Hosts you don’t fully own — user-wide only, no system packages, no /etc files.

Every mise tool installs identically on both scopes — user-level under ~/.local/share/mise/installs, reached through ~/.local/share/mise/shims or mise activate. That includes Helix: its runtime ships inside its own mise install dir, and there is no HELIX_RUNTIME env var and no /usr/local anywhere in the toolchain any more (the sudo column above is about system packages and /etc files only, never tools).

Scope maps to the MISE_ENV token set computed by scripts/lib/mise-env.sh (linux for prod; linux,dev,host,wsl or linux,dev,host,native for dev, depending on whether the host is WSL). bootstrap.sh takes --dev / --prod directly (exactly one is required); scripts/update-hosts.sh derives the flag from each host's group column in hosts.conf for bulk remote updates.

Setup

1. Configure once

Update before pushing your fork:

  • bootstrap.sh — if you forked the repo, change DOTFILES_REPO at the top of the script to point at your fork's clone URL.
  • hosts.conf — add hosts with ./scripts/manage-hosts.sh --add ... (or edit and --format), or let bootstrap.sh self-register them.

2. On each Linux host

bootstrap.sh needs only curl, git, tar, and iproute (ip) — unzip is no longer required (mise extracts its own archives). A single preflight check reports all missing prereqs at once. The script then installs the pinned mise binary, computes MISE_ENV, runs scripts/lib/mise-install.sh (tools), then mise bootstrap --yes (packages, /etc files, services, compose, repos, dotfiles) — ONE command per host, no ansible-core install, no Python ≥ 3.9 gate.

Env vars to set before running

Var Why
GITHUB_TOKEN Authenticates the curl fetch of bootstrap.sh + the script’s internal git clone/pull/push. Persisted into .git/config so scripts/update-hosts.sh, manual git pull, and the auto-push step keep working without re-passing it. Never committed. Generate at github.com/settings/tokens with repo scope (classic) or Contents:Read (fine-grained).
GIT_USER_NAME Author name on the auto-registration commit (falls back to whoami).
GIT_USER_EMAIL Author email on the auto-registration commit (falls back to whoami@hostname).

Keep these in a password manager (1Password, Bitwarden, KeePass) so the token and identity travel together.

(Warp’s own cloud settings-sync is deliberately off, so it can’t fight the dotfiles apply for authorship.)

Windows Terminal config model: the dotfiles (mode = copy) deploy the tracked settings.json straight to the Store package’s live LocalState path (%LOCALAPPDATA%\Packages\Microsoft.WindowsTerminal_8wekyb3d8bbwe\LocalState\). The hosts.conf-driven launch entries are generated separately, as a profile fragment under %LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\workstation\ (Invoke-WindowsTerminalFragments in bootstrap.ps1, every run — only *.json inside that one app dir is rewritten, so other apps’ fragments and your own profiles are never touched). After bootstrap, restart your shell so the dotfiles-applied $PROFILE picks up — starship prompt, wsa/wse/wsd/wss/wsr/wsu aliases, git aliases, etc. Editing dotfiles: same workflow as Linux. wse <path> opens the source-state copy; wsa applies; wsd shows the diff; the checkout at %USERPROFILE%\.config\mise IS the source dir, so cd there directly for git ops.

Bootstrapping WSL distros

WSL distros are first-class managed hosts — same tools, same tracked zshrc + starship prompt + aliases as a real Linux box. They’re accessed through Windows Terminal’s AlmaLinux-9 WSL profile (or wsl.exe from any shell), not SSH, so bootstrap.sh auto-detects WSL ($WSL_DISTRO_NAME / /proc/version) and skips the hosts.conf self-registration step. The rest of the flow (tool install, dotfiles apply) runs unchanged.

The tracked settings.json already lists an AlmaLinux-9 profile (WSL’s own Microsoft.WSL profile source supplies it — no manual Settings step needed); the default profile stays Nushell, so pick AlmaLinux-9 from the new-tab dropdown. The distro’s login shell is /usr/bin/zsh; use Linux-home paths for active projects where practical. Open a new tab (or wsl.exe in any shell) and run:

export GIT_USER_NAME='Arrush Chaturvedi'
export GIT_USER_EMAIL='contact@arrushc.com'

Why WSL tabs land in ~: the AlmaLinux-9 profile comes from WSL’s own Terminal fragment (source: Microsoft.WSL), which launches wsl.exe -d AlmaLinux-9 --cd ~, so a fresh WSL tab starts in the WSL user’s home instead of the inherited Windows cwd (typically /mnt/c/Users/<windows-user>). Long-lived work still belongs in a zellij session — a closed tab doesn’t take the shell with it.

Truecolor signaling. Every tracked shell exports COLORTERM=truecolor on startup (see dotfiles/zshrc.tera / dotfiles/bashrc.tera), and Windows Terminal runs TERM=xterm-256color — full 24-bit RGB. Verify with the smooth-gradient one-liner in the Troubleshooting section (renders without banding).

WSL config is tracked & deployed. Two files configure WSL, and the repo owns both. /etc/wsl.conf (per-distro: systemd, automount, interop, default user) is deployed on WSL hosts by mise bootstrap (config.wsl.toml's [bootstrap.files] entry, loaded only when MISE_ENV carries the wsl token), from the tracked configs/wsl/wsl.conf. The global %USERPROFILE%\.wslconfig (WSL2 VM memory / CPU / networking, all distros) is deployed by the mise dotfiles (mode = copy) on the Windows host from dotfiles/wslconfig. Both need wsl --shutdown from a Windows terminal to take effect. mise has no run_onchange equivalent (ruling 6), so on the Windows side a bootstrap.ps1 step sha256-compares the source against a stored marker and prints the reminder when .wslconfig changes; on Linux, remember it yourself after a /etc/wsl.conf change (the Make-era printed reminder is gone with makefile/ — mise bootstrap reports the file as updated, but prints no follow-up hint). The tracked .wslconfig already opts into dynamic memory (autoMemoryReclaim=gradual returns cached RAM to Windows) and pre-opts into sparse VHDs (sparseVhd=true — currently disabled upstream; see Troubleshooting “WSL disk keeps growing” for manual disk reclaim).

Host management

hosts.conf is the single source of truth. Two outputs are regenerated from it, one per managed terminal, both on every Windows bootstrap.ps1 run:

  • the Warp Tab Configs (%APPDATA%\warp\Warp\data\tab_configs\workstation-ssh-<host>.toml, one per row) — Invoke-WarpTabConfigs;
  • the workstation SSH-profile fragment for Windows Terminal (%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\workstation\hosts.json, one SSH: <host> profile per row) — Invoke-WindowsTerminalFragments.

Both run the same ssh -t <user>@<ip> zellij attach --create main, so a host opened in either terminal attaches the same remote session — that’s zellij working as designed, not a conflict. Each generator owns only its own prefix, so launch entries you create yourself survive. On Linux nothing is generated — the provisioning scripts read hosts.conf directly.

scripts/update-hosts.sh reads hosts.conf directly when doing bulk remote updates — the group column drives the per-host --dev/--prod flag passed to bootstrap.sh. It’s a prod-host tool: prod never needs sudo, so the fleet run is fully non-interactive. Dev hosts are bootstrapped by hand, interactively, one at a time — see “Remote fleet updates” in Daily workflows.

Group must be dev_machine or prod_machine. Both manage-hosts scripts validate the input and reject anything else — an unknown group means update-hosts.sh can't derive MODE from it. Interactive prompt defaults to prod_machine.

Don’t hand-pad hosts.conf. The save routine recalculates column widths from data; manual padding gets normalised away on next save. Auto-sorted by group, then by name, on every save — manual reordering won’t survive.

Alias What it does
wse <path> mise dot edit — edit a dotfile’s source (e.g. wse ~/.zshrc, wse $PROFILE)
wsd mise dot diff — preview pending changes to $HOME
wsa Apply — writes tracked state to $HOME. Checks for an un-recorded edit first (anything mise dot status reports as differs): if it finds one it prints the diff and asks before overwriting, instead of silently blowing it away. (The raw form, mise bootstrap --only dotfiles --yes, skips that check.)

Every ws* command always acts on this host’s own checkout (~/.config/mise on Linux, %USERPROFILE%\.config\mise on Windows) — regardless of the current directory. mise resolves its config root by walking up from the current directory, so an unpinned command run from anywhere with its own .config/mise reachable in that walk (a Windows drive mount under WSL is the case that bit us) would silently manage a different checkout instead of erroring. Every ws* alias/function pins mise -C to the host’s own home directory to rule that out, and wsa additionally refuses to apply if the config root mise actually resolved doesn’t match.

Every target is an independent file in $HOME now — there is no symlinked case any more, so editing the deployed file directly (by hand, or a Claude Code agent editing ~/.claude/CLAUDE.md) does not update dotfiles/, and the next wsa silently overwrites that edit unless it’s been recorded back first. Zellij

Zellij is the persistence layer: it runs on the remote host, so a dropped SSH tab never takes your work with it. Every generated Warp Tab Config and Windows Terminal profile lands you in zellij attach --create main.

A new session opens as a single full-width pane between the tab bar and the status bar — zellij’s built-in default layout. The two repo layouts are opt-in (and keep zellij’s swap layouts, so ALT+[ / ] still cycle as you add panes):

Command What you get
zs Attach to (or create) the main session
zs <session> Same, for a named session
zs <session> dev or zellij -l dev Editor pane (60%) left; terminal + run stacked right

The layout argument only applies when the session is being created. Naming an existing session always attaches to it, so you can never clobber running work by passing the wrong layout.

The top bar is zjstatus. Rounded Catppuccin pills: a mode badge on the left (mauve NORMAL means zellij is listening; red LOCKED means every key goes to the pane), then the tabs, numbered to match ALT+1…9, and the session name on the right. It is a plugin (~/.local/share/zellij/plugins/zjstatus.wasm, installed by provisioning like any other tool) that replaces only the top bar — the bottom bar is still zellij’s own, because it prints the key hints from this config. The first session on a host asks once for permission: the bar shows the request; click it (or CTRL+P then ↑ to focus it) and press Y. The answer is cached in ~/.cache/zellij/permissions.kdl.

Why ALT+S exists: CTRL+S is remapped to Session mode, which shadows zellij’s own CTRL+S → Scroll. That left scrollback search with no way in from Normal mode; ALT+S restores it and collides with nothing in either Windows terminal.

Editing in a pane? CTRL+G locks zellij. Helix and zellij both want CTRL+O, CTRL+S, CTRL+B/F and CTRL+N/P. Locked mode hands every keystroke to the program in the pane; CTRL+G again returns. Tabs name themselves after the directory. Both rc files rename the active tab to the current folder’s basename on every cd (~ for home), so a row of tabs reads as a row of projects. A tab holds several panes with independent directories, so whichever pane you last cd’d in wins, and a manual rename (CTRL+T then R) is replaced on your next cd. Opt out with WORKSTATION_ZELLIJ_TAB_NAMES=0 in ~/.zshrc.local.

Floating panes: zr <cmd> runs a command in one (zr lazygit, zr btop; bare zr gives a floating shell). It overlays the layout instead of resizing it — ALT+F toggles floating panes back into view, and CTRL+P then E embeds one into the layout to keep it.

Sessions survive a reboot. Zellij serializes each session — tabs, panes, working directories, and (newly) up to 10 000 lines of pane scrollback — under ~/.cache/zellij/ on the host it runs on, so zellij attach main after a restart brings the session back with its output intact. The tradeoff is deliberate and called out in the tracked config.kdl: terminal output can contain secrets, and that cache is protected only by being user-owned and mode 700. Drop serialize_pane_viewport if that is not a trade you want on a given host.

Config changes need a fresh session. Zellij reads config.kdl when a session is created, so wsa alone changes nothing about a running main — zellij kill-session main, then reattach.

Adding tools & hosts

Adding a new tool

One line, in the right file — every tool is a mise pin now. config.linux.toml is the Linux toolbelt (both scopes); config.dev.toml is dev_machine-only tools on both OSes (add os = ["linux"] to a table entry when it’s dev-only and Linux-only). Prefer mise’s aqua registry short name (~65 tools already use it, e.g. fzf = "0.74.3") — reach for a github:/http: backend only when the registry picks the wrong asset (a glibc floor EL9 can’t meet, the wrong build) or there’s no GitHub release at all. 

# config.linux.toml — [tools] (both scopes; aqua registry short name)
direnv = "2.34.0"

A tool the registry gets wrong needs an explicit asset instead (see the gping / yazi / television / atuin / qsv entries in config.linux.toml for worked examples of the EL9-glibc-floor case): 

# config.linux.toml — pin an explicit asset when the registry default won't run on EL9
"github:direnv/direnv" = { version = "2.34.0", asset_pattern = "direnv.linux-amd64" }
  1. mise install <name> — installs just that tool.
  2. tasks/verify-tools — the capability gate every install goes through (ELF arch, dynamic-loader resolution, glibc floor); a failure here is the signal to pick an explicit github: asset instead of the registry default.
  3. Refresh both lockfiles for the platforms the fleet runs: MISE_ENV=linux,dev,host,native mise lock --global --platform linux-x64 and MISE_ENV=windows,dev mise lock --global --platform windows-x64 (skip the second for a tool marked os = ["linux"]).
  4. Commit the edited config*.toml, the mise.lock / mise.linux.lock / mise.dev.lock files, and any new sidecar under locks/** (dependency-locked pypi:/npm: tools get one).

Do not add tool-specific logic to bootstrap.sh or invent a parallel install path under scripts/. The machine-level Claude memory’s tool inventory regenerates from config*.toml automatically (scripts/gen-tool-memory.sh, run by the sync-tool-memory.sh hook on every edit — or run it by hand).

Sanity-test before pushing: 

mise install direnv
mise where direnv            # installed?
tasks/verify-tools            # capability gate — arch/loader/glibc

Bumping a tool version

Edit the version in config.toml / config.linux.toml / config.dev.toml (or run mise config set tools.<name> <version> — note that it drops a same-line comment on the bumped string entry and a leading comment above a table’s first key, so re-add those by hand afterward if they mattered), then refresh both lockfiles the same way as above and commit. No stamp file to invalidate — mise is idempotent on its own. mise outdated --bump does this across the whole toolbelt at once; it’s what the weekly version-bumps.yml job runs.

Multi-binary archives install every binary they contain by default (ast-grep ships sg+ast-grep). When an archive also carries files you don’t want (LICENSE, shell completions — age, yazi) or several binaries and you only want one (qsv ships six), pin it with bin or bin_path on the github: entry — see qsv’s bin = "qsv" or pwndbg’s bin_path = "pwndbg/bin" in config.linux.toml / config.dev.toml for worked examples.

Adding a dotfile

One [dotfiles] entry, keyed by the target path, plus the source file under dotfiles/ (real name, no dot_ prefixing). Add it to the config*.toml file whose MISE_ENV token should gate it — cross-platform in config.toml, Linux in config.linux.toml, Windows in config.windows.toml, dev-only (both OSes) in config.dev.toml, Linux-dev-only in config.host.toml: 

# config.linux.toml — [dotfiles]
"~/.config/example/config.toml" = { source = "dotfiles/config/example/config.toml", mode = "copy" }

Only two modes exist in this repo, on every platform (ruling 7 — no [dotfiles] entry symlinks, anywhere, by explicit user decision: copy semantics survive applications on either OS that don’t respect symlinks): copy for a plain file (add exclude = [".vendor", ".gitkeep"] too if the source is a whole directory, e.g. a vendored plugin tree — copy on a directory leaves unmanaged siblings alone, same as it did on Linux before) — a copy-mode edit, whether made through an app (Zed/Warp/VS Code/Windows Terminal settings) or by hand under $HOME, needs recording back to source or the next apply silently overwrites it: wsr (mise dot add --changed) for a FILE entry, or mise dot add <target> naming the directory’s own exact path for a DIRECTORY entry (--changed does not see inside one); template for a Tera .tera source that needs a rendered var (host name, OS branch, git identity) — guard every vars.* reference with is defined or default(), since one undefined variable or failing exec() aborts the ENTIRE mise dot apply/mise bootstrap run and writes nothing at all (ruling 3) — render it individually first (mise dot apply --force -- "~/.config/...") and add it to scripts/check-templates.sh. Disabling an entry inherited from a less-specific file needs enabled = false and a repeated mode in the override (ruling 2 — enabled = false alone is silently ignored).

  1. mise dot apply --yes -- "<target>" — apply just that one entry.
  2. mise dot status / mise dot diff — confirm it lands the way you expect.
  3. bash scripts/check-invariants.sh — runs check_dotfiles_config (source exists, mode is valid, every Windows entry is copy/template, every .tera file is referenced by exactly one entry).
  4. Commit the config edit and the new source file.

First apply on a host still running the old chezmoi bootstrap: every target already exists as a real file, and copy/template refuse to overwrite one that already differs (even --dry-run exits 1) — mise dot apply --force or mise bootstrap --force-dotfiles resolves it (ruling 1). bootstrap.sh/bootstrap.ps1 pass --force-dotfiles automatically, but only while ~/.local/state/workstation/dotfiles-migrated is absent, so a later real conflict still fails loudly.

LET’S GET YOU UNSTUCK

Troubleshooting

Bootstrap reports “Missing required prerequisites: …”

Install all listed tools at once via your distro’s package manager.

RHEL/Fedora: sudo dnf install curl git tar iproute

Debian/Ubuntu: sudo apt install curl git tar iproute2

Bootstrap deliberately collects every gap up front so you only have to install once.

Bootstrap finishes with “Push failed (auth, conflict, or no upstream)”

Provisioning succeeded — only the host-list push didn’t.

Recover with cd ~/.config/mise && git push.

Common causes: no SSH key for the git remote, a divergent upstream (git pull --rebase first), or you’ve forked and never set the remote.

The checkout moved (~/.local/share/chezmoi is gone)

This repo is mise’s global config dir now (config.toml + mise.lock live at its root), so bootstrap.sh / bootstrap.ps1 relocate it from the old ~/.local/share/chezmoi / %USERPROFILE%\.local\share\chezmoi to ~/.config/mise / %USERPROFILE%\.config\mise on first run.

The move is automatic and one-time. A pre-existing ~/.config/mise from before the relocation (the chezmoi-era conf.d layout) is moved aside first as *.pre-relocation.<timestamp> — delete it once the new layout is confirmed working. Any leftover pre-migration chezmoi config (~/.config/chezmoi/) is swept up separately, by --reinstall or bootstrap.ps1’s own one-time sweep — nothing reads or writes it any more, since chezmoi itself is gone. scripts/update-hosts.sh detects either path on a host that hasn’t re-bootstrapped since the move.

Windows: “Cannot move item … is in use” during the one-time relocation

The relocation above (moving ~\.local\share\chezmoi to ~\.config\mise) fails with Move-Item : Cannot move item because the item at … is in use. Windows refuses to move a directory that any process holds as its current directory — almost always a shell (or editor) sitting inside the old checkout, including the very shell running .\bootstrap.ps1 in-process. bootstrap.ps1 releases its own hold on the directory before moving it, but can’t release one held by a different process (another terminal tab, an editor window, or the shell that launched it).

cd ~ in every shell open inside ~\.local\share\chezmoi, close any editor with that folder open, then re-run: & "$HOME\.local\share\chezmoi\bootstrap.ps1".

Private repo: clone fails with “Authentication failed” or 404

Set GITHUB_TOKEN to a PAT with repo (classic) or Contents:Read (fine-grained) scope and re-run.

The token is written into .git/config as http.https://github.com/.extraheader so subsequent ops (push, scripts/update-hosts.sh, manual git pull) all work — re-passing the env var on later runs just refreshes the stored value.

To clear: git -C ~/.config/mise config --unset http.https://github.com/.extraheader.

manage-hosts.sh --copy-id keeps prompting for a password every connection

The key landed but sshd isn’t using it.

Check the target’s /etc/ssh/sshd_config: PubkeyAuthentication yes, AuthorizedKeysFile .ssh/authorized_keys.

Check perms: ~/.ssh = 700, ~/.ssh/authorized_keys = 600.

On SELinux RHEL: restorecon -R -v ~/.ssh.

ssh-keygen on Windows opens a passphrase prompt despite -N '""'

Some PowerShell quoting variants strip the empty-passphrase argument.

Re-run interactively and just press Enter twice; the rest of the flow is unchanged.

Copying inside a remote Zellij session doesn’t reach the Windows clipboard

Zellij runs on the remote host, so it cannot touch your local clipboard directly. The only mechanism that crosses an SSH connection is the OSC 52 escape sequence, which zellij uses by default — but only while copy_command is unset in ~/.config/zellij/config.kdl. Setting it (to xclip, wl-copy, pbcopy, …) overrides OSC 52 with a program that runs on the remote box, where there is no display and usually no such binary — so every yank silently goes nowhere. The tracked config deliberately leaves it unset and says so in a comment; don’t re-add it.

Both managed terminals accept OSC 52 writes — Warp via osc52_clipboard_access = "write_only" in its tracked settings.toml, Windows Terminal natively. If copy still doesn’t land:

  • Re-apply and reconnect — zellij reads its config when the session is created, so an already-running main keeps the old behavior until zellij kill-session main (or a fresh host).
  • Check the config actually parsed: zellij setup --check must say Well defined. KDL comments are // — a single # line invalidates the whole file and zellij silently falls back to built-in defaults.
Zellij’s tabs and pane borders are green, not mauve

Green is zellij’s built-in catppuccin-mocha showing through. The repo ships its own catppuccin-mocha-mauve theme (in ~/.config/zellij/themes/) that re-accents the chrome to the same mauve #cba6f7 that Warp (its accent and cursor) and fzf use. Windows Terminal is deliberately not part of that set — its Catppuccin Mocha scheme carries no mauve at all (ANSI purple maps to pink #f5c2e7), so there is nothing to change there. Seeing green means the zellij theme isn’t in effect. Two causes, in order of likelihood:

  • The session predates the change. Zellij reads its config when a session is created, so wsa does nothing to a running main. Run zellij kill-session main and reattach.
  • The theme file didn’t deploy. Check ls ~/.config/zellij/themes/ on the host zellij runs on — that’s the remote box, not your laptop. If it’s missing, wsu (mise run update) there.

Note that zellij setup --check is no help here: it reports Well defined even when theme names a theme that doesn’t exist, and zellij then falls back to the built-in one silently. That gap is why scripts/check-invariants.sh matches the theme "<name>" line against the block names in themes/*.kdl — run mise run lint if you suspect the config itself.

Green in one place is correct and deliberate: a pane’s success exit code. Success stays green and failure stays red so status still reads at a glance — only the chrome went mauve.

SSH tab dies with “client_loop: send disconnect: Broken pipe” and floods the pane with garbage

Two layers of self-healing apply — both are already configured by the tracked dotfiles.

Prevention. The tracked ~/.ssh/config template ships ServerAliveInterval 30, ServerAliveCountMax 3, and TCPKeepAlive yes. Dead connections are detected within ~90s instead of hours, so the cursor-position-report flood you see when the remote keeps writing into a zombied pipe should be rare. Confirm with ssh -G <hostname> | grep -i serveralive.

Recovery. When a pipe does break, open the host’s SSH: <host> profile again from the SSH hosts folder in Windows Terminal’s new-tab dropdown. Zellij’s attach --create main reattaches the existing remote session, so you land back exactly where you were; close the dead tab once you’ve confirmed the reconnect.

Per-machine overrides. Add host blocks to the un-tracked ~/.ssh/config.local file (same pattern as ~/.zshrc.local) — the tracked config has Include config.local at the top, so per-host overrides win over the global Host * defaults.

Warp: missing Tab Configs, wrong theme, or it opened PowerShell instead of AlmaLinux-9

Warp hot-reloads settings.toml, so a theme or font change lands as soon as wsa applies it (same alias on WSL or in a Windows shell). Tab Configs are the exception — Warp reads %APPDATA%\warp\Warp\data\tab_configs\ at launch, so a regenerated set needs a full Warp restart before new SSH: <host> entries appear in the “+” menu.

If something is still wrong:

  • No SSH: <host> entries — re-run .\bootstrap.ps1; Invoke-WarpTabConfigs rebuilds them from hosts.conf every run. .\bootstrap.ps1 -Doctor counts them. If it says Warp is not installed while Warp clearly is, the Uninstall-registry DisplayName changed — the generator keys off it.
  • Theme reverted to a stock one — the theme is referenced by the relative filename catppuccin-mocha.yaml, and it must exist under %APPDATA%\warp\Warp\data\themes\. A wsa restores it.
  • Opened PowerShell, not AlmaLinux-9 — Warp warns and falls back to the system default when it rejects new_session_shell_override. Use the WSL: AlmaLinux-9 Tab Config to get back in, then re-check the key against Warp’s current settings schema.
  • Your edits keep coming back — the tracked dotfiles own settings.toml (mode = copy). Change it in the Settings panel if you like, then re-sync the repo with wsr (mise dot add --changed). Don’t enable Warp’s settings sync (is_settings_sync_enabled); cloud sync and the next wsa will fight over the file.
  • The same host opened in both terminals mirrors itself — expected. Both launchers run zellij attach --create main, so they attach the same remote session and zellij sizes it to the smallest client. Detach one, or start a differently-named session by hand.
  • Nushell looks broken in Warp — it is, knowingly. See Warp keybinds: Warp doesn’t support Nushell, so use Windows Terminal for it.
Windows Terminal shows old settings / missing SSH hosts

The tracked settings.json deploys (mode = copy) straight to the Store package’s LocalState path — so an edit in the repo needs a wsa (same alias on WSL or in a Windows shell) before Windows Terminal can see it. settings.json itself hot-reloads: the change lands in open windows within a second of the apply.

Fragments are the exception — Windows Terminal reads Fragments\ only at launch, so a regenerated Fragments\workstation\hosts.json needs a full restart (close every window) before new SSH: <host> profiles appear.

If a host is still missing after the restart:

  • Stale or absent fragment — re-run .\bootstrap.ps1; Invoke-WindowsTerminalFragments rebuilds it from hosts.conf on every run (verify with .\bootstrap.ps1 -Doctor, which counts the profiles in it).
  • Brand-new fragment source — recent Windows Terminal builds list fragment providers on Settings → Extensions and can require a one-time enable of the workstation entry before its profiles show up.
  • Your edits keep coming back — the Settings UI re-serializes settings.json on save; change it there if you like, then wsr (mise dot add --changed) to record the edit back to dotfiles/windows/... before the next wsa overwrites it with the stale source.
bootstrap.ps1 aborts with “Git is required but isn’t on PATH”

bootstrap.ps1 aborts with “<Tool> sha256 mismatch — refusing to install”

The portable tools (Starship/Helix/Nushell/jq/OpenCode/omp/mise/DevToys CLI/dnGrep/LogExpert) are pinned to a specific version and sha256 in $PortableTools inside bootstrap.ps1. A mismatch means the pinned hash is stale (upstream re-published the asset) or the download was corrupted/tampered. The script refuses to install an unverified binary. Installer-class tools ($InstallerTools, e.g. Obsidian, Zed, DevToys, DBeaver, WinSCP, Beyond Compare) are not pinned — they verify against the GitHub API’s sha256 digest for the latest asset (WinSCP and Beyond Compare, which publish no GitHub releases, verify against the official winget manifest’s sha256 instead), and the same hard-fail applies on a mismatch.

(Get-FileHash -Algorithm SHA256 .\<asset>.zip).Hash.ToLower()

mise bootstrap failed with a dnf error naming one package

The dnf batch is all-or-nothing — mise runs ONE sudo dnf install -y <every missing name> per [bootstrap.packages] table, so a single unresolvable name fails the whole batch, even though every other name would have installed fine.

Confirm the exact name for this host’s repos with dnf repoquery <name>. Every name already in config.host.toml / config.native.toml was EL9-verified as of 2026-09-17; a newer dnf metadata refresh, a disabled repo, or a typo in a freshly-added line are the usual causes. Fix the entry (or the repo state) and re-run mise bootstrap --only packages --yes.

A bootstrap phase fails and blocks the rest

mise bootstrap runs its phases in a fixed order (packages, files/services/compose, repos, dotfiles, tools, then the bootstrap task) and stops at the first failure — a wedged phase blocks every phase after it, not just its own step.

Re-running ./bootstrap.sh --dev|--prod is idempotent and resumes: every already-settled resource is skipped, so you aren’t redoing work, only retrying what failed. If a single phase is wedged on something outside your control (a flaky dnf mirror, a proxied host, an unreachable upstream), skip just that phase to make progress elsewhere: 

mise bootstrap --skip packages --yes       # e.g. a flaky dnf mirror
mise bootstrap --skip files,services --yes # comma-separated, or repeat --skip

then re-run the full ./bootstrap.sh --dev|--prod once the underlying cause is fixed — a skipped phase leaves real drift behind (see mise run health). Use mise bootstrap plan first to see what a phase would actually do before running it for real.

mise dot apply/mise bootstrap fails with “Variable … is not defined” (or a template renders garbage) — and NOTHING got applied

One broken template aborts the entire dotfiles apply and writes nothing at all — not just the one entry with the bad template. That is by design (ruling 3 in the migration plan): a single undefined Tera variable or a failing exec() in ANY mode = "template" entry fails the whole run, so a partial apply that leaves half the dotfiles tree stale never happens.

mise puts the useful part first: the target, the source file, then the actual error (error: Variable <name> is not defined and a caret line), followed by generic mise ERROR Version/Run boilerplate you can ignore. To find the culprit yourself instead of reading a bulk-run failure, apply every template-mode entry individually: 

mise dot apply --force --yes -- "<target>"   # one entry at a time, names the failure precisely
bash scripts/check-templates.sh                    # does exactly this for every .tera file, all four MISE_ENV sets

Fix the template (guard the variable with is defined or default(value=...), or make the exec() command fail-safe), then re-run the bulk apply (wsa). scripts/check-templates.sh runs in CI precisely so this is caught before it ever reaches a host.

mise dot apply/mise bootstrap refuses with “refusing to overwrite existing files (use --force)”

copy/template targets refuse to replace a pre-existing file that already differs — even --dry-run exits 1 without --force. This is expected and correct on the first apply on any host that previously ran the old chezmoi-based bootstrap: every target chezmoi deployed is a real, differing file today, so mise won’t silently reclaim it.

bootstrap.sh/bootstrap.ps1 already handle this — they pass --force-dotfiles to mise bootstrap automatically, but only while the migration marker (~/.local/state/workstation/dotfiles-migrated) is absent. Once it’s written (after the first successful apply), a later “refusing to overwrite” means a real conflict — a file you or another tool created at that exact path — and gets surfaced loudly instead of silently clobbered.

To resolve one entry by hand: inspect what is actually there, then either mise dot apply --force --yes -- "<target>" to let the dotfiles win, or move the conflicting file aside first if you want to keep it. Never reach for --force-dotfiles / --force as a reflex outside the migration case above — it silently discards whatever was at that path.

scripts/update-hosts.sh fails on a host with “fatal: Not possible to fast-forward, aborting” (or the pull just silently does nothing)

This checkout itself has an uncommitted change — note this is not caused by a dotfile drifting in $HOME any more (every [dotfiles] target is an independent copy/template deploy now, outside the checkout; see Repo layout) — it means something inside the repo itself changed: a hand-edited version pin in config*.toml, an interactive wse edit to a dotfiles/ source file, a wsr/mise dot add write recording a live edit back, or mise itself rewriting a lock file. scripts/update-hosts.sh runs git pull --ff-only on every host, which refuses to run — and, depending on the git version, can fail outright rather than no-op — against local changes.

Check for it directly on the host: mise run health has a repo checkout row that reports an uncommitted-change count. Fix by committing (then push, so the change isn’t only local) or stashing: 

cd ~/.config/mise
git status --porcelain          # see what's dirty
git add -A && git commit -m '...' && git push   # keep the edit
# or:
git stash                       # discard it from the working tree for now

then re-run update-hosts.sh (or just git pull --ff-only directly) on that host.

A copy-mode file (Warp / Windows Terminal / Zed / VS Code settings) reverts to the old content after wsa

Expected, and the whole reason these targets use mode = "copy": the app rewrites the file in place (Warp’s Settings panel, Windows Terminal serializing on every change, Zed/VS Code’s settings UI), so the copy in $HOME and the source under dotfiles/ drift apart the moment you change something through the app’s own UI. The next wsa then overwrites your UI edit with the (now stale) tracked source — wsa DOES warn first if it notices (see the next entry for the general case and what that warning looks like).

Record the live file back to source instead of hand-editing both copies: 

wsr                    # mise dot add --changed — records every changed tracked file
mise dot add --changed -- "<target>"   # or just the one you edited

then commit the updated source file. Do this before the next wsa/wsu, or the edit is lost.

I edited a file in $HOME directly (e.g. ~/.claude/CLAUDE.md) and wsa reverted it

Every [dotfiles] target is now an independent copy under $HOME, not a symlink into this checkout — so an edit made straight to the deployed file (by hand, or a Claude Code agent editing its own ~/.claude/CLAUDE.md) never reaches dotfiles/ on its own. wsa checks mise dot status first and warns you when it finds a differs entry — it prints the diff and asks before overwriting, and refuses outright rather than guessing when run non-interactively. If you saw a plain overwrite with no warning, the edit was applied through the raw mise bootstrap --only dotfiles --yes form (scripted/CI use, or an older shell session before this check shipped) — that form has always overwritten silently, by design.

Record the edit back to source before re-running wsa: 

wsr                              # mise dot add --changed — FILE entries only
mise dot add ~/.claude/agents    # DIRECTORY entries (agents, commands, hooks,
                                  # skills, zellij, zsh/completions, gdb, local/bin) —
                                  # name the directory's own target path;
                                  # wsr's --changed does NOT see inside one

mise dot add <directory> captures every edit AND any brand-new file you dropped straight into that directory in one shot — but it’s a replace of the source directory, not a merge, so a source-only placeholder that was never deployed (e.g. .gitkeep in an otherwise-empty dotfiles/claude/agents/) drops out of the source the first time you do this — expected, and harmless once the directory has real tracked content. Then commit the updated source file(s).

mise bootstrap plan / status asks for a sudo password and hangs (no TTY)

This repo ships NO [bootstrap.linux.firewall] table on purpose (Ruling 1 in the migration plan): mise re-execs itself with sudo for any firewall rule, even during a read-only plan/status call, and a non-interactive session (CI, a cron job, an SSH one-liner) has no TTY to answer the password prompt — it just hangs or fails with “sudo: a password is required”.

If you see this, a [bootstrap.linux.firewall] table was added to a config file that loads unconditionally (unsupported here — mise run health would break on every host). Open a port the existing firewall-cmd way instead, inside a post-packages hook task, which only runs during an actual mise bootstrap --yes, never during plan/status. Remove the table to restore unprivileged plan/status.

pueue status fails, or pueued isn’t running

Check the unit first: systemctl --user is-active dev.mise.pueued.service. If it isn’t active, read the log: journalctl --user -u dev.mise.pueued -n 20.

The usual cause is the systemd user manager not carrying MISE_ENV — the unit's ExecStart shim then errors with something like “No version is set for shim: pueued” because it can’t tell which config*.toml files declared the tool. The unit deliberately carries no Environment=MISE_ENV=... line of its own (the value differs per host), so it relies entirely on the user manager's environment: ~/.config/environment.d/10-mise.conf (picked up at the user manager's next start/re-exec — i.e. your next login) and systemctl --user set-environment MISE_ENV=<your token set> (fixes the live manager immediately, no re-login needed). ./bootstrap.sh does both on every run, so this normally only bites after a manual pueued edit or a manager restart that raced the environment file. Fix, then systemctl --user restart dev.mise.pueued.service.

Tofu boxes / missing icons after install

Symptom: starship prompt shows boxes instead of icons; eza rows show empty cells where icons should appear; lazygit / k9s / yazi look broken; on Windows, Windows Terminal pops Unable to find the following fonts: JetBrainsMono NFM. JetBrainsMono Nerd Font Mono isn’t loaded.

Triage:

  • Linux: fc-list | grep -i 'jetbrainsmono nerd font mono' — expect 6 entries. Empty? Run mise run fonts. Re-run starting shells to refresh.
  • Windows: Test-Path "$env:LOCALAPPDATA\Microsoft\Windows\Fonts\JetBrainsMonoNerdFontMono-Regular.ttf" — expect True. False? Re-run bootstrap.ps1 (the Invoke-InstallNerdFonts step is idempotent; takes a stamp-based fast path on a second run). The installer activates the font in the current session (AddFontResourceW + WM_FONTCHANGE), so no logout is needed. If the .ttf exists but apps still can’t find the font (Windows Terminal pops Unable to find the following fonts: JetBrainsMono NFM) — typically after a reboot — the cause is that Windows does not reliably load HKCU per-user fonts into the system font collection at logon (the per-user fonts dir “has no special powers” and is excluded from the KnownFolder API). The installer handles this by registering a per-user, hidden, no-admin scheduled task (WorkstationNerdFontActivate) that re-runs the AddFontResourceW activation at every logon, so the font is durable across reboots. Re-run bootstrap.ps1 to (re-)create the task and re-activate the current session; the same run also rewrites any stale bare-filename HKCU entries left by older builds as full paths.
  • VS Code / Zed still showing tofu: apps cache font lists at launch — quit and relaunch. Also check the font-family name in the app config: on Windows it must be JetBrainsMono NFM, not JetBrainsMono Nerd Font Mono. Nerd Fonts abbreviates the GDI family name to fit Windows’ 31-char limit; the full “Nerd Font Mono” name only resolves in apps that read the typographic name.
  • Windows Terminal still showing tofu: restart it so it re-enumerates the installed fonts. Confirm nerd_font_version in config.toml [vars] matches the $Version literal in scripts/install-nerd-fonts.ps1 — drift between the two means Linux and Windows hosts can end up on different font versions.
  • WSL host running mise run fonts says “skipped on WSL — the Windows terminal resolves fonts”: intentional. WSL apps render via the Windows host’s terminal (Windows Terminal), which uses Windows-registered fonts. Run bootstrap.ps1 on the Windows side instead.
Shell startup / a PATH-scanning command feels slow on WSL (a second or two)

Symptom: opening a new tab, or any command that probes for other binaries on $PATH (e.g. command -v <tool> feature-detection in a shell rc, or the old chezmoi’s clipboard-tool probing before it was retired), stalls ~1.5 s on a WSL host. The process is mostly idle, not computing (low CPU, high wall-clock).

Cause: WSL2 with appendWindowsPath=true tacks the entire Windows %PATH% (~90 /mnt/c dirs) onto $PATH. A lookup for a binary that doesn’t exist stat-walks every /mnt/c dir over the slow 9p/drvfs mount before giving up. Hundreds of failed stats ≈ 1.5 s, and it compounds with every such probe a shell rc or tool runs at startup.

Fix (two parts):

  • Set appendWindowsPath=false under [interop] in /etc/wsl.conf — now deployed for you by mise bootstrap (config.wsl.toml's [bootstrap.files] entry, tracked at configs/wsl/wsl.conf) — then wsl --shutdown from a Windows terminal (ends all WSL sessions) and reopen.
  • The tracked ~/.zshrc / ~/.bashrc re-add only the two Windows dirs still called from WSL — PowerShell (for ~/.claude/notify.sh toasts) and system32 (clip.exe). No action needed; it’s automatic on shell start.

Verify in a fresh tab: echo $PATH | tr ':' '\n' | grep -c /mnt/ drops from ~90 to ~2; a lookup for a nonexistent command (e.g. time command -v not-a-real-binary) drops from over a second to near-instant.

Trade-off: other Windows executables (explorer.exe, VS Code’s code) leave the WSL $PATH. Re-add any you want in ~/.zshrc.local.

WSL disk (ext4.vhdx) keeps growing — freed space never returns to Windows

Symptom: deleting files inside the distro never shrinks the virtual disk on the Windows side. That part is expected: WSL2 VHDs grow on demand but never shrink on their own.

The auto-shrink feature (sparse VHD) is disabled upstream on WSL ≥ 2.5 after data-corruption reports (microsoft/WSL #13075) — so the tracked sparseVhd=true in dotfiles/wslconfig is currently inert (it self-activates for newly created VHDs if Microsoft re-enables the feature), and wsl --manage <Distro> --set-sparse true refuses unless forced.

Find the VHD first (regular PowerShell):

Get-ChildItem HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss |
  ForEach-Object { Get-ItemProperty $_.PSPath } |
  Select-Object DistributionName, BasePath

Safe one-time reclaim (admin PowerShell; manual maintenance — the repo deliberately does not automate this): 

wsl --shutdown
Optimize-VHD -Path "<BasePath>\ext4.vhdx" -Mode Full

No Hyper-V module (Optimize-VHD missing)? Use the always-available diskpart route (still admin): 

wsl --shutdown
diskpart
# inside diskpart:
select vdisk file="<BasePath>\ext4.vhdx"
attach vdisk readonly
compact vdisk
detach vdisk
exit

Unsafe opt-in — only if you accept the corruption risk Microsoft disabled this over (read-only filesystems, lost files). Back up first, then force sparse mode so the disk auto-returns freed space: 

wsl --export <Distro> D:\backup\<Distro>.tar
wsl --manage <Distro> --set-sparse true --allow-unsafe

RAM is the separate, already-solved half: autoMemoryReclaim=gradual in the tracked .wslconfig returns cached VM memory to Windows automatically — no action needed.

LSP servers — a language server is missing after mise bootstrap

There is no separate verify step any more (the Make-era lsp-servers target is gone with makefile/). mise bootstrap's tools phase (also reachable directly as ./bootstrap.sh --dev or scripts/lib/mise-install.sh) is what installs the whole stack, via mise. Servers and their mechanisms:

  • clangd — not a mise tool; comes from dnf (clang-tools-extra in config.host.toml, see the C/C++ entry below). mise run health does not check it — verify with command -v clangd.
  • Windows — the same servers install via bootstrap.ps1's Invoke-MiseRuntimes step, straight from config.toml + config.dev.toml; mise ls --missing and .\bootstrap.ps1 -Doctor are the checks; open a new terminal after the first run (User PATH).

C / C++ toolchain — a tool is missing, or ninja / vcpkg behaves oddly

The compilers, debuggers and analysis tools (gcc-c++, clang, clangd/clang-tidy/clang-format, lldb, valgrind, cppcheck, cmake, meson, ninja-build, heaptrack, the sanitizer runtimes) install via dnf on dev_machine only, best-effort. Several come from EPEL/CRB, not BaseOS — the config.host.toml pre-packages hook (mise run enable-el-repos) auto-enables both (EPEL + CodeReady Builder) on RHEL-family hosts before the dnf batch runs, because EPEL on EL9 needs CRB or meson/ninja-build (which live in CRB) and heaptrack/bear (which pull CRB deps) fail to resolve. If a package still fails to resolve (e.g. CRB couldn’t be auto-enabled), enable it manually and re-run: 

sudo dnf install epel-release
sudo dnf config-manager --set-enabled crb   # EL9 Alma/Rocky/Stream (powertools on EL8)
mise bootstrap --only packages --yes

ninja: command not found — on RHEL the binary is ninja-build, not ninja. If a project hard-codes ninja, symlink it once: ln -s "$(command -v ninja-build)" ~/.local/bin/ninja.

Two GDB front-ends, no conflict. Plain gdb auto-loads GEF (via the tracked ~/.gdbinit); pwndbg is a separate standalone command. So gdb ./a.out → GEF, pwndbg ./a.out → pwndbg, and gdb -nx ./a.out → vanilla gdb (no GEF). nnd ./a.out is the modern from-scratch TUI debugger.

vcpkg: it lives at $VCPKG_ROOT (~/.local/share/vcpkg, a user-owned shallow clone at the pinned tag, installed by mise run vcpkg and exported by the shell rc on dev hosts). Being user-owned, classic-mode vcpkg install <pkg> (which writes into the tree) needs no sudo any more — manifest mode (a vcpkg.json per project, installs into the project’s vcpkg_installed/) is still preferred for reproducibility, but nothing blocks classic mode now. Missing entirely? mise run vcpkg. Prefer the compiler sanitizers (-fsanitize=address,undefined, ~2–4× overhead) over Valgrind (~20–50×) for everyday checks; keep Valgrind for unmodified binaries and uninitialized-read detection ASan misses.

bootstrap.ps1 popped a UAC prompt (or SSHFS-Win reports “skipping”)

That’s the SSHFS-Win step — the one deliberate exception to the otherwise admin-free bootstrap. SSHFS-Win depends on WinFsp, a kernel-mode filesystem driver; kernel drivers install machine-wide, so elevation is unavoidable. The step is best-effort: declining the prompt, being offline, or having neither winget nor network just skips it — nothing else in the bootstrap is affected, and an already-installed machine never sees the prompt (Uninstall-registry detection).

Install it later with winget install SSHFS-Win.SSHFS-Win (pulls WinFsp automatically) or re-run .\bootstrap.ps1 and accept the prompt; suppress the attempt entirely with -SkipElevated. Once installed, mount with net use X: \\sshfs\user@host or browse \\sshfs\user@host directly in Explorer.

Zellij’s top bar is plain, shows a “permission” request, or renders boxes instead of rounded pills

The top bar is the zjstatus plugin. A permission request in the bar is the one-time first-run prompt on that host: click the bar (or CTRL+P then ↑ to focus it) and press Y. The grant is cached in ~/.cache/zellij/permissions.kdl.

mise run bootstrap              # user-level, no sudo — re-copies zjstatus.wasm
                                 # into zellij's data dir (runs on both scopes)
zellij kill-session main        # config and plugins load when a session is created
