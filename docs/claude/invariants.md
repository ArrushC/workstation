# Load-bearing invariants

> Claude-internal reference, split out of `CLAUDE.md` to keep it lean. CLAUDE.md
> carries a terse index of these rule headlines; this file holds the full *why*
> and failure modes. README documents the *what*; these are the *why*. Each one
> exists because the opposite was tried at some point and broke.

- **`bootstrap.sh` is a thin seed.** No `*_VERSION` constants, no install logic — with one deliberate exception: `MISE_VERSION`/`MISE_SHA256`, the pinned, sha256-verified `mise` binary it installs into `~/.local/bin` before handing off. Everything else lives in `config*.toml` or `makefile/`. If `bootstrap.sh` and `scope.mk` ever disagree on scope, fix `scope.mk`.
- **Tool pins live in `config.toml`/`config.linux.toml`/`config.dev.toml` + the three lock files (`mise.lock`, `mise.linux.lock`, `mise.dev.lock`) + `locks/**`.** This repo root IS mise's global config dir (Linux: `~/.config/mise`; Windows: `%USERPROFILE%\.config\mise`); the lock files (one per config file, mise's own mechanism) replace the old stamp-filename-baked-version trick — a pin bump plus a re-lock is what triggers mise to reinstall, not a Make stamp. Never hand-edit `mise*.lock` or anything under `locks/**`; regenerate with `mise lock --global` from outside the checkout via the `XDG_CONFIG_HOME` symlink form, then normalize the sidecar paths (see `docs/claude/file-care.md`). `makefile/versions.mk` keeps only the five pins Make still owns directly (`CLAUDE_VERSION`, `DOZZLE_VERSION`, `JETBRAINSMONO_NERD_VERSION`, `VCPKG_VERSION`, `PYTHON_VERSION`) plus the `ZJSTATUS_ZELLIJ_FLOOR` coupling constant, until PR2 moves host state onto mise too. Never re-introduce per-tool versions in `bootstrap.sh`, scripts, or new playbooks.
- **`$(SUDO)` thread.** `scope.mk` sets `SUDO := sudo --preserve-env=DEST` for dev, empty for prod. The `TOOL` macro (the sole surviving bespoke-target macro; `EGET_TOOL`/`USER_TOOL` are gone with the tool layer) must use `$(SUDO)`, never literal `sudo`. The `--preserve-env` list is load-bearing — sudo's `env_reset` strips DEST otherwise. New scope-aware env vars must be added to the list.
- **`MODE` has no default.** `scope.mk` errors at parse time if missing. The choice (dev vs prod) is too load-bearing to silently fall through. `bootstrap.sh` rejects `--full` and missing flags for the same reason. The documented `make dev` / `make prod` entry points work via **goal inference in `makefile/Makefile`** — MODE is derived from the goal name *before* `include scope.mk`, and contradictions (`make dev MODE=prod`, `make dev prod`) error out. The inference MUST stay above the include: the original "friendly alias" recipes (`$(MAKE) MODE=dev provision`) were dead code from day one (5a3c196) because scope.mk's parse-time `$(error)` fires before any recipe runs — first actually hit when PR #62's pin bumps needed a live `make dev`. This is inference from an explicit goal, not a default: goal-less `make` and every other target still require `MODE=`.
- **Provisioning is parallel-by-default; phases are recipe lines, NOT prerequisites.** The per-tool layer is an independent-stamp, network-bound DAG — measured 6.3× at `-j8` over 12 tools (13.7s → 2.2s, byte-identical results). Top-level make self-assigns `--jobs=$(nproc)`; `make <goal> -j1` is the serial escape hatch (a command-line `-j` IS visible in parse-time `MAKEFLAGS`, so the guard yields — verified on GNU make 4.3). Empirically-established constraints (all verified on make 4.3, this fleet's version — `.WAIT` needs 4.4+ and is NOT available):
  - **`MAKELEVEL`-guard the self-assign.** Makefile-assigned `-j`/`-O` do NOT reach a sub-make's parse-time `MAKEFLAGS`, so an unguarded sub-make re-adds `-j` and clobbers the parent's jobserver ("-jN forced in submake" warnings). Only level 0 self-assigns; recursive phases inherit parallelism through the jobserver via the `+` recipe prefix. The same block is duplicated in the root `GNUmakefile` (which is level 0 for root invocations — its sub-make is level 1 and must NOT re-add).
  - **Phases are `provision`'s sequential recipe lines** (`+@$(MAKE) packages` → `+@$(MAKE) --output-sync=target provision-fanout` → `+@$(MAKE) dotfiles`). Prerequisites of one target are UNORDERED under `-j` — `provision: packages tools …` cannot express "packages before tools", and per-stamp `| packages` edges would force dnf runs into every standalone `make <tool>`. New provision-phase targets join `PROVISION_FANOUT` in `makefile/Makefile`.
  - **`packages-core → packages-epel → packages-optional` are real dependency edges** (packages.mk): optional is best-effort `|| true`, so racing ahead of EPEL/CRB enablement silently skips EPEL/CRB-backed packages — the CRB failure mode again, as a race. The chain also serializes dnf (global lock), and on dev it fields the single sudo password prompt before the fanout starts (everything after rides the cached timestamp).
  - **`dotfiles` stays the UNSYNCED serial tail.** `chezmoi update` prompts interactively on stdout; under `--output-sync` that prompt is buffered → invisible → looks hung. Recursive (`+`) recipe lines are exempt from the parent's output-sync, and the dotfiles child gets no `-O` of its own. Running last also guarantees chezmoi `run_` scripts see a fully-provisioned host (tic from ncurses, pueued unit, …).
  - **`--output-sync=target` is passed explicitly to the fanout child only.** `-O` never appears in parse-time `MAKEFLAGS` (unlike `-j`), so a "set globally unless overridden" guard is dead code — there is no way to detect an explicit `--output-sync=none`. Direct multi-target runs (`make a b c`) interleave unless you pass `-O` yourself.
- **Makefile recipe lines must be tab-indented**, not spaces. Macro bodies use `$$` to defer expansion to rule-fire time — don't switch to single `$` without testing.
- **ccstatusline sentinel block.** Auto-generated between `# CCSTATUSLINE:START` / `# CCSTATUSLINE:END` (column 0) in `chezmoi/.chezmoiignore.tmpl` by `scripts/setup-ccstatusline.sh`. Each opt-out host contributes one line of the form `{{ if eq .chezmoi.hostname "<host>" }}.config/ccstatusline/settings.json{{ end }}` (TARGET path, not the `dot_config/...` source name — `.chezmoiignore` matches target paths). Hand-edits inside the markers get clobbered on any subsequent setup-ccstatusline.sh run that hits options 1, 2-persist, or 3.
- **The `CCSTATUSLINE_VERSION` dual-edit is gone.** ccstatusline is a plain `npm:ccstatusline` mise pin in `config.dev.toml` now; the enforced `statusLine.command` in `chezmoi/private_dot_claude/modify_private_settings.json` is the bare command `ccstatusline` (no version literal), so there is nothing left to drift against `makefile/versions.mk` — mise's own pin is the only version that matters.
- **`versions.mk` ↔ `lib/font.sh` ↔ `install-nerd-fonts.ps1` triple-edit for `JETBRAINSMONO_NERD_VERSION`.** Three places must move together when bumping the Nerd Font pin: (1) `JETBRAINSMONO_NERD_VERSION` in `makefile/versions.mk`; (2) the `case "$VERSION" in 3.4.0) EXPECT_SHA='...' ;;` branch in `makefile/lib/font.sh` (SHA256 of `JetBrainsMono.tar.xz` from the matching `SHA-256.txt` upstream); (3) the `$Version` + `$Sha256` literals in `scripts/install-nerd-fonts.ps1` (SHA256 of `JetBrainsMono.zip` — different artifact, different hash). Procedure: bump the version variable; `curl -sL https://github.com/ryanoasis/nerd-fonts/releases/download/v<VER>/SHA-256.txt | grep -E 'JetBrainsMono\.(tar\.xz|zip)$'` for the two new SHAs; substitute both. Drift means Linux and Windows hosts can end up on different font versions across a mid-bump fleet, with subtle icon-rendering differences across host kinds. No chezmoi-template variable currently bridges them.
- **Tools are mise-managed via `make tools` (BOTH scopes, USER-LEVEL — never `$(SUDO)` except the one-time legacy sweep in `tasks/migrate-legacy`).** This is PR1 of the Make→mise migration (spec `docs/superpowers/specs/2026-09-16-mise-everything-design.md`; supersedes the tool-layer half of the earlier `2026-09-13-mise-runtimes-design.md`, whose runtime-management decisions carry forward unchanged) — **every** tool in the toolbelt, not just the runtimes, is now a mise pin. Declarations: `config.toml` (cross-platform: `uv`, `python`), `config.linux.toml` (the Linux toolbelt, both scopes — aqua-registry short names preferred; `github:`/`http:` backends only for the tools the registry gets wrong, e.g. a glibc floor EL9 can't meet), and `config.dev.toml` (dev tools on both OSes; Linux-only dev tools carry `os = ["linux"]` so mise never tries to install them on Windows). **This repo root IS mise's global config dir** (Linux `~/.config/mise`, Windows `%USERPROFILE%\.config\mise`) — there is no separate `conf.d`, nothing chezmoi-generated or copied for mise any more; mise reads `config*.toml` directly off the checkout. `MISE_ENV` (computed by `scripts/lib/mise-env.sh <dev|prod>`, exported by the rc files / a Windows User var / `~/.config/environment.d/10-mise.conf` for systemd user units, plus a direct unit-level `Environment=MISE_ENV=...` on `pueued.service` itself — systemd user units start with no shell env, so the shim can't resolve `pueued` without it) picks which files load: `linux` (prod) · `linux,dev,host,wsl` · `linux,dev,host,native` · `windows,dev`. `make tools` runs three steps in order: `scripts/lib/mise-install.sh` (`mise install`, force-reinstalling `node` only when its declaration changed while it was already installed — tracked via a cksum marker under `~/.local/state/workstation/`, so a changed npm-postinstall string re-runs the language-server install without forcing a reinstall on every unrelated pin bump — then `mise prune`), `tasks/verify-tools` (the post-install capability gate — see the verify-gate entry below), and `tasks/migrate-legacy` (one-time sweep of the pre-mise binaries: on dev the whole `/usr/local` node/go/uv/LSP name list plus the eget-era tool set that used to live in `~/.local/bin`/`/usr/local/bin`, on prod only `uv`/`uvx`; sudo is used ONLY for `/usr/local` on a dev host, and is skipped ENTIRELY — not path-by-path — when there is no sudo on this host, since a sudo-less prod host never had a Make install under `/usr/local` to sweep in the first place). `python` **IS declared** in `config.toml` (a three-way pin with `PYTHON_VERSION` in `versions.mk` and `$PythonEnvVersion` in `bootstrap.ps1`, asserted equal by `check-invariants.sh`) — unlike the earlier mise-runtimes design's deliberate omission of `python`, PR1 needs it because the dependency-locked `pypi:`/`pipx:` tools (`basedpyright`, `glances`, `asciinema`, `harlequin`) run `uv sync --frozen --python <mise python>` to produce a lockfile, and without a declared interpreter mise falls back to the system 3.9, which refuses those installs. It shadows `python3` only in mise-activated shells; the system interpreter stays untouched at `/usr/bin/python3` (sudo and system services never see it — same EL9-Python-3.9-floor story that caps the GEF vendoring, see the C/C++ toolbelt entry below, but `python-env`'s and mise's own `python` are two *different* installs sharing a version by coincidence of the three-way pin, not the same interpreter). Non-interactive shells see the tools through `~/.local/share/mise/shims` (`dot_zshenv.tmpl`; `dot_bashrc.tmpl` ABOVE its interactive guard — parity pair), interactive ones through `mise activate`. `lsp-servers` is now a thin dev alias (+ clangd verify only — every other server installs as part of `tools`). **Windows half:** the checkout at `%USERPROFILE%\.config\mise` IS mise's config dir there too (no separate conf.d, ever, on either OS); `MISE_ENV` persists as a User environment variable; `Invoke-MiseRuntimes` in `bootstrap.ps1` (right after chezmoi applies) runs `mise install` directly against `config.toml` + `config.dev.toml` at the checkout root — `config.linux.toml` never loads there (`linux` is not in the Windows `MISE_ENV`), so only the `config.dev.toml` tools without `os = ["linux"]` install on Windows (node, Go, uv, gopls, the language servers, ccstatusline); the Linux-only dev tools (herdr, opencode, omp, pwndbg, DevToys CLI) stay separate `$PortableTools` pins there instead. **Why this shape — the failure stories that motivated the migration (from the mise-runtimes precursor, still the reasoning behind going further in PR1):** (1) the install paths mise replaced verified **nothing** the way mise does — `lib/node.sh`/`lib/go.sh` curl'd tarballs straight off nodejs.org/go.dev with no checksum and no signature, and eget's own per-tool checks caught arch/loader/glibc problems only, never a supply-chain one; mise verifies what it downloads (the uv install, for instance, goes through GitHub artifact attestations + checksum). (2) mise had been on the toolbelt since the 2026-05 wave and wired via `mise activate` in both rc files since 2026-07, **with almost nothing to manage** — a tool manager installed and idle while ~90 hand-rolled `EGET_TOOL`/`TOOL`/`USER_TOOL` macros in the now-deleted `tools.mk` did its job worse. (3) `mise prune --yes` removes every installed version no config references, including ad-hoc installs made by hand outside the tracked config (it dropped a stray `aqua:nushell/nushell` from the WSL host on the first real mise-runtimes run, before PR1) — so a pin belongs in `config*.toml`, never a bare `mise use -g <tool>` run by hand.
- **`python-env` is a both-scopes, USER-LEVEL bespoke Make target (every host gets the ad-hoc scripting venv) — literally never `$(SUDO)`, unlike its dev-only `vcpkg` sibling (the other former sibling, `pwndbg`, is a mise tool now — see the C/C++ toolbelt entry below).** The posture matches the `pypi:basedpyright` mise tool in `config.dev.toml`: ad-hoc Python tooling belongs to the dev user, not `/usr/local`. `makefile/lib/python-env.sh` (LF, 0755, shfmt/shellcheck-clean, auto-covered by the `makefile/lib/*.sh` glob) takes `<python-version>`, runs `uv python install` (uv is mise-managed — the recipe prepends `$(MISE_SHIMS)` so it resolves before any shell has activated mise; the pinned CPython comes via python-build-standalone and lands user-level under `~/.local/share/uv/`), recreates `~/.local/share/workstation-python` from scratch (`rm -rf` first — deterministic, and it means any ad-hoc `uv pip install -p <env> <pkg>` addition is disposable, wiped on the next rebuild), then `uv pip install --python <env> --upgrade`s the nine-library canonical list held as a **one-line** bash array (`PY_LIBS`). **Why libs track latest but the runtime is exact-pinned:** these are ad-hoc scripting libs (the `pypi:glances`/`asciinema`/`harlequin` precedent — mise tools pinned to `"latest"` that self-refresh on every provision, never individually version-pinned); `PYTHON_VERSION` in `versions.mk` is the one thing that IS exact-pinned, because the venv's identity (and the install stamp) depends on it. **Why `wpy` is a wrapper script, not a symlink:** a symlink from `~/.local/bin/wpy` to the venv's `bin/python` loses the venv — CPython resolves the full symlink chain back to uv's base interpreter and never finds the `pyvenv.cfg` sitting next to the *resolved* target, so imports silently fail (verified 2026-08-03; see commit `60595c6`). The tiny `#!/bin/sh` wrapper that `exec`s the venv python by its real path keeps the venv, and lets nested shebangs (`#!/usr/bin/env wpy`) work. `textual`/`typer` stay plain symlinks — they're venv entry-point scripts whose OWN shebangs already point into the env, so the symlink-resolution problem doesn't apply to them. **Stamp composition:** `$(STAMP)/python-env-$(PYTHON_VERSION)-<cksum>.done`, where `<cksum>` is `cksum lib/python-env.sh` — so either a `PYTHON_VERSION` bump OR an edit to the lib list (which lives inside that same script) changes the stamp filename and triggers a rebuild on the next `make python-env`; `uv` (mise-managed) is a PRIOR provision phase (`tools`, not a Make prerequisite — `provision`'s sequential recipe lines already order `tools` before `python-env`'s fanout member), so no order-only dependency on a mise stamp is needed any more. Upgrading the latest-tracking libs is deliberate and manual: `make python-env-rebuild` (a plain re-`provision` never re-fires a stamp that's still current). **`python-env-rebuild` is a serialized two-phase wrapper** (`+@$(MAKE) clean-python-env` then `+@$(MAKE) python-env`, the `provision` phases-are-recipe-lines precedent) — a combined `make clean-python-env python-env` goal list races under the default `-j$(nproc)` (both are independent command-line goals, so make may run them in parallel job slots; `python-env` can stat the still-present stamp before `clean-python-env`'s `rm` fires, leaving the env+launchers+stamp deleted and NOTHING rebuilt). Two recipe lines within a single target's recipe, by contrast, always execute in order regardless of `-j`. **Windows half:** uv is mise-installed (`Invoke-PythonEnv` resolves it via `mise which uv` after `Invoke-MiseRuntimes`, and warns-and-skips when that comes back empty) + `Invoke-PythonEnv`, which builds `%LOCALAPPDATA%\workstation\python-env` from `$PythonEnvVersion`/`$PythonLibs` and writes the three `.cmd` shims into `workstation\bin`. **The lesson uv's retired `$PortableTools` entry taught still binds every `tree`-layout tool** (mise is one): a `tree` extraction WIPES its `Dest` on every re-pin, so such a tool gets its OWN directory — **never** `workstation\bin`, which holds the `wpy.cmd`/`textual.cmd`/`typer.cmd` shims a wipe would delete (uv had `workstation\uv` until 2026-09-16; mise has `workstation\mise`). **Why a uv-managed CPython at all, instead of the system interpreter:** this sidesteps the same EL9-ships-Python-3.9 floor that caps the GEF vendoring at release `2024.06` (see the C/C++ toolbelt entry below) — rather than being stuck on whatever `python3` the dnf base OS provides, `python-env` installs its own exact-pinned, independently-upgradable CPython via `uv python install`, so current `polars`/`duckdb`/`pydantic-core` wheels are available regardless of the host's system Python. No WSL skip (useful in a WSL dev guest, like `pwndbg`/`vcpkg`); no rc changes (`~/.local/bin` is already on PATH).
- **Machine-level Claude memory is `chezmoi/private_dot_claude/CLAUDE.md` → `~/.claude/CLAUDE.md`**, dev-only (chezmoi gated via the `.claude` dev/prod block). The `<!-- TOOLS:START -->` / `<!-- TOOLS:END -->` sentinel block is auto-generated by `scripts/gen-tool-memory.sh`, which reads `config.toml`/`config.linux.toml`/`config.dev.toml` (every mise tool pin) + `makefile/versions.mk` (the few Make-owned pins) + `makefile/packages.mk` (dnf lists) as its single source of truth. **Hand-edits inside the sentinels are clobbered** by the next generator run. `scripts/check-invariants.sh` runs the generator against a temp file and diffs to enforce zero drift in CI. The hook `.claude/hooks/sync-tool-memory.sh` regenerates on every edit to `config.toml`/`config.*.toml`/`makefile/versions.mk`/`makefile/packages.mk` (PostToolUse). Add a guidance prose section outside the sentinels; the block structure (categories, commands, versions) is driven entirely by the generator.
- **`workstation-lsp` is a declarative skills-dir plugin; it installs nothing.** Source: `chezmoi/private_dot_claude/skills/workstation-lsp/` (dev-only, under the same `.claude` chezmoi gate). Three files: `dot_claude-plugin/plugin.json` (plugin manifest), `dot_lsp.json` (server registry → `~/.claude/skills/workstation-lsp/.lsp.json`), `SKILL.md` (marker + diagnostics toggle note). Auto-loads by presence once deployed; the enforced `workstation-lsp@skills-dir` entry in `modify_private_settings.json`'s `enabledPlugins` block is belt-and-suspenders. **`.lsp.json` MUST be strict JSON** — the runtime `LSP` loader rejects JSONC `//` comments (all 12 servers fail to load silently). `claude plugin validate` is JSONC-tolerant and will NOT catch this; test with `python3 -m json.tool .lsp.json`. Diagnostics are on by default (the `"diagnostics": false` per-server toggle is documented in `SKILL.md`, not in `.lsp.json`). `check-invariants.sh` runs `claude plugin validate --strict` over the plugin source directory as a soft check. Binaries come from `make tools MODE=dev` (mise, from `config.dev.toml`) — `make lsp-servers MODE=dev` only verifies `clangd`; the plugin merely registers server paths. Verify after `cza` + `/reload-plugins`: `/reload-plugins` reports our **12** servers (13 total on this host — the +1 is the standalone `lua-lsp` plugin), with no "error during load".
- **Docker is dev-only and managed via `docker-engine`.** Bespoke target in `makefile/Makefile` (outside the macros), joining `provision`'s deps only when `MODE=dev`, and skipped on WSL (`IS_WSL=true` → bare-phony skip message; the engine there is Docker Desktop on the Windows host — same gating as `dozzle-service`/`cockpit-service`). Installs Docker CE from Docker's official dnf repo (repo file curl'd straight into `/etc/yum.repos.d/` to avoid a dnf-plugins-core dependency; `linux/rhel` on RHEL proper, `linux/centos` on Alma/Rocky/CentOS), enables the service, and adds `$USER` to the `docker` group (takes effect on next login — needed for sudo-less lazydocker/dive/ctop). Fast-path: a pre-existing `docker` on PATH (manual install or podman shim) skips the repo+package steps — never fight an existing engine; the enable/group steps are guarded for that case (unit or group may not exist). NO `versions.mk` pin and no version in the stamp — Docker CE versions come from dnf, same precedent as cockpit. `dozzle-service`'s stamp order-only-depends on `$(STAMP)/docker-engine.done` (the stamp FILE, not the phony — the same stamp-on-stamp order-only-dep discipline that used to gate the now-deleted `EGET_TOOL` macro's per-tool stamps too) so `make -j` can't fire dozzle before the engine exists; dozzle's `command -v docker` sanity check stays as a safety net for direct invocation.
- **`HELIX_RUNTIME` is gone (both scopes, both OSes).** It used to be needed because `make` installed the Helix runtime to a dev-only location (`/usr/local/lib/helix/runtime`) that wasn't one of Helix's built-in search paths (`~/.config/helix/runtime`, `<bin>/runtime`), so the rc had to export `HELIX_RUNTIME` explicitly or Helix silently fell back to its built-in theme (`failed to load theme … file not found` in `~/.cache/helix/helix.log` — this is exactly how `tokyo_night` then `catppuccin_mocha` silently never loaded, historically). Now Helix is a mise tool (`helix` in `config.linux.toml`, the aqua-registry archive) whose archive carries `runtime/` right next to `hx` — one of Helix's own built-in search paths (`<bin>/runtime`) — so it needs no env var on any scope or OS. Verify per dev host after `make tools MODE=dev`: `hx --health` lists a runtime path with no "does not exist" warning, and a `hx <file>` launch adds no `failed to load theme` line to the log.
- **The C/C++ toolbelt deliberately spans three install mechanisms; don't "unify" them.** (1) The **bulk is dnf, dev-only, best-effort** — `gcc-c++ clang clang-tools-extra llvm lldb valgrind cppcheck ltrace libasan libubsan libtsan cmake meson ninja-build heaptrack bear ccache` live in `LINUX_OPTIONAL_PACKAGES` (`makefile/packages.mk`), not the core list, because several come from EPEL/CRB rather than BaseOS (`clang-tools-extra` → clangd+clang-tidy+clang-format, `cppcheck`, `meson`, `ninja-build`, `heaptrack`, `bear`, `ccache`). `bear` is the compile-DB generator (`bear -- make` → `compile_commands.json`) that makes clangd usable on non-CMake/meson projects; `ccache` is a compiler cache. **`packages-epel` auto-enables EPEL + CRB** on RHEL-family hosts (best-effort, idempotent: ensures `dnf-plugins-core`, then `dnf config-manager --set-enabled` across `crb` [EL9] / `powertools` [EL8] / `codeready-builder-*` [subscribed RHEL]). Its RHEL-family detection **sources `/etc/os-release` and matches `$ID`/`$ID_LIKE`** — do NOT revert to a loose `grep -i fedora /etc/os-release`: AlmaLinux's os-release carries `ID_LIKE="rhel centos fedora"` + `LOGO="fedora-logo-icon"`, so the substring grep matched Alma as "Fedora" and skipped EPEL/CRB on the exact hosts that need it (skip only true `$ID = fedora`, then require an EL marker rhel/centos/almalinux/rocky) — this is required, NOT optional polish: EPEL on EL9 fails to resolve many packages without CRB, and `meson`/`ninja-build` live directly in CRB while `heaptrack`/`bear` pull CRB-resident deps. Discovered the hard way — a fresh AlmaLinux 9 host had EPEL on but CRB off, so exactly those four silently hit the skip path. The per-package `|| true` fast-path in `packages-optional` is the final fail-soft: even if CRB can't be enabled (e.g. no `config-manager`, or a future EL10/dnf5 host whose syntax is `config-manager setopt <repo>.enabled=1`), the missing ones skip cleanly instead of aborting the build. `gcc`/`make` are already core; `gdb`/`perf`/`strace` were already in the optional list — NOT re-added (but `gdb-gdbserver` — the separate EL subpackage providing the remote-debug stub `gdbserver`, since the `gdb` package doesn't bundle it — IS in the list, paired with `gdb` in the general dev-tools group, NOT the C/C++ block; verified on AlmaLinux 9: `dnf provides */bin/gdbserver` → `gdb-gdbserver`). The sanitizers (ASan/UBSan/TSan) are compiler features, not packages — `libasan`/`libubsan`/`libtsan` are only the **gcc** runtime `.so`s the `-fsanitize=` link step needs (clang ships its own compiler-rt). GOTCHA: the RHEL `ninja-build` package installs the binary as `ninja-build`, not `ninja`. (2) **`nnd`** (modern from-scratch TUI debugger) is a both-scopes mise tool (`github:al13n321/nnd` = `"0.80"` in `config.linux.toml`) — its release assets are bare `nnd` + `nnd-dbgo` with no os/arch tokens, so even mise needs the explicit `asset_pattern = "nnd"` override to disambiguate (the same class of problem `jq`/`shfmt`/`witr` used to solve via the now-deleted `direct.sh`, solved the same way every mise tool solves an ambiguous asset: an explicit `asset_pattern`). - **Post-install binary verification gate.** Under Make's per-tool macros this used to be an install-time `&&`-chain onto each tool's install command, so a bad binary failed *that tool's* install before its stamp was written; under mise (which owns install ordering and has no per-tool Make stamp to gate) it is a **post-install** sweep instead: `tasks/verify-tools` (a `post-tools`-shaped hook, run by `scripts/lib/mise-install.sh`/`make tools` after `mise install` completes) walks every bin dir `mise bin-paths` exposes and runs `scripts/lib/verify-binary.sh` (moved from `makefile/lib/` to `scripts/lib/`, same logic) on every ELF it finds — script "tools" (nb, sysz, ssh-copy-id, cht.sh) pass through untouched since they never match the ELF-magic check. A failure fails the whole `make tools` run loudly; the fix is an explicit `github:` `asset_pattern` for that tool in `config*.toml` (converting silent "installed but won't run" successes — the historical fastfetch musl-loader and usql glibc-floor breakages — into loud, retryable stops, same as before).
  - **Non-executing**: ELF magic + `e_machine` arch, then `ldd` (static → PASS; any `not found` → FAIL), then glibc-floor via `objdump`/`readelf`.
  - **Static binaries MUST pass** (most musl-asset tools are static). Do not "tighten" the check to fail non-dynamic binaries — it would false-fail the many musl tools in `config.linux.toml`.
  - **Degrades**: no `objdump`/`readelf` (minimal prod) → skip the glibc-floor sub-check with a note; keep ELF+arch+ldd.
  - **Symlinked bins are followed, not skipped** — mise's `.mise-bins/` shim indirection means a bin-path entry is often a symlink; `[ -f ]`, `head -c4`, and `verify-binary.sh` itself all resolve through it (a plain `find` without `-L` would miss them).
  - Verify with: `MISE_CONFIG_DIR=$PWD MISE_DATA_DIR=/tmp/mise-sandbox MISE_ENV=linux,dev,host,native mise install && MISE_DATA_DIR=/tmp/mise-sandbox tasks/verify-tools` — a passing run prints `✓ verify-tools: N ELF binaries pass (arch, loader, glibc floor)`.
- **SSH connection multiplexing is gated out on Windows.** `chezmoi/private_dot_ssh/private_config.tmpl` (cross-platform; deploys to `~/.ssh/config` on both OSes) keeps its `ControlMaster auto` / `ControlPersist 60s` / `ControlPath ~/.ssh/cm-%r@%h:%p` block under `Host *` inside a `{{ if ne .chezmoi.os "windows" }}…{{ end }}` gate. Windows OpenSSH can't multiplex — the muxed connection runs over a handle that isn't a Winsock socket, so `getsockname()` returns `WSAENOTSOCK` (`getsockname failed: Not a socket`) and the session hangs until `ServerAlive` trips (`Timeout, server <host> not responding.`). This breaks **every** Windows ssh, including git's SSH transport to GitHub — a chicken-and-egg, since pulling the fix itself needs ssh: break the loop with a one-shot `GIT_SSH_COMMAND="ssh -o ControlMaster=no -o ControlPath=none" git pull`, then `chezmoi apply` strips the block from the deployed config for good. The gate deliberately keeps multiplexing on Linux/macOS (load-bearing for `scripts/update-hosts.sh` bulk runs + interactive `ssh`/`scp`/`rsync` reuse). Don't move `ControlMaster` outside the gate, and don't drop the `.tmpl` suffix. Per-host opt-out anywhere (incl. a stale Windows host pre-`apply`): `ControlPath none` in `~/.ssh/config.local` (Included first, first-match-wins). Verify after apply: `ssh <managed-host> hostname` connects with no `-o` overrides.
