# Load-bearing invariants

> Claude-internal reference, split out of `CLAUDE.md` to keep it lean. CLAUDE.md
> carries a terse index of these rule headlines; this file holds the full *why*
> and failure modes. README documents the *what*; these are the *why*. Each one
> exists because the opposite was tried at some point and broke.

- **`bootstrap.sh` is a thin seed.** No `*_VERSION` constants, no install logic. Everything in `makefile/`. If `bootstrap.sh` and `scope.mk` ever disagree on scope, fix `scope.mk`.
- **Tool versions only in `makefile/versions.mk`.** Baked into the stamp filename, so bumps auto-trigger reinstall. Never re-introduce per-tool versions in `bootstrap.sh`, scripts, or new playbooks.
- **`$(SUDO)` thread.** `scope.mk` sets `SUDO := sudo --preserve-env=DEST,HELIX_RUNTIME_DEST` for dev, empty for prod. Macros (`TOOL`, `EGET_TOOL`) must use `$(SUDO)`, never literal `sudo`. The `--preserve-env` list is load-bearing — sudo's `env_reset` strips DEST otherwise. New scope-aware env vars must be added to the list.
- **`MODE` has no default.** `scope.mk` errors at parse time if missing. The choice (dev vs prod) is too load-bearing to silently fall through. `bootstrap.sh` rejects `--full` and missing flags for the same reason. The documented `make dev` / `make prod` entry points work via **goal inference in `makefile/Makefile`** — MODE is derived from the goal name *before* `include scope.mk`, and contradictions (`make dev MODE=prod`, `make dev prod`) error out. The inference MUST stay above the include: the original "friendly alias" recipes (`$(MAKE) MODE=dev provision`) were dead code from day one (5a3c196) because scope.mk's parse-time `$(error)` fires before any recipe runs — first actually hit when PR #62's pin bumps needed a live `make dev`. This is inference from an explicit goal, not a default: goal-less `make` and every other target still require `MODE=`.
- **`EGET_TOOL` stamp-on-stamp order-only dep.** Per-tool stamps depend on `$(STAMP)/eget-$(EGET_VERSION).done` (the stamp file), NOT a phony. Putting the dep on the phony breaks `make -j` (Make resolves the stamp directly, bypassing order).
- **Provisioning is parallel-by-default; phases are recipe lines, NOT prerequisites.** The per-tool layer is an independent-stamp, network-bound DAG — measured 6.3× at `-j8` over 12 tools (13.7s → 2.2s, byte-identical results). Top-level make self-assigns `--jobs=$(nproc)`; `make <goal> -j1` is the serial escape hatch (a command-line `-j` IS visible in parse-time `MAKEFLAGS`, so the guard yields — verified on GNU make 4.3). Empirically-established constraints (all verified on make 4.3, this fleet's version — `.WAIT` needs 4.4+ and is NOT available):
  - **`MAKELEVEL`-guard the self-assign.** Makefile-assigned `-j`/`-O` do NOT reach a sub-make's parse-time `MAKEFLAGS`, so an unguarded sub-make re-adds `-j` and clobbers the parent's jobserver ("-jN forced in submake" warnings). Only level 0 self-assigns; recursive phases inherit parallelism through the jobserver via the `+` recipe prefix. The same block is duplicated in the root `GNUmakefile` (which is level 0 for root invocations — its sub-make is level 1 and must NOT re-add).
  - **Phases are `provision`'s sequential recipe lines** (`+@$(MAKE) packages` → `+@$(MAKE) --output-sync=target provision-fanout` → `+@$(MAKE) dotfiles`). Prerequisites of one target are UNORDERED under `-j` — `provision: packages tools …` cannot express "packages before tools", and per-stamp `| packages` edges would force dnf runs into every standalone `make <tool>`. New provision-phase targets join `PROVISION_FANOUT` in `makefile/Makefile`.
  - **`packages-core → packages-epel → packages-optional` are real dependency edges** (packages.mk): optional is best-effort `|| true`, so racing ahead of EPEL/CRB enablement silently skips EPEL/CRB-backed packages — the CRB failure mode again, as a race. The chain also serializes dnf (global lock), and on dev it fields the single sudo password prompt before the fanout starts (everything after rides the cached timestamp).
  - **`dotfiles` stays the UNSYNCED serial tail.** `chezmoi update` prompts interactively on stdout; under `--output-sync` that prompt is buffered → invisible → looks hung. Recursive (`+`) recipe lines are exempt from the parent's output-sync, and the dotfiles child gets no `-O` of its own. Running last also guarantees chezmoi `run_` scripts see a fully-provisioned host (tic from ncurses, pueued unit, …).
  - **`--output-sync=target` is passed explicitly to the fanout child only.** `-O` never appears in parse-time `MAKEFLAGS` (unlike `-j`), so a "set globally unless overridden" guard is dead code — there is no way to detect an explicit `--output-sync=none`. Direct multi-target runs (`make a b c`) interleave unless you pass `-O` yourself.
- **Makefile recipe lines must be tab-indented**, not spaces. Macro bodies use `$$` to defer expansion to rule-fire time — don't switch to single `$` without testing.
- **Wezterm sentinel block.** Auto-generated between `-- HOSTS:START` / `-- HOSTS:END` (column 0) by both manage-hosts scripts. Edit outside the sentinels freely; inside gets clobbered on the next sync. Bash uses `awk`, PowerShell uses a `(?s)` regex — both must produce identical output for the same `hosts.conf`.
- **ccstatusline sentinel block.** Auto-generated between `# CCSTATUSLINE:START` / `# CCSTATUSLINE:END` (column 0) in `chezmoi/.chezmoiignore.tmpl` by `scripts/setup-ccstatusline.sh`. Each opt-out host contributes one line of the form `{{ if eq .chezmoi.hostname "<host>" }}.config/ccstatusline/settings.json{{ end }}` (TARGET path, not the `dot_config/...` source name — `.chezmoiignore` matches target paths). Hand-edits inside the markers get clobbered on any subsequent setup-ccstatusline.sh run that hits options 1, 2-persist, or 3.
- **`versions.mk` ↔ `modify_private_settings.json` dual-edit for `CCSTATUSLINE_VERSION`.** The `ccstatusline@<pin>` literal in the enforced `statusLine.command` of `chezmoi/private_dot_claude/modify_private_settings.json` MUST match `CCSTATUSLINE_VERSION` in `makefile/versions.mk` (no chezmoi-template variable bridges them; `check-invariants.sh` greps this file). Drift means Claude Code's `statusLine` pins a different version than `setup-ccstatusline.sh` invokes interactively.
- **`versions.mk` ↔ `lib/font.sh` ↔ `install-nerd-fonts.ps1` triple-edit for `JETBRAINSMONO_NERD_VERSION`.** Three places must move together when bumping the Nerd Font pin: (1) `JETBRAINSMONO_NERD_VERSION` in `makefile/versions.mk`; (2) the `case "$VERSION" in 3.4.0) EXPECT_SHA='...' ;;` branch in `makefile/lib/font.sh` (SHA256 of `JetBrainsMono.tar.xz` from the matching `SHA-256.txt` upstream); (3) the `$Version` + `$Sha256` literals in `scripts/install-nerd-fonts.ps1` (SHA256 of `JetBrainsMono.zip` — different artifact, different hash). Procedure: bump the version variable; `curl -sL https://github.com/ryanoasis/nerd-fonts/releases/download/v<VER>/SHA-256.txt | grep -E 'JetBrainsMono\.(tar\.xz|zip)$'` for the two new SHAs; substitute both. Drift means Linux and Windows hosts can end up on different font versions across a mid-bump fleet, with subtle icon-rendering differences across host kinds. No chezmoi-template variable currently bridges them.
- **Node.js is dev-only and managed via `node-runtime`.** `makefile/lib/node.sh` extracts `node-v$(NODE_VERSION)-linux-<arch>.tar.xz` from nodejs.org into `$(DEST)/_node-vX.Y.Z/` and symlinks `node`/`npm`/`npx`/`corepack` into `$(DEST)/`. Like `claude-cli`, the `node-runtime` target is bespoke (outside the macros) and only joins `provision`'s deps when `MODE=dev`. `claude-statusline` adds a dev-only dep on it so the npx the script invokes is the chezmoi-managed Linux-native one — never the Windows passthrough that crashes on WSL working dirs.
- **`go-runtime` + `lsp-servers` are dev-only meta-targets; don't unify their install mechanisms.** `go-runtime` (`lib/go.sh`): extracts the official go.dev tarball to `$(DEST)/_go-<ver>/`, sweeps older `_go-*` trees (same pattern as `node.sh`), and symlinks `go`/`gofmt` into `$(DEST)/`. Pinned `GO_VERSION` in `versions.mk`; bespoke target (outside the macros), `$(SUDO)`-wrapped on dev. `lsp-servers` (`lib/lsp.sh`) is intentionally multi-mechanism (every sub-installer is **best-effort, warns and exits 0 on failure** so a single server's outage never aborts `make dev`): (1) **npm** — TypeScript/bash/yaml/json language servers via `npm install --prefix $(DEST)/..` (bins land under `$(DEST)/`); needs `node-runtime` (stamped dep). (2) **lua** — `lua-language-server` TREE install (multi-file, not a single binary; a binary-only `archive.sh` install would break it — this is why it's NOT an `EGET_TOOL`); symlinks the wrapper script. (3) **gopls** — `GOBIN=$(DEST) go install golang.org/x/tools/gopls@<ver>` (requires `go-runtime`; stamped dep). (4) **basedpyright** — `uv tool install basedpyright@<ver>` (user-site, **never sudo**; `uv` installs to `~/.local/share/uv/`). (5) **verify-clangd** — warns if `clangd` is absent; clangd comes from `clang-tools-extra` (dnf/EPEL, see the C/C++ invariant), not a separate download. The three both-scope eget tools (`rust-analyzer`, `marksman`, `taplo`) are normal `EGET_TOOL` entries in `tools.mk` + `versions.mk` — they don't belong in `lsp-servers`. **No dual/triple-edit for the LSP pins** (`LSP_PINS` map in `Makefile` is the single source; `lsp-servers` reads it directly). `lsp-servers` joins `provision` only when `MODE=dev`.
- **Machine-level Claude memory is `chezmoi/private_dot_claude/CLAUDE.md` → `~/.claude/CLAUDE.md`**, dev-only (chezmoi gated via the `.claude` dev/prod block). The `<!-- TOOLS:START -->` / `<!-- TOOLS:END -->` sentinel block is auto-generated by `scripts/gen-tool-memory.sh`, which reads `makefile/versions.mk` + `tools.mk` + `packages.mk` as its single source of truth. **Hand-edits inside the sentinels are clobbered** by the next generator run. `scripts/check-invariants.sh` runs the generator against a temp file and diffs to enforce zero drift in CI. The hook `.claude/hooks/sync-tool-memory.sh` regenerates on every edit to a tool-source makefile (PostToolUse). Add a guidance prose section outside the sentinels; the block structure (categories, commands, versions) is driven entirely by the generator.
- **`workstation-lsp` is a declarative skills-dir plugin; it installs nothing.** Source: `chezmoi/private_dot_claude/skills/workstation-lsp/` (dev-only, under the same `.claude` chezmoi gate). Three files: `dot_claude-plugin/plugin.json` (plugin manifest), `dot_lsp.json` (server registry → `~/.claude/skills/workstation-lsp/.lsp.json`), `SKILL.md` (marker + diagnostics toggle note). Auto-loads by presence once deployed; the enforced `workstation-lsp@skills-dir` entry in `modify_private_settings.json`'s `enabledPlugins` block is belt-and-suspenders. **`.lsp.json` MUST be strict JSON** — the runtime `LSP` loader rejects JSONC `//` comments (all 12 servers fail to load silently). `claude plugin validate` is JSONC-tolerant and will NOT catch this; test with `python3 -m json.tool .lsp.json`. Diagnostics are on by default (the `"diagnostics": false` per-server toggle is documented in `SKILL.md`, not in `.lsp.json`). `check-invariants.sh` runs `claude plugin validate --strict` over the plugin source directory as a soft check. Binaries come from `make lsp-servers MODE=dev`; the plugin merely registers their paths. Verify after `cza` + `/reload-plugins`: `/reload-plugins` reports our **12** servers (13 total on this host — the +1 is the standalone `lua-lsp` plugin), with no "error during load".
- **Docker is dev-only and managed via `docker-engine`.** Bespoke target in `makefile/Makefile` (outside the macros), joining `provision`'s deps only when `MODE=dev`, and skipped on WSL (`IS_WSL=true` → bare-phony skip message; the engine there is Docker Desktop on the Windows host — same gating as `dozzle-service`/`cockpit-service`). Installs Docker CE from Docker's official dnf repo (repo file curl'd straight into `/etc/yum.repos.d/` to avoid a dnf-plugins-core dependency; `linux/rhel` on RHEL proper, `linux/centos` on Alma/Rocky/CentOS), enables the service, and adds `$USER` to the `docker` group (takes effect on next login — needed for sudo-less lazydocker/dive/ctop). Fast-path: a pre-existing `docker` on PATH (manual install or podman shim) skips the repo+package steps — never fight an existing engine; the enable/group steps are guarded for that case (unit or group may not exist). NO `versions.mk` pin and no version in the stamp — Docker CE versions come from dnf, same precedent as cockpit. `dozzle-service`'s stamp order-only-depends on `$(STAMP)/docker-engine.done` (the stamp FILE, not the phony — same rule as the EGET_TOOL stamp-on-stamp invariant) so `make -j` can't fire dozzle before the engine exists; dozzle's `command -v docker` sanity check stays as a safety net for direct invocation.
- **Helix runtime discovery on dev needs `HELIX_RUNTIME` exported from the rc.** `make` installs the Helix runtime to `$(HELIX_RUNTIME_DEST)/runtime` — `/usr/local/lib/helix/runtime` on dev, `~/.config/helix/runtime` on prod (`scope.mk`). But Helix's only built-in runtime search paths are `~/.config/helix/runtime` and `<bin>/runtime` (verify with `hx --health`), so the **dev** location is NOT auto-discovered. `chezmoi/dot_zshrc.tmpl` + `chezmoi/dot_bashrc.tmpl` (parity pair) export `HELIX_RUNTIME="/usr/local/lib/helix/runtime"`, gated to `dev_machine` via `{{ if and (hasKey . "group") (eq .group "dev_machine") }}`. Without it Helix finds NO runtime and silently falls back to its built-in (purple) default theme, ignoring `theme =` in `config.toml` — the failure logs `failed to load theme … file not found` in `~/.cache/helix/helix.log` (this is exactly how `tokyo_night` then `catppuccin_mocha` silently never loaded). prod_machine needs no export — its runtime already lands in a default search path. The rc literal MUST stay in sync with `HELIX_RUNTIME_DEST` in `makefile/scope.mk`; no chezmoi-template variable bridges them (dual-edit, like the `CCSTATUSLINE_VERSION` / Nerd-Font pins). Verify per dev host after `cza`: `hx --health` lists `/usr/local/lib/helix/runtime` with no "does not exist" warning for it, and a `hx <file>` launch adds no `failed to load theme` line to the log.
- **The C/C++ toolbelt deliberately spans three install mechanisms; don't "unify" them.** (1) The **bulk is dnf, dev-only, best-effort** — `gcc-c++ clang clang-tools-extra llvm lldb valgrind cppcheck ltrace libasan libubsan libtsan cmake meson ninja-build heaptrack bear ccache` live in `LINUX_OPTIONAL_PACKAGES` (`makefile/packages.mk`), not the core list, because several come from EPEL/CRB rather than BaseOS (`clang-tools-extra` → clangd+clang-tidy+clang-format, `cppcheck`, `meson`, `ninja-build`, `heaptrack`, `bear`, `ccache`). `bear` is the compile-DB generator (`bear -- make` → `compile_commands.json`) that makes clangd usable on non-CMake/meson projects; `ccache` is a compiler cache. **`packages-epel` auto-enables EPEL + CRB** on RHEL-family hosts (best-effort, idempotent: ensures `dnf-plugins-core`, then `dnf config-manager --set-enabled` across `crb` [EL9] / `powertools` [EL8] / `codeready-builder-*` [subscribed RHEL]). Its RHEL-family detection **sources `/etc/os-release` and matches `$ID`/`$ID_LIKE`** — do NOT revert to a loose `grep -i fedora /etc/os-release`: AlmaLinux's os-release carries `ID_LIKE="rhel centos fedora"` + `LOGO="fedora-logo-icon"`, so the substring grep matched Alma as "Fedora" and skipped EPEL/CRB on the exact hosts that need it (skip only true `$ID = fedora`, then require an EL marker rhel/centos/almalinux/rocky) — this is required, NOT optional polish: EPEL on EL9 fails to resolve many packages without CRB, and `meson`/`ninja-build` live directly in CRB while `heaptrack`/`bear` pull CRB-resident deps. Discovered the hard way — a fresh AlmaLinux 9 host had EPEL on but CRB off, so exactly those four silently hit the skip path. The per-package `|| true` fast-path in `packages-optional` is the final fail-soft: even if CRB can't be enabled (e.g. no `config-manager`, or a future EL10/dnf5 host whose syntax is `config-manager setopt <repo>.enabled=1`), the missing ones skip cleanly instead of aborting the build. `gcc`/`make` are already core; `gdb`/`perf`/`strace` were already in the optional list — NOT re-added (but `gdb-gdbserver` — the separate EL subpackage providing the remote-debug stub `gdbserver`, since the `gdb` package doesn't bundle it — IS in the list, paired with `gdb` in the general dev-tools group, NOT the C/C++ block; verified on AlmaLinux 9: `dnf provides */bin/gdbserver` → `gdb-gdbserver`). The sanitizers (ASan/UBSan/TSan) are compiler features, not packages — `libasan`/`libubsan`/`libtsan` are only the **gcc** runtime `.so`s the `-fsanitize=` link step needs (clang ships its own compiler-rt). GOTCHA: the RHEL `ninja-build` package installs the binary as `ninja-build`, not `ninja`. (2) **`nnd`** (modern from-scratch TUI debugger) is a both-scopes raw binary installed via `direct.sh`, NOT `EGET_TOOL` — its release assets are bare `nnd` + `nnd-dbgo` with no os/arch tokens, so eget can't auto-disambiguate (same reason jq/shfmt/witr use `direct.sh`); pinned `NND_VERSION`, v-prefixed tag, `UPDATE_SPECS` hand-registered. (3) **`pwndbg`** and **`vcpkg`** are dev-only bespoke Makefile targets (outside the macros) joining `provision`'s deps only when `MODE=dev`, each `$(SUDO)`-wrapped (they write under `/usr/local` on dev) with a version-baked stamp; `DOCTOR_ROWS`/`UPDATE_SPECS`/`list`/`help` hand-registered. `lib/pwndbg.sh` installs the self-contained **portable tarball** (bundled Python) and symlinks a standalone `pwndbg` command — it must NOT touch `~/.gdbinit`. `lib/vcpkg.sh` git-clones+bootstraps `microsoft/vcpkg` into `VCPKG_ROOT_DIR` (= `$VCPKG_ROOT`) and symlinks the binary into `$(DEST)`; **`VCPKG_ROOT_DIR` in `makefile/Makefile` is a dual-edit with the dev-gated `VCPKG_ROOT` literal in `dot_zshrc.tmpl` + `dot_bashrc.tmpl`** (both verified by `check-invariants.sh`, like the Helix-runtime dual-edit). Neither `pwndbg`/`vcpkg` carries a WSL skip — both are useful in a WSL dev guest (unlike the host-management services). **GEF** is the plain-`gdb` front-end (the counterpart to the standalone `pwndbg`): vendored `chezmoi/dot_config/gdb/gef.py` **pinned to release `2024.06`** (sha256 in its `.vendor` sidecar, no `versions.mk` entry) sourced by absolute path from the tracked `chezmoi/dot_gdbinit.tmpl`. **The 2024.06 pin is load-bearing, not arbitrary:** it is the LAST GEF release supporting Python 3.6–3.9 (`PYTHON_MIN_VERSION=(3,6)`, no `match` statements); GEF `2025.01`+ requires Python 3.10 and uses 3.10 `match`/`case` syntax. AlmaLinux 9's gdb embeds **Python 3.9**, so a newer GEF fails to even *parse* — `gdb` prints a `Python Exception SyntaxError` on every launch and the GEF commands never register (verified: current GEF errors at `gef.py:12979`, 2024.06 loads with "GEF for linux ready ... Python engine 3.9"). DO NOT bump past 2024.06 while any managed host runs EL9/Python-3.9; the `.vendor` sidecar carries the constraint + the `gdb -nx -batch -ex 'source gef.py' -ex 'gef help'` verify recipe. (`gef-legacy` is NOT a fallback — it targets GDB+Python2.) pwndbg sidesteps this entirely because its portable build bundles its own newer Python. Both are **dev-only + Linux-only**, gated in `.chezmoiignore.tmpl` as the TARGET paths `.gdbinit` + `.config/gdb` in BOTH the dev/prod block and the Windows block (source-state names would silently ignore nothing — verify with `chezmoi ignored`). GEF needs a gdb built with Python 3 (RHEL 9 qualifies). Net UX: `gdb` → GEF, `pwndbg` → pwndbg, `gdb -nx` → vanilla, `nnd` → the from-scratch debugger; the two front-ends never collide because pwndbg is a separate command, not a `~/.gdbinit` hook. The single most actionable usage rule (from the deep-research that drove this): prefer the compiler sanitizers (`-fsanitize=`, ~2–4× overhead) for everyday memory/threading checks over Valgrind (~20–50×), keeping Valgrind for unmodified binaries and the uninitialized-read detection ASan misses.
- **Claude Code `~/.claude/settings.json` is a chezmoi merge-on-apply, not a whole-file template.** The source `chezmoi/private_dot_claude/modify_private_settings.json` is a `chezmoi:modify-template` (no `.tmpl` extension) that deep-merges seed defaults → the live file (`.chezmoi.stdin`) → enforced keys (later wins) via `mergeOverwrite … | toPrettyJson`. **Enforced** (forced every apply): `statusLine`, `hooks`, `enabledPlugins`, `skipAutoPermissionPrompt`, `skipWorkflowUsageWarning`, `remoteControlAtStartup`, `agentPushNotifEnabled`, `inputNeededNotifEnabled`. **Seed** (set only when absent, so Claude Code's in-app changes persist): `model`, `effortLevel`, `theme`, `editorMode`, `tui`, `verbose`. `option_set_global` in `setup-ccstatusline.sh` still must NOT write settings.json (the enforced `statusLine` overrides a stray statusLine-only block anyway). Cross-host changes to an enforced key = edit the enforced block, commit, push.
- **chezmoi-level dev/prod gating via the `group` data field.** `chezmoi/.chezmoi.toml.tmpl` `[data]` block has a `group` field populated from the `WORKSTATION_GROUP` env var (bootstrap.sh sets it from the `--dev`/`--prod` flag → `GROUP_NAME="${MACHINE_TYPE}_machine"`), falling back to `promptStringOnce` for stand-alone `chezmoi init` runs. `.chezmoiignore.tmpl` consumes `.group` to ignore dev-only paths on prod_machine hosts — listed as their TARGET paths `.claude` + `.config/ccstatusline` (NOT the source names `private_dot_claude`/`dot_config/ccstatusline`; `.chezmoiignore` matches the destination path, so the source-name form silently ignores nothing — this was broken until the target-path fix). A `hasKey` guard makes the gate no-op on legacy chezmoi.toml files (pre-`group`-field), so re-running `chezmoi init` (or `bootstrap.sh --dev|--prod`) on existing hosts is the migration step. When you add a new chezmoi-tracked path that should be dev-only, list it inside the existing `{{ if and (hasKey . "group") (ne .group "dev_machine") }}` block as a target path.
- **Three-piece WSL invariant** in `chezmoi/dot_config/wezterm/` (`wsl.lua` for piece 1, `actions.lua` for piece 2) + `chezmoi/dot_zshrc.tmpl` (mirrored in `chezmoi/dot_bashrc.tmpl` for bash-fallback parity):
  1. `default_cwd='~'` loop over `wezterm.default_wsl_domains()` — first tab opens in `/home/<user>`.
  2. `smart_new_tab` callback on `CTRL+SHIFT+T` — for WSL panes without tracked cwd, spawns via `DomainName` (NOT `SpawnCommandInNewTab { cwd='~' }`, which tilde-expands on Windows and lands you in `/mnt/c/Users/<user>`).
  3. OSC 7 emission via `__wezterm_osc7` — registered as a zsh `precmd` hook (`add-zsh-hook -Uz precmd __wezterm_osc7`) in `dot_zshrc.tmpl` and as a `PROMPT_COMMAND` entry in `dot_bashrc.tmpl`. Lets `CTRL+SHIFT+T` inherit current pane's cwd post-bootstrap. Keep both implementations in sync — anyone who invokes `bash` interactively still needs the cwd-tracking.
  Each piece covers a distinct failure mode. Keep all three.
- **`</dev/tty` redirect in chezmoi init.** Load-bearing under `curl | bash` — script stdin is the pipe, so `chezmoi`'s `promptStringOnce` reads EOF without the redirect. Make recipes can't do this either, which is why `dotfiles.mk` only runs `chezmoi update`, never `init`. First-run `init` is `bootstrap.sh`'s job.
- **WSL detection is centralized in `is_wsl()`** in `bootstrap.sh` (checks `$WSL_DISTRO_NAME` + `/proc/version`). If it ever needs to distinguish WSL 1 / WSL 2, extend the helper — don't introduce parallel detection.
- **chezmoi source dir is `chezmoi/`**, not the repo root. `.chezmoiroot` (one-line file at root containing `chezmoi`) redirects chezmoi there. Without it, `dot_zshrc.tmpl` would map to `~/chezmoi/.zshrc`. Don't delete or edit `.chezmoiroot`.
- **chezmoi naming conventions** (relative to `chezmoi/`): `dot_X` → `~/.X`; `dot_config/X` → `~/.config/X`; `private_X` enforces 0600 files / 0700 dirs (required for `~/.ssh/` since OpenSSH refuses world-readable config); `.tmpl` triggers Go templates; `AppData/`, `Documents/` are Windows-only (gated via `.chezmoiignore.tmpl`).
- **`.chezmoiscripts/` are NOT covered by `.chezmoiignore`.** OS-gate via the script body's `{{ if eq .chezmoi.os "linux" }}…{{ end }}` (empty render → chezmoi skips zero-byte scripts), not via ignore patterns.
- **Only two valid host groups**: `dev_machine` and `prod_machine`. Both manage-hosts scripts reject anything else. The group drives `MODE` derivation in `update-hosts.sh`. A third group requires extending `scope.mk` AND `update-hosts.sh`'s case branch.
- **`configs/` is sudo-installed to `/etc/`, NOT chezmoi-managed.** Files under `configs/<tool>/` are deployed by paired `<tool>-service` make targets (see `makefile/Makefile`) via `sudo install -m 0644 ../configs/<tool>/<file> /etc/<dest>`. Chezmoi continues to own `$HOME` exclusively — don't try to migrate `configs/` files under `chezmoi/`. The pattern exists because chezmoi has no facility for system-scope (`/etc/`) destinations. Currently used by `dozzle-service` (`configs/dozzle/dozzle.service` + `.env`) and `cockpit-service` (`configs/cockpit/cockpit.conf`). For the Dozzle env file specifically, the recipe sed-substitutes `@DOZZLE_VERSION@` from `$(DOZZLE_VERSION)` so `versions.mk` remains the single source of truth for the Docker image tag. To add a new system service, create a `configs/<tool>/` directory and a matching `<tool>-service` bespoke rule in `makefile/Makefile`.
- **`config.term='wezterm'` ↔ wezterm-terminfo install chain.** `chezmoi/dot_config/wezterm/appearance.lua` sets `config.term = 'wezterm'` so every spawned PTY (local WSL, SSH-domain default_prog, manual `ssh`) gets `TERM=wezterm`. That entry MUST exist in `~/.terminfo/w/wezterm` on every host where a TUI eventually runs, or apps error with `Error opening terminal: wezterm` (and `tput` prints `unknown terminal "wezterm"` at shell startup). The entry is installed by `chezmoi/.chezmoiscripts/run_install-wezterm-terminfo.sh.tmpl`, which runs on **every** `chezmoi apply` and tic-compiles `chezmoi/dot_local/share/wezterm/wezterm.terminfo` (vendored upstream). It is a **self-healing `run_` script, NOT `run_onchange_`**: it re-tic's whenever ncurses can't resolve `wezterm` (entry missing) OR the source changed since the last compile (the source sha256 is recorded in a `~/.terminfo/.wezterm.srchash` stamp; a bump invalidates it — mirroring the old "reinstall on bump" behaviour), and no-ops cheaply (one `infocmp` + one stamp read) otherwise. **Do not revert it to `run_onchange_`:** that was the original design and it caused a real regression — `run_onchange_` fires only when the script text changes and records the soft-fail skip (`tic` absent because ncurses isn't installed yet) as a *successful* run, so any apply that beats ncurses onto PATH (a manual `cza` during setup, a parallel-make race, a partial run) permanently disabled the compile until the source bumped, and `cza`/`czu` could not self-heal it. The `tic` binary comes from the `ncurses` package in `LINUX_PACKAGES` (`makefile/packages.mk`), so `make provision MODE=dev` installs it before the canonical first apply; the self-heal makes correctness independent of that ordering. Four artifacts move together (`ncurses` package, vendored .terminfo source, the `run_` install script, `config.term` flip) — flipping `config.term` without the other three breaks TUIs on stale hosts. Verify per host: `infocmp wezterm` exits 0.
- **Install-time binary verification gate.** `EGET_TOOL`/`TOOL` `&&`-chain `lib/verify-binary.sh '$(DEST)/<name>'` onto the install command (via the `verify_cmd` make function), so a binary that cannot run on this host fails the install **before** the stamp is written — converting silent "installed but won't run" successes (the fastfetch musl-loader and wrong-file breakages) into loud, retryable stops.
  - **Non-executing**: ELF magic + `e_machine` arch, then `ldd` (static → PASS; any `not found` → FAIL), then glibc-floor via `objdump`/`readelf`.
  - **Static binaries MUST pass** (most `--asset musl` tools are static). Do not "tighten" the check to fail non-dynamic binaries — it would false-fail ~33 eget tools.
  - **Degrades**: no `objdump`/`readelf` (minimal prod) → skip the glibc-floor sub-check with a note; keep ELF+arch+ldd.
  - **Verify is automatic for `EGET_TOOL`** (override the binary name via the 6th arg — bottom→`btm`; skip with `-`) and **opt-in for `TOOL`** (4th arg = the ELF binary's basename). Script "tools" (nb, sysz, ssh-copy-id) and non-binary helpers (helix.sh, pipe.sh) are deliberately NOT verified.
  - Verify with: `make <tool> MODE=prod DEST=/tmp/t STAMP=/tmp/s` — a passing install prints `✓ verify <tool>` and writes the stamp.
- **SSH connection multiplexing is gated out on Windows.** `chezmoi/private_dot_ssh/private_config.tmpl` (cross-platform; deploys to `~/.ssh/config` on both OSes) keeps its `ControlMaster auto` / `ControlPersist 60s` / `ControlPath ~/.ssh/cm-%r@%h:%p` block under `Host *` inside a `{{ if ne .chezmoi.os "windows" }}…{{ end }}` gate. Windows OpenSSH can't multiplex — the muxed connection runs over a handle that isn't a Winsock socket, so `getsockname()` returns `WSAENOTSOCK` (`getsockname failed: Not a socket`) and the session hangs until `ServerAlive` trips (`Timeout, server <host> not responding.`). This breaks **every** Windows ssh, including git's SSH transport to GitHub — a chicken-and-egg, since pulling the fix itself needs ssh: break the loop with a one-shot `GIT_SSH_COMMAND="ssh -o ControlMaster=no -o ControlPath=none" git pull`, then `chezmoi apply` strips the block from the deployed config for good. The gate deliberately keeps multiplexing on Linux/macOS (load-bearing for `scripts/update-hosts.sh` bulk runs + interactive `ssh`/`scp`/`rsync` reuse). Don't move `ControlMaster` outside the gate, and don't drop the `.tmpl` suffix. Per-host opt-out anywhere (incl. a stale Windows host pre-`apply`): `ControlPath none` in `~/.ssh/config.local` (Included first, first-match-wins). Verify after apply: `ssh <managed-host> hostname` connects with no `-o` overrides.
