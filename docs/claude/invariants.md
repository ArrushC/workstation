# Load-bearing invariants

> Claude-internal reference, split out of `CLAUDE.md` to keep it lean. CLAUDE.md
> carries a terse index of these rule headlines; this file holds the full *why*
> and failure modes. README documents the *what*; these are the *why*. Each one
> exists because the opposite was tried at some point and broke.

- **`bootstrap.sh` is a thin seed.** No `*_VERSION` constants, no install logic — with one deliberate exception: `MISE_VERSION`/`MISE_SHA256`, the pinned, sha256-verified `mise` binary it installs into `~/.local/bin` before handing off. Everything else lives in `config*.toml` (`[bootstrap.*]`/`[dotfiles]` tables) or `tasks/`. Its run_bootstrap() does, in order: preflight (curl/git/tar/ip only — no `make` any more) → clone/relocate the repo to `~/.config/mise` → install pinned mise → self-register the host in `hosts.conf` → compute `MISE_ENV` from `--dev`/`--prod` via `scripts/lib/mise-env.sh` → `systemctl --user set-environment MISE_ENV=…` (dev only, live user manager) → `ensure_config_local()` (write/migrate `config.local.toml`) → `scripts/lib/mise-install.sh` (tools) → `mise bootstrap --yes` (packages/files/services/compose/repos/**dotfiles** [`--force-dotfiles` on the first run only]/tools-gate/the `bootstrap` task) → `set_default_shell` → push `hosts.conf`. There is no `scope.mk` any more to disagree with — `MISE_ENV` is the single source of scope, computed fresh by `bootstrap.sh` every run.
- **Tool pins live in `config.toml`/`config.linux.toml`/`config.dev.toml` + the three lock files (`mise.lock`, `mise.linux.lock`, `mise.dev.lock`) + `locks/**`.** This repo root IS mise's global config dir (Linux: `~/.config/mise`; Windows: `%USERPROFILE%\.config\mise`); the lock files (one per config file, mise's own mechanism) replace the old stamp-filename-baked-version trick — a pin bump plus a re-lock is what triggers mise to reinstall, not a Make stamp. Never hand-edit `mise*.lock` or anything under `locks/**`; regenerate with `mise lock --global` from outside the checkout via the `XDG_CONFIG_HOME` symlink form, then normalize the sidecar paths (see `docs/claude/file-care.md`). **The five pins Make used to own directly** (renamed and moved, PR2) landed in `config.toml`'s `[vars]` table: `python_version` (was `PYTHON_VERSION`), `nerd_font_version` (was `JETBRAINSMONO_NERD_VERSION`), `dozzle_version` (was `DOZZLE_VERSION`), `vcpkg_version` (was `VCPKG_VERSION`), `zjstatus_zellij_floor` (was `ZJSTATUS_ZELLIJ_FLOOR`) — the sixth, `CLAUDE_VERSION`, is gone entirely: it was always `:= latest` (rolling, no real pin), and Claude Code's official installer self-updates on its own, so there is nothing left to track. `dozzle_version` itself is gone too, as of 2026-09-22 — Dozzle provisioning was removed entirely (see the `configs/` bullet below and `CLAUDE_CHANGELOG.md`), so the remaining four are `python_version`, `nerd_font_version`, `vcpkg_version`, `zjstatus_zellij_floor`. Global mise tasks read `[vars]` via `#MISE env={NAME="{{ vars.name }}"}` headers (Tera rendering, spec-verified) — see e.g. `tasks/fonts`'s `NERD_FONT_VERSION`. Never re-introduce per-tool versions in `bootstrap.sh`, scripts, or new playbooks.
- **`MISE_ENV` picks which config files load, and `[bootstrap.*]`/`[dotfiles]` tables merge by union across every loaded file (verified).** Tokens: `config.toml` (always) · `config.linux.toml` (`linux`) · `config.dev.toml` (`dev`) · `config.host.toml` (`host` — dnf packages + the EPEL/CRB pre-packages hook, PLUS the Linux-dev-only dotfiles: `~/.gdbinit`, `~/.config/gdb`, `~/.config/herdr/config.toml`) · `config.native.toml` (`native` — NFS client only, as of 2026-09-22; see the `configs/` bullet below) · `config.wsl.toml` (`wsl` — `/etc/wsl.conf`) · `config.windows.toml` (`windows` — the 13 Windows-only dotfiles) · `config.local.toml` (always, git-ignored). Token sets, from `scripts/lib/mise-env.sh` (the single source): prod Linux `linux`; dev WSL `linux,dev,host,wsl`; dev native `linux,dev,host,native`; Windows `windows,dev`. **Prod hosts load NO host state** — `config.host.toml`/`config.native.toml`/`config.wsl.toml` carry every sudo-requiring table; `config.toml`/`config.linux.toml`/`config.dev.toml` must never gain one. A dnf package, an `/etc` file, a service, or a dotfile can be declared in whichever loaded file its intended `MISE_ENV` token gates — mise unions the tables at load time, so don't duplicate a declaration across files "to be safe"; that would just double-declare it once both files happen to load on the same host.
- **dnf packages are all-or-nothing.** mise runs ONE `sudo dnf install -y <every missing name>` per `[bootstrap.packages]` table — a single unresolvable name fails the WHOLE batch, unlike the old Make-era `packages-optional`'s per-package `|| true` fail-soft. Every name in `config.host.toml`/`config.native.toml` is therefore EL9-verified (a dedicated spike against AlmaLinux 9.8, 2026-09-17, ran `dnf repoquery` on the full Make-era package list) — never add a name the spike marked NOT FOUND or virtual. Three names dropped in the process: `fswatch` and `entr` (neither packaged for EL9), `cockpit-networkmanager` (a virtual provide of `cockpit-system` — `rpm -q` never resolves a virtual provide, so the old Make code silently "installed" a package that was never really there). `shellcheck` becomes `ShellCheck` — EPEL capitalises it. `make` itself STAYS (Ruling 5): it's a C-toolchain dependency now (`bear -- make`, autotools projects), not this repo's orchestrator any more.
- **No `[bootstrap.linux.firewall]` table, anywhere in this repo (Ruling 1) — this is the single most consequential deviation from the original spec, discovered by the 2026-09-17 mise 2026.9.9 spike.** Any firewall rule, in any loaded config file, makes mise re-exec itself with sudo for that table — including during a *read-only* `mise bootstrap plan` or `mise bootstrap status` call. On a host with no cached sudo credential and no TTY (a CI job, a cron-driven health check, an SSH one-liner), that re-exec hangs or fails outright with `sudo: a password is required`. The spec's original design had Cockpit's firewall port opened via `[bootstrap.linux.firewall]`; the spike caught that `mise run health` — meant to be safe to run from anywhere, any time, no sudo — would have broken on every single host the moment that table existed. Fix (historical — Cockpit provisioning, including `tasks/native-post-packages`, was removed entirely 2026-09-22; see the `configs/` bullet below and `CLAUDE_CHANGELOG.md`): Cockpit's port stayed the pre-existing `firewall-cmd` snippet, folded into the `native-post-packages` post-packages hook task, which only ran during a real `mise bootstrap --yes`, never during `plan`/`status` — the general principle (no `[bootstrap.linux.firewall]` table, ever) still stands for any future `[bootstrap.*]` table. If you ever see a `plan`/`status` call hang on a sudo prompt, `grep -rn bootstrap.linux.firewall config*.toml` is the first thing to check.
- **No `[bootstrap.user] login_shell` anywhere (Ruling 2).** It shells out to `chsh`, which two things break: (1) EL9 *minimal* images don't ship `util-linux-user` (the package providing `chsh`) by default, so the call fails outright on a fresh minimal install; (2) `chsh` itself prompts for the *user's* password interactively — sudo can't paper over it — which is exactly the kind of hang `mise bootstrap --yes` (a non-interactive, unattended flag) is supposed to prevent. `bootstrap.sh`'s existing `set_default_shell()` stays the only mechanism: `sudo usermod -s "$(command -v zsh)" "$USER"` on dev (works even on minimal images — `usermod` ships in `shadow-utils`, always present), a printed manual-`chsh` hint on prod (no sudo there, so it can only ask).
- **Hooks are always `mise run <task>` — never a literal shell one-liner — with exactly one pinned exception.** Hook strings are opaque shell to mise: it does not verify cwd, `PATH`, or `$HOME` expansion the way it does for `[bootstrap.packages]`/`[bootstrap.files]`. `mise run <task>` sidesteps all of that — it finds global tasks from any cwd and puts every mise-installed tool on `PATH` before the task body runs. Every hook name (`pre-packages`, `post-packages`, `post-tools`, `post-dotfiles`, …) is defined in **exactly one** config file — the merge semantics for a *duplicate* hook name across two loaded files are unverified, so treat a collision as a bug to fix, not a feature to rely on. **Tasks live in `$HOME/.config/mise/tasks`** (i.e. this checkout, since the checkout IS `$HOME/.config/mise`) and are discovered from there — **`MISE_CONFIG_DIR` does NOT redirect global task discovery**; mise always looks under the real home for global tasks, so a test harness or CI job that points `MISE_CONFIG_DIR` elsewhere (to avoid touching a real `~/.config/mise`) still picks up THIS repo's tasks if it happens to be checked out at the real path — verified during the PR2 spike, and the reason `lint.yml`'s sandboxed test runs don't fully isolate task discovery (`scripts/check-templates.sh`'s header documents and works around the matching fallback for `mise dot`/`mise bootstrap` config DISCOVERY, a related but separate gap). Task names must not collide with a built-in mise subcommand if you want the short `mise <name>` form — `fmt` collides (`mise fmt` is mise's own code-formatter subcommand), so ours is always invoked as `mise run fmt`, never the shorthand. **`post-dotfiles`** (`config.linux.toml`) is the ONE deliberate exception — a pinned, verified-safe literal `chmod` one-liner, not a task reference, because it must run unconditionally on every apply and must never be skippable by a missing/broken task file; see the dotfiles-hooks entry below for the full reasoning.
- **`[bootstrap.repos]` does a plain, full-depth `git clone` and never pulls on re-run — this is why `vcpkg` stays a task, not a repo entry (Ruling 3).** Verified against mise 2026.9.9: a `[bootstrap.repos."<path>"]` table clones once and then leaves the checkout alone on every subsequent `mise bootstrap` — there is no shallow-clone option and no "reconcile to a newer tag" behavior. The repo declares NO `[bootstrap.repos]` entry at all: the cheat-community sheets were one until the whole-branch review showed the repos phase runs BEFORE tools, services and the `bootstrap` task, so an unreachable clone URL aborted the entire run — they are a soft-failing step in `tasks/bootstrap` instead. It is NOT fine for vcpkg: the existing `scripts/lib/vcpkg.sh` logic needs a `--depth 1` shallow clone (the full `microsoft/vcpkg` history is enormous) AND a tag-reconcile step on every re-run (so bumping `vcpkg_version` in `[vars]` actually moves the checkout to the new tag, not just clones-once-and-forgets). Neither behavior exists in mise's repo primitive, so `tasks/vcpkg` wraps the old shell logic directly instead of trying to force it through `[bootstrap.repos]`.
- **pueued's `MISE_ENV` comes from the user manager, never from the unit itself (Ruling 6) — this one broke on first attempt.** `config.linux.toml`'s `[bootstrap.services.pueued]` table has mise generate and enable `~/.config/systemd/user/dev.mise.pueued.service`; inspect a live host's unit (`cat ~/.config/systemd/user/dev.mise.pueued.service`) and there is deliberately **no** `Environment=MISE_ENV=...` line in it — the temptation is to add one, and the first cut of this migration did exactly that, then noticed the unit is *generated from static TOML*, so a hard-coded value would be wrong on every host but the one it was written against (wsl vs native vs prod each want a different `MISE_ENV`). Without ANY `MISE_ENV`, systemd user units start with essentially no shell environment at all, so the unit's `ExecStart=%h/.local/share/mise/shims/pueued -v` shim can't resolve which config files declared `pueued` and fails to start. The actual fix is two mechanisms, both required: (1) `~/.config/environment.d/10-mise.conf` (a `[dotfiles]` `template` entry, `dotfiles/config/environment.d/10-mise.conf.tera`) — systemd's user manager imports every `~/.config/environment.d/*.conf` file, but only **at manager start or re-exec**, not per-unit-start, so this only helps a *future* login; (2) `bootstrap.sh`'s `systemctl --user set-environment MISE_ENV=…` — sets it on the *currently running* user manager immediately, covering the login that's doing the bootstrapping right now. Task 1 of the PR2 plan proved the generated unit against a live `dev.mise.pueued.service active` before anything else was allowed to depend on it; if you ever see `pueued` fail to start with a PATH/shim-resolution error, check both halves of this chain before touching the unit generation itself.
- **ccstatusline per-host opt-out sentinel.** Auto-generated inside a `# CCSTATUSLINE-OPTOUT:START` / `# CCSTATUSLINE-OPTOUT:END` block that `scripts/setup-ccstatusline.sh` writes into `config.local.toml`'s own `[dotfiles]` table (git-ignored, per-host). Each opt-out host's entry repeats `"~/.config/ccstatusline/settings.json" = { enabled = false, mode = "copy" }` (matching the base entry's own `mode = "copy"` in `config.dev.toml`) — **both keys are required** (ruling 2): `enabled = false` alone is silently ignored by mise, because there is no `state = "absent"` key the way chezmoi's `.chezmoiignore` used to provide, so the override must repeat `mode` for mise to even recognize it as overriding the inherited entry. Hand-edits inside the markers get clobbered on any subsequent `setup-ccstatusline.sh` run that hits options 1, 2-persist, or 3.
- **The `CCSTATUSLINE_VERSION` dual-edit is gone.** ccstatusline is a plain `npm:ccstatusline` mise pin in `config.dev.toml` now; the enforced `statusLine.command` in `dotfiles/claude/settings.enforced.json` is the bare command `ccstatusline` (no version literal), so there is nothing left to drift against — mise's own pin is the only version that matters.
- **`config.toml`'s `[vars] nerd_font_version` ↔ `scripts/lib/font.sh` ↔ `install-nerd-fonts.ps1` triple-edit.** Three places must move together when bumping the Nerd Font pin: (1) `nerd_font_version` in `config.toml`'s `[vars]` table (was `JETBRAINSMONO_NERD_VERSION` in `makefile/versions.mk` pre-PR2); (2) the `case "$VERSION" in 3.4.0) EXPECT_SHA='...' ;;` branch in `scripts/lib/font.sh` (moved from `makefile/lib/` — SHA256 of `JetBrainsMono.tar.xz` from the matching `SHA-256.txt` upstream); (3) the `$Version` + `$Sha256` literals in `scripts/install-nerd-fonts.ps1` (SHA256 of `JetBrainsMono.zip` — different artifact, different hash). Procedure: bump the `[vars]` entry; `curl -sL https://github.com/ryanoasis/nerd-fonts/releases/download/v<VER>/SHA-256.txt | grep -E 'JetBrainsMono\.(tar\.xz|zip)$'` for the two new SHAs; substitute both. Drift means Linux and Windows hosts can end up on different font versions across a mid-bump fleet, with subtle icon-rendering differences across host kinds. `tasks/fonts` reads the pin via `#MISE env={NERD_FONT_VERSION="{{ vars.nerd_font_version }}"}`.
- **Tools are mise-managed (BOTH scopes, USER-LEVEL — never sudo except the dnf batch itself).** This is PR1's Make→mise migration, now completed for host state by PR2 — **every** tool in the toolbelt is a mise pin. Declarations: `config.toml` (cross-platform: `uv`, `python`), `config.linux.toml` (the Linux toolbelt, both scopes — aqua-registry short names preferred; `github:`/`http:` backends only for the tools the registry gets wrong, e.g. a glibc floor EL9 can't meet), and `config.dev.toml` (dev tools on both OSes; Linux-only dev tools carry `os = ["linux"]` so mise never tries to install them on Windows). **This repo root IS mise's global config dir** (Linux `~/.config/mise`, Windows `%USERPROFILE%\.config\mise`) — there is no separate `conf.d`, nothing generated or copied for mise's tool declarations; mise reads `config*.toml` directly off the checkout. `MISE_ENV` (computed by `scripts/lib/mise-env.sh <dev|prod>`, exported by the rc files / a Windows User var / `~/.config/environment.d/10-mise.conf` for systemd user units, plus `bootstrap.sh`'s `systemctl --user set-environment MISE_ENV=…` for the live user manager this login — see the pueued-chain entry above for why the unit itself carries no `Environment=` line) picks which files load: `linux` (prod) · `linux,dev,host,wsl` · `linux,dev,host,native` · `windows,dev`. **Install order (Ruling 7):** `bootstrap.sh` runs `scripts/lib/mise-install.sh` (`mise install`, force-reinstalling `node` only when its declaration changed while it was already installed — tracked via a cksum marker under `~/.local/state/workstation/`, so a changed npm-postinstall string re-runs the language-server install without forcing a reinstall on every unrelated pin bump — then `mise prune` + `mise reshim`) BEFORE `mise bootstrap --yes`, because that marker logic has no mise-native equivalent; `mise bootstrap`'s own tools phase is then a no-op the second time. `config.linux.toml`'s `post-tools` hook (`mise run verify-tools`) runs right after either path completes (see the verify-gate entry below), and the `bootstrap` task (`mise bootstrap`'s final `task` phase, depending on `python-env`/`fonts`/`vcpkg`) runs `tasks/migrate-legacy` (one-time sweep of pre-mise binaries) plus the zjstatus-into-zellij-data-dir copy, the Claude Code + plugin install, and `scripts/lib/claude-settings-merge.sh`. `python` **IS declared** in `config.toml` (a three-way pin: `[vars] python_version` == `tools.python` == `$PythonEnvVersion` in `bootstrap.ps1`, asserted equal by `check-invariants.sh`) — it exists because the dependency-locked `pypi:`/`pipx:` tools (`basedpyright`, `glances`, `asciinema`, `harlequin`) run `uv sync --frozen --python <mise python>` to produce a lockfile, and without a declared interpreter mise falls back to the system 3.9, which refuses those installs. It shadows `python3` only in mise-activated shells; the system interpreter stays untouched at `/usr/bin/python3` (`python-env`'s and mise's own `python` are two *different* installs sharing a version by coincidence of the three-way pin, not the same interpreter — see the C/C++ toolbelt entry below for the same EL9-Python-3.9-floor story capping the GEF vendoring). Non-interactive shells see the tools through `~/.local/share/mise/shims` (`dotfiles/zshenv.tera`; `dotfiles/bashrc.tera` ABOVE its interactive guard — parity pair), interactive ones through `mise activate`. **Windows half:** the checkout at `%USERPROFILE%\.config\mise` IS mise's config dir there too; `MISE_ENV` persists as a User environment variable; a single `mise bootstrap --only dotfiles,tools --yes` (`Invoke-MiseBootstrap`) applies the whole dotfiles tree AND installs tools in one pass, straight against `config.toml` + `config.dev.toml` at the checkout root — `config.linux.toml` never loads there, so only the `config.dev.toml` tools without `os = ["linux"]` install on Windows (node, Go, uv, gopls, the language servers, ccstatusline); the Linux-only dev tools (herdr, opencode, omp, pwndbg, DevToys CLI) stay separate `$PortableTools` pins there instead. `Invoke-MiseRuntimes` then re-runs every bootstrap (self-heals the shims dir on the User `PATH`, sweeps legacy installs) — it is a second, idempotent pass, not the thing that installs the tools any more (that moved into `Invoke-MiseBootstrap`'s `mise bootstrap` call, PR3). **Why mise at all (the failure stories that motivated PR1, still the reasoning behind going further in PR2/PR3):** (1) the install paths mise replaced verified **nothing** the way mise does — hand-rolled `lib/node.sh`/`lib/go.sh` curl'd tarballs with no checksum and no signature. (2) `mise prune --yes` removes every installed version no config references, including ad-hoc installs made by hand outside the tracked config — so a pin belongs in `config*.toml`, never a bare `mise use -g <tool>` run by hand.
- **`python-env` is a both-scopes, USER-LEVEL global mise task (every host gets the ad-hoc scripting venv) — literally never sudo, unlike its dev-only `vcpkg` sibling (the other former sibling, `pwndbg`, is a mise tool now — see the C/C++ toolbelt entry below).** The posture matches the `pypi:basedpyright` mise tool in `config.dev.toml`: ad-hoc Python tooling belongs to the dev user, not `/usr/local`. `scripts/lib/python-env.sh` (moved from `makefile/lib/`; LF, 0755, shfmt/shellcheck-clean) takes `<python-version>`, runs `uv python install` (uv is mise-managed and resolves via the shims dir — the pinned CPython comes via python-build-standalone and lands user-level under `~/.local/share/uv/`), recreates `~/.local/share/workstation-python` from scratch (`rm -rf` first — deterministic, and it means any ad-hoc `uv pip install -p <env> <pkg>` addition is disposable, wiped on the next rebuild), then `uv pip install --python <env> --upgrade`s the nine-library canonical list held as a **one-line** bash array (`PY_LIBS`). **Why libs track latest but the runtime is exact-pinned:** these are ad-hoc scripting libs (the `pypi:glances`/`asciinema`/`harlequin` precedent — mise tools pinned to `"latest"` that self-refresh on every provision, never individually version-pinned); `python_version` in `config.toml`'s `[vars]` is the one thing that IS exact-pinned, because the venv's identity (and the install stamp) depends on it. **Why `wpy` is a wrapper script, not a symlink:** a symlink from `~/.local/bin/wpy` to the venv's `bin/python` loses the venv — CPython resolves the full symlink chain back to uv's base interpreter and never finds the `pyvenv.cfg` sitting next to the *resolved* target, so imports silently fail (verified 2026-08-03; see commit `60595c6`). The tiny `#!/bin/sh` wrapper that `exec`s the venv python by its real path keeps the venv, and lets nested shebangs (`#!/usr/bin/env wpy`) work. `textual`/`typer` stay plain symlinks — they're venv entry-point scripts whose OWN shebangs already point into the env, so the symlink-resolution problem doesn't apply to them. **Stamp composition:** `tasks/python-env` writes `~/.local/state/workstation/python-env.stamp` containing `$PYTHON_VERSION $(cksum scripts/lib/python-env.sh)` — so either a `python_version` bump OR an edit to the lib list (which lives inside that same script) changes the stamp content and triggers a rebuild on the next `mise run python-env`. Upgrading the latest-tracking libs deliberately: `REBUILD=1 mise run python-env` forces a rebuild regardless of the stamp — no more separate `clean-python-env`/`python-env` two-target race to worry about (the mise task is a single idempotent script; there is no parallel-goal hazard the way there was under Make's `-j$(nproc)`). **Windows half:** uv is mise-installed (`Invoke-PythonEnv` resolves it via `mise which uv` after `Invoke-MiseRuntimes`, and warns-and-skips when that comes back empty) + `Invoke-PythonEnv`, which builds `%LOCALAPPDATA%\workstation\python-env` from `$PythonEnvVersion`/`$PythonLibs` and writes the three `.cmd` shims into `workstation\bin`. **Why a uv-managed CPython at all, instead of the system interpreter:** this sidesteps the same EL9-ships-Python-3.9 floor that caps the GEF vendoring at release `2024.06` (see the C/C++ toolbelt entry below) — rather than being stuck on whatever `python3` the dnf base OS provides, `python-env` installs its own exact-pinned, independently-upgradable CPython via `uv python install`, so current `polars`/`duckdb`/`pydantic-core` wheels are available regardless of the host's system Python. No WSL skip (useful in a WSL dev guest, like `pwndbg`/`vcpkg`); no rc changes (`~/.local/bin` is already on PATH).
- **Machine-level Claude memory is `dotfiles/claude/CLAUDE.md` → `~/.claude/CLAUDE.md`**, a dev-only `[dotfiles]` `copy` entry in `config.dev.toml` (gated purely by the `dev` `MISE_ENV` token). Since the 2026-09-22 copy-migration the deployed file is an independent copy, not a symlink into the checkout — a live edit here (which Claude Code agents are routinely nudged to make directly) does not round-trip back to `dotfiles/claude/CLAUDE.md` on its own; `wsr` (`mise dot add --changed`) captures it, and `wsa` warns before an un-recorded edit would be overwritten (see the `[dotfiles]` mode bullet below). The `<!-- TOOLS:START -->` / `<!-- TOOLS:END -->` sentinel block is auto-generated by `scripts/gen-tool-memory.sh`, which reads `config*.toml` alone now — `config.toml`/`config.linux.toml`/`config.dev.toml`'s `[tools]` tables for every mise tool pin, `config.toml`'s `[vars]` for the pins Make used to own, `config.host.toml`/`config.native.toml`'s `[bootstrap.packages]` for dnf lists — as its single source of truth. **Hand-edits inside the sentinels are clobbered** by the next generator run. `scripts/check-invariants.sh` runs the generator against a temp file and diffs to enforce zero drift in CI. The hook `.claude/hooks/sync-tool-memory.sh` regenerates on every edit to `config.toml`/`config.*.toml` (PostToolUse). Add a guidance prose section outside the sentinels; the block structure (categories, commands, versions) is driven entirely by the generator.
- **`workstation-lsp` is a declarative skills-dir plugin; it installs nothing.** Source: `dotfiles/claude/skills/workstation-lsp/`, nested inside the dev-only `[dotfiles]` `copy` entry for the whole `~/.claude/skills` directory in `config.dev.toml`. Three files, all real names now (no `dot_`/`private_` prefixing): `.claude-plugin/plugin.json` (plugin manifest), `.lsp.json` (server registry, deployed as-is to `~/.claude/skills/workstation-lsp/.lsp.json`), `SKILL.md` (marker + diagnostics toggle note). Auto-loads by presence once deployed; the enforced `workstation-lsp@skills-dir` entry in `dotfiles/claude/settings.enforced.json`'s `enabledPlugins` block is belt-and-suspenders. **`.lsp.json` MUST be strict JSON** — the runtime `LSP` loader rejects JSONC `//` comments (all 12 servers fail to load silently). `claude plugin validate` is JSONC-tolerant and will NOT catch this; test with `python3 -m json.tool .lsp.json`. Diagnostics are on by default (the `"diagnostics": false` per-server toggle is documented in `SKILL.md`, not in `.lsp.json`). `check-invariants.sh` runs `claude plugin validate --strict` over the plugin source directory as a soft check.   Per-host SSH launch profiles are deliberately NOT hand-added to `settings.json` — WT's dynamic-profile **fragment** extension point owns them, so `hosts.conf` churn never touches the tracked static file. `Invoke-WindowsTerminalFragments` runs every bootstrap (self-heals) and writes exactly one file, `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\workstation\hosts.json`, with one `profiles[]` entry per `hosts.conf` row (`SSH: <host>`, `commandline: ssh -t <user>@<ip> zellij attach --create main`, dev/prod tab color). The `workstation` fragment directory is the wholly-owned managed namespace — the step wipes **only** the `*.json` files directly inside it before regenerating, never the directory itself and never a sibling app's fragment directory (`Fragments\<other-app>\*.json` survives untouched by construction: the wipe globs one specific path). GUIDs are deterministic RFC 4122 v5 (`New-Uuid5`), chained `{f65ddb7e-706b-4499-8a50-40313caf510a}` (fixed namespace constant, WT's own fragment-GUID convention) → `"workstation"` (app-namespace name) → `"SSH: <host>"` (profile name) — each name's bytes are hashed as **UTF-16LE** (`[System.Text.Encoding]::Unicode.GetBytes`), so profile identity survives every regeneration even though the file itself is rewritten wholesale each run. WT reads fragments only at launch, so a `hosts.conf` edit needs a WT restart to show up — the step's success message says so. `disabledProfileSources: ["Windows.Terminal.SSH"]` in the tracked `settings.json` is load-bearing here: WT 1.24 ships its own SSH-config-derived dynamic profile source, which would otherwise duplicate every managed host as a second, `zellij`-less entry.
  Nothing in `Invoke-WindowsTerminalFragments` or `Install-WindowsTerminal` may write to the tracked `settings.json` — that file is the human/Settings-UI side (theme, keybindings, `profiles.defaults`, `newTabMenu`); the generator's only output is the fragment JSON. Mixing the two would make `wsr` fight the generator on every apply.
- **Warp Terminal — the PRIMARY managed Windows terminal, full detail.** `Install-Warp` is a best-effort evergreen winget seed, structurally the twin of `Install-WindowsTerminal`: `Test-InstallerPresent -DisplayName "Warp"` (HKCU Uninstall key `warp-terminal-stable_is1`) detects an existing install; absent that, `winget install --id Warp.Warp --exact --scope user --silent` — `--scope user` maps to Warp's Inno `/CURRENTUSER` switch, so **no UAC**, and Warp self-updates afterward, so there is **no pin to track** and no `$InstallerTools` entry (Warp publishes no GitHub release assets to hash — winget's manifest is the hash authority). No winget on PATH soft-warns with https://www.warp.dev/download instead of failing. `-ForceInstaller` adds `--force`; `-SkipToolInstall` skips it. One caveat worth knowing: winget resolves Warp's declared `Microsoft.VCRedist.2015+` dependency, and on a box missing the VC++ runtime entirely that dependency install is machine-scope and *can* pop a UAC prompt — declining it is survivable.
  `[dotfiles]` `copy`-mode entries in `config.windows.toml` track **three static Warp files** — `dotfiles/windows/AppData/Local/warp/Warp/config/settings.toml`, `.../keybindings.yaml`, and `dotfiles/windows/AppData/Roaming/warp/Warp/data/themes/catppuccin-mocha.yaml`. Warp splits its state deliberately: `%LOCALAPPDATA%\warp\Warp\config\` is machine-local config, `%APPDATA%\warp\Warp\data\` is roaming/portable data (themes, tab configs) — the tracked paths mirror that split exactly, so do not "tidy" them into one tree. Same **sync-from-host** drift model as WT's `settings.json`: Warp's Settings panel rewrites `settings.toml` and Warp hot-reloads external edits, so re-capture UI changes with `wsr` (`mise dot add --changed`) (`is_settings_sync_enabled = false` is load-bearing — it stops Warp's cloud sync from fighting the next `wsa` for authorship). The theme is referenced by the **relative** filename `catppuccin-mocha.yaml`, never an absolute path (warpdotdev/warp#9723). Windows-only by construction — declared only in `config.windows.toml`, which never loads on Linux (no separate ignore-list needed).
  Warp has no profile list; its `+` menu is the launch surface, so unlike WT the **local** shells need generated entries too. `Invoke-WarpTabConfigs` runs every bootstrap (self-heals) and writes `%APPDATA%\warp\Warp\data\tab_configs\workstation-*.toml`: three local entries (`WSL: AlmaLinux-9`, `Windows PowerShell`, `Nushell (compatibility)`) plus one `workstation-ssh-<slug>.toml` per `hosts.conf` row running the same load-bearing `ssh -t <user>@<ip> zellij attach --create main` as the WT fragment, green (`dev_machine`) / cyan (prod). **The `workstation-` prefix IS the managed namespace** — the step wipes only `workstation-*.toml` in that directory, so user-created Tab Configs survive by construction (the exact counterpart of WT's "only `*.json` inside the `workstation` fragment dir"). Same rule as WT: nothing in `Invoke-WarpTabConfigs` or `Install-Warp` may write to a dotfiles-tracked file — the generator's only output is the `workstation-*.toml` set, or `wsr` and the generator would fight on every apply.
  **Two things Warp cannot do**, both load-bearing for why WT stays fully managed: it cannot register as Windows' *default terminal application* (warpdotdev/warp#6261 — console handoff stays WT's job), and it **does not support Nushell** (supported shells are pwsh 7 / PowerShell 5 / WSL2 / Git Bash; an unsupported login shell gets a banner and a PowerShell fallback). Hence Warp's `session.new_session_shell_override = { custom = "wsl.exe --distribution AlmaLinux-9 --cd ~" }` — the `{ custom = … }` shape sidesteps the executable-path validation that rejects `wsl.exe` (warpdotdev/warp#7576), re-verified 2026-08: `new_session_shell_override` still accepts only `"system_default"` / `{ executable = … }` / `{ custom = … }`, with no first-class WSL value. Nushell's first-class home stays WT's `defaultProfile`.
  The rc files carry **runtime `TERM_PROGRAM != WarpTerminal` guards** (`dotfiles/zshrc.tera`: fzf, atuin, starship, zsh-shift-select, the fzf-tab zstyles + source; `dotfiles/bashrc.tera`: fzf, starship — a parity pair) because Warp owns the input editor and supplies its own equivalents. They are runtime-only, so WT/SSH/WSL sessions are untouched. **Scope discipline is the tripwire here:** commit `c9709cf` documents the last time the fzf-tab guard's `fi` was allowed to swallow the whole plugin-load section, silently disabling zsh-autosuggestions, zsh-syntax-highlighting, zsh-you-should-use and zsh-history-substring-search. Guard each block with its own single-line condition; the one multi-line guard (the two fzf-tab zstyles) closes immediately and says so on its `fi`.
- **Post-install binary verification gate.** Under Make's per-tool macros this used to be an install-time `&&`-chain onto each tool's install command, so a bad binary failed *that tool's* install before its stamp was written; mise owns install ordering and has no per-tool stamp to gate, so it is a **post-install** sweep instead, wired as `config.linux.toml`'s `post-tools` hook (`"post-tools" = "mise run verify-tools"`) — mise calls it automatically right after the tools phase of ANY `mise install`/`mise bootstrap` invocation completes. `tasks/verify-tools` walks every bin dir `mise bin-paths` exposes and runs `scripts/lib/verify-binary.sh` (moved from `makefile/lib/` to `scripts/lib/`, same logic) on every ELF it finds — script "tools" (nb, sysz, ssh-copy-id, cht.sh) pass through untouched since they never match the ELF-magic check. A failure fails the whole tools phase loudly; the fix is an explicit `github:` `asset_pattern` for that tool in `config*.toml` (converting silent "installed but won't run" successes — the historical fastfetch musl-loader and usql glibc-floor breakages — into loud, retryable stops, same as before).
  - **Non-executing**: ELF magic + `e_machine` arch, then `ldd` (static → PASS; any `not found` → FAIL), then glibc-floor via `objdump`/`readelf`.
  - **Static binaries MUST pass** (most musl-asset tools are static). Do not "tighten" the check to fail non-dynamic binaries — it would false-fail the many musl tools in `config.linux.toml`.
  - **Degrades**: no `objdump`/`readelf` (minimal prod) → skip the glibc-floor sub-check with a note; keep ELF+arch+ldd.
  - **Symlinked bins are followed, not skipped** — mise's `.mise-bins/` shim indirection means a bin-path entry is often a symlink; `[ -f ]`, `head -c4`, and `verify-binary.sh` itself all resolve through it (a plain `find` without `-L` would miss them).
  - Verify with: `MISE_CONFIG_DIR=$PWD MISE_DATA_DIR=/tmp/mise-sandbox MISE_ENV=linux,dev,host,native mise install && MISE_DATA_DIR=/tmp/mise-sandbox tasks/verify-tools` — a passing run prints `✓ verify-tools: N ELF binaries pass (arch, loader, glibc floor)`.
- **SSH connection multiplexing is gated out on Windows.** `dotfiles/ssh/config.tera` (`template` mode, `config.toml` — cross-platform, os()-branches internally) keeps its `ControlMaster auto` / `ControlPersist 60s` / `ControlPath ~/.ssh/cm-%r@%h:%p` block under `Host *` inside a `{% if os() != "windows" %}…{% endif %}` gate. Windows OpenSSH can't multiplex — the muxed connection runs over a handle that isn't a Winsock socket, so `getsockname()` returns `WSAENOTSOCK` (`getsockname failed: Not a socket`) and the session hangs until `ServerAlive` trips (`Timeout, server <host> not responding.`). This breaks **every** Windows ssh, including git's SSH transport to GitHub — a chicken-and-egg, since pulling the fix itself needs ssh: break the loop with a one-shot `GIT_SSH_COMMAND="ssh -o ControlMaster=no -o ControlPath=none" git pull`, then `wsa` strips the block from the deployed config for good. The gate deliberately keeps multiplexing on Linux/macOS (load-bearing for `scripts/update-hosts.sh` bulk runs + interactive `ssh`/`scp`/`rsync` reuse). Don't move `ControlMaster` outside the gate, and don't rename the source away from `.tera`/`template` mode. Per-host opt-out anywhere (incl. a stale Windows host pre-apply): `ControlPath none` in `~/.ssh/config.local` (Included first, first-match-wins). Verify after apply: `ssh <managed-host> hostname` connects with no `-o` overrides.
